# Безопасность прошивки FloatCore

Документ отвечает на один вопрос: **почему эта прошивка физически не может
сформировать команду мотору или кадр CAN через реализованный программный
путь.** Не «мы не будем», а «нечем».

Область действия — лабораторный профиль `FLOATCORE_LAB_SAFE`, этапы
v0.5–v0.6x. Как только появится реальный передатчик, документ обязан быть
переписан целиком. Список того, что для этого надо сделать, — в разделе
«Requirements before enabling motor output» в конце.

---

## 1. Единственный путь от Refloat к мотору

SDK VESC содержит двенадцать функций, способных что-либо подать на мотор.
Список получен вычиткой `refloat-upstream/vesc_pkg_lib/vesc_c_if.h:436-447,
476, 653`, а не по памяти:

```
mc_set_current            mc_set_duty            mc_set_handbrake
mc_set_brake_current      mc_set_duty_noramp     mc_set_handbrake_rel
mc_set_current_rel        mc_set_pid_speed       mc_release_motor
mc_set_brake_current_rel  mc_set_pid_pos         foc_play_tone
```

`foc_play_tone` в списке не по ошибке: звук на VESC издаётся подачей
напряжения на обмотки, то есть это тоже выход на мотор.

**Все двенадцать указателей заполнены и ведут в одну функцию.** Заполнены
именно все, а не только используемые Refloat: оставленный NULL — это место,
куда однажды впишут прямой вызов мимо политики.

```
Refloat → VESC_IF->mc_set_*()
        → fc_motor_gate_request(kind, value, now)
              ├─ 1. значение конечно и в пределах лимита?
              ├─ 2. супервизор не в FAULT?
              ├─ 3. состояние разрешает выход?      ← в LAB_SAFE: никогда
              └─ 4. backend существует?             ← в LAB_SAFE: нет как кода
        ← возврат. Всё.
```

Дальше кода нет. Устройство политики и счётчики — `safety_supervisor.md`.

## 2. Пять независимых причин, почему выхода нет

Каждая из них по отдельности достаточна.

### 2.1 В прошивке нет драйвера CAN

Ни один файл не включает `driver/twai.h` и не вызывает функций `twai_*`.
Компоновщик это подтверждает — в `.elf` **ноль** символов TWAI:

```
$ xtensa-esp32-elf-nm build/floatcore_esp32.elf | grep -i twai
(пусто)
```

Проверка автоматизирована и входит в `tools/esp32_smoke.sh` (шаг 4): наличие
хотя бы одного символа TWAI объявлено stop condition и валит прогон. Там же
проверяется отсутствие символов `fc_motor_gate_set_backend`,
`manual_set_current`, `manual_set_duty`, `motor_can_send`,
`real_motor_backend`, `safety_bypass` и присутствие `refloat_init`,
`fc_motor_gate_request`, `fc_supervisor_poll`, `icm20948_read`.

Единственные совпадения по подстроке `can_` в прошивке —
`can_engage` (функция состояния самого Refloat, к шине отношения не имеет),
`fc_can_backend_name` (наша строка для консоли) и `s_flash_op_can_start`
(внутреннее имя ESP-IDF).

### 2.2 Пины не сконфигурированы

Ни один GPIO не переводится в режим CAN: нет ни `gpio_set_direction`, ни
подключения к матрице периферии. `VESC_IF->io_set_mode()` и
`VESC_IF->io_write()` реализованы как заглушки, возвращающие `false`, — даже
пищалка не заводится.

### 2.3 Трансивера нет физически

К плате не подключён ни CAN-трансивер, ни VESC, ни мотор (ТЗ §19). Даже если
бы драйвер существовал и пины были настроены, на шине не было бы уровней.

### 2.4 Backend физической отправки не существует как код

В профиле `FLOATCORE_LAB_SAFE` макрос `FC_MOTOR_BACKEND_AVAILABLE` равен нулю,
и функция `fc_motor_gate_set_backend()` **не объявляется и не определяется**.
Зарегистрировать backend нечем.

Это проверяется не на слово: отдельная компиляция файла с вызовом этой функции
падает с ошибкой «call to undeclared function», а в таблице символов её нет.

### 2.5 Разрешение на выход — компилируемая константа

`fc_supervisor_motor_output_permitted()` в лабораторном профиле возвращает
литеральный `false`. Компилятор видит это и выкидывает недостижимые ветки.
Ни одно состояние супервизора, включая `READY`, разрешения не даёт;
`ARMED`/`RUNNING` недостижимы, потому что переходов в них не написано.

**Снять блокировку одним флагом или параметром нельзя.** Нужно сменить профиль
сборки, написать код передачи, включить компонент драйвера, настроить пины,
подключить трансивер. Это отдельный этап с отдельной ревизией.

## 3. Что видно в трассе

Блокировка не молчаливая: каждый запрос считается и классифицируется. Команда
`safety` в любой момент:

```
SUPERVISOR   state=DISARMED faults=none(0x00000000) latched=0x00000000
  profile    LAB_SAFE
  imu(hw)    OK age=2.3 ms ok=31434 errors=0 stuck=0 stale=0
  loop       500.0 Hz p99=2480 us max=3166 us late=1266 missed=0
  footpad    NONE
  cfg_write  allowed (принято=1 отклонено=0 коммитов=1, худший 5061 мкс)
  motor      requested=30681 rejected(disarmed=30681 fault=0 invalid=0)
             allowed=0 sent=0 backend=none (blocked)
  can        unavailable (TWAI не собран, трансивер не подключён)
```

`physically_sent` инкрементируется исключительно backend-ом физической
отправки. Его в этой сборке нет, поэтому счётчик обязан всегда быть нулём —
это проверяется в каждом host-тесте и в smoke-скрипте.

Соотношение «одна команда на семпл IMU» сходится: 30 681 запрос за 62 с при
контуре 500 Гц.

## 4. Footpad: почему доска считается неактивированной

Решение Refloat принимает так (`refloat-upstream/src/footpad_sensor.c:31`):

```c
bool adc1_on = config->fault_adc1 == 0.0f || adc1 > config->fault_adc1;
```

Датчик считается нажатым, если напряжение **выше** порога. Пороги по
умолчанию — 2.00 В (`settings.xml`, `fault_adc1`/`fault_adc2`). Платформа
отдаёт **0.00 В**, что ниже любого допустимого ненулевого порога из диапазона
0.01…3.30 В — это перебором проверено host-тестом.

Значение −1.0 В («пина нет на железе») намеренно не используется: оно тоже
ниже порога, но означало бы «канала не существует», а мы сообщаем «канал есть
и он отпущен».

**Отдельный опасный случай, который значением ADC не лечится.** Если порог
выставлен в 0, первая ветка условия делает зону нажатой **всегда**, при любом
напряжении. Поэтому фактическое состояние проверяется не по ADC, а по самому
Refloat: прошивка после старта печатает

```
[floatcore] footpad: NONE, adc 0.00/0.00 V, пороги 2.00/2.00 V -> DISENGAGED (ok)
```

и логирует ошибку, если состояние окажется не `FS_NONE`. Это прямая проверка
stop condition из ТЗ («mock ADC приводит Refloat в engaged state»).

## 5. Mock IMU: почему покой — это покой

Контракт выведен из upstream, а не назначен (подробности —
`platform/esp32/main/fc_imu_mock.c`):

| Величина | Значение | Обоснование |
|---|---|---|
| `imu_get_roll/pitch/yaw` | 0 рад | `imu.c:36-40` оборачивает в `rad2deg()` |
| `acc` в callback | (0, 0, +1) g | `balance_filter.c:100` при единичном кватернионе даёт направление гравитации +Z; любой другой вектор заставил бы Mahony доворачивать доску |
| `gyro` | (0, 0, 0) рад/с | `balance_filter.c:114-125` интегрирует `q += 0.5*q*g*dt` |
| кватернион | (1, 0, 0, 0) | покой |
| `dt` | реальный интервал `esp_timer` | `frequency_tracker`/`latency_tracker` считают частоту по нему |

Результат на плате: `pitch/roll 0.000 / 0.000 deg` и `imu 500.0 Hz` по
счётчикам самого Refloat.

`imu_startup_done()` возвращает `false` первые 1.5 секунды — как время
калибровки гироскопа на VESC. Пока он `false`, Refloat остаётся в
`STATE_STARTUP`, то есть в безопасном состоянии по умолчанию.

## 6. Радио выключено

`CONFIG_BT_ENABLED=n`, `CONFIG_ESP_WIFI_ENABLED=n` в `sdkconfig.defaults`.
Ни Wi-Fi, ни BLE не инициализируются, provisioning не делается, транспорт
VESC Tool на плату не переносился (ТЗ §18). Ядро 0 остаётся свободным, контур
целиком на ядре 1.

## 7. Инвентарь диагностических команд

Консоль (`platform/esp32/main/fc_console.c`) не имеет доступа ни к одной
функции, способной что-либо запросить у мотора. Классификация выражена
структурой файла, а не только таблицей ниже.

### SAFE_READONLY — компилируются всегда

| Команда | Что делает |
|---|---|
| `status` | состояние системы, супервизора и Refloat |
| `supervisor` | состояние, причины отказов, все входы |
| `imu` | конфигурация датчика, статистика, последний сырой семпл |
| `timing` | периоды и время исполнения всех задач |
| `timing-hist` | гистограмма периодов контура |
| `tasks` | остаток стека по задачам |
| `heap` | куча |
| `config` | конфигурация, политика записи, статистика |
| `safety` | сводка безопасности и счётчики Motor Gate |
| `imu-cal-show` | текущая калибровка, её статус и ход измерения |
| `i2cscan` | опрос адресов 0x08…0x77 и чтение `WHO_AM_I` у ответивших |
| `help` | список команд |

`i2cscan` относится сюда с оговоркой, которую стоит сделать явно: чтобы
прочитать `WHO_AM_I`, команда выбирает нулевой банк записью в `BANK_SEL`. Это
переключение окна регистров, которое драйвер выполняет и при каждом обычном
чтении, а не изменение конфигурации датчика. Если шина не поднята, команда
поднимает её — ради этого случая она и добавлена.

### STATE_CHANGING — только при `FC_LAB_DIAGNOSTICS`

Меняют состояние системы, но физически безопасны.

| Команда | Что делает | Почему безопасна |
|---|---|---|
| `ready` | `DISARMED → READY` | `READY` не разрешает тягу ни в одном профиле |
| `disarm` | `READY → DISARMED` | снятие готовности всегда безопасно |
| `fault-clear` | снять залипший отказ | не проходит, пока причина активна |
| `persist` | записать косметический параметр яркости LED | подчиняется политике записи; лента не подключена |
| `timing-reset` | обнулить статистику | только счётчики |
| `restart` | `esp_restart()` | перезагрузка возвращает систему в `BOOT` |
| `imu_stress [сек] [кГц] [порог_сброса]` | стресс-тест шины I2C: замещает штатную задачу чтения и читает ICM-20948 без пауз (~1640 Гц). Необязательные аргументы — частота шины и число отказов подряд до сброса шины (0 — не сбрасывать) | только шина датчика; Refloat всё это время работает от mock-IMU, Motor Gate не затрагивается. Задача пиннится на ядро housekeeping, контур не трогает — см. `fc_imu_stress.c` |
| `imu_stress-stop` | досрочно завершить тест | снимает флаг; штатное чтение восстанавливается автоматически |
| `imu_stress-log` | показать предысторию первого отказа | только печать сохранённого кольца |
| `imu-cal-detect [yaw]` | измерить калибровку ориентации и смещений | ничего не записывает во flash; на движущейся доске не завершается |
| `imu-cal-save` | записать измеренную калибровку | подчиняется политике записи: только в `DISARMED`, коммит делает задача хранилища |
| `imu-cal-clear` | стереть калибровку, вернуть единичную | то же; после стирания READY недостижим |

### LAB_DIAGNOSTICS — только при `FC_LAB_DIAGNOSTICS`

Намеренно ломают подсистему, чтобы доказать, что защита срабатывает.
Требуют подтверждения прямо в имени команды.

| Команда | Что делает | Что доказывает |
|---|---|---|
| `wdtest-confirm` | контур не отмечается 8 с | супервизор ловит `LOOP_STALL` за 1.5 с, TWDT — за 8.6 с |
| `crashtest-confirm` | разыменование нулевого указателя | panic печатает причину, регистры, backtrace и останавливает CPU |
| `imu-fail-confirm` | 500 ошибок чтения подряд | `READ_ERROR` → `FAULT (IMU_UNHEALTHY)` |
| `imu-freeze-confirm` | 500 повторов одного семпла | `STUCK` → `FAULT (IMU_UNHEALTHY)` |
| `imu-stop-confirm` | остановить задачу чтения | нужна для сравнительных прогонов тайминга |
| `imu-start` | запустить её заново | — |

### SAFETY_BYPASS и MOTOR_OUTPUT

**Таких команд не существует.** Ни одной команды, способной ослабить политику
безопасности или подать что-либо на мотор, в прошивке нет. Проверяется
поиском символов `manual_set_current`, `manual_set_duty`, `motor_can_send`,
`safety_bypass` в `.elf`.

### Что будет в профиле мотора

В `FLOATCORE_MOTOR_CAPABLE` макрос `FC_LAB_DIAGNOSTICS` равен нулю, поэтому
две последние категории **не компилируются вовсе**. Это не флаг, который можно
переключить во время работы: соответствующих функций в двоичном файле нет.

## 8. Requirements before enabling motor output

Исчерпывающий список того, что должно быть сделано **до** того, как хоть одна
команда сможет уйти на мотор. Пока хотя бы один пункт открыт, профиль
`FLOATCORE_MOTOR_CAPABLE` собирать и прошивать нельзя.

### A. Датчик и ориентация

1. **Финальный механический монтаж IMU.** Сейчас модуль закреплён временно;
   гравитация распределена между двумя осями.
2. **Привязка осей датчика к осям доски** с физическим обоснованием каждой
   перестановки и инверсии — не подбором «пока UI не выглядит правильно».
   *Измерено на этапе v0.6B (`imu_orientation_mapping.md`), но получено на
   прежнем монтаже: после переборки железа требует повторного подтверждения.*
3. ~~**Передача реальных данных в Refloat** через `VESC_IF->imu_*` и проверка
   pitch/roll ручным наклоном.~~ *Выполнено на v0.6D
   (`real_imu_refloat_integration.md`): Refloat работает от физического
   ICM-20948, знаки подтверждены шестью движениями и знаком запрошенного тока.*
4. **Калибровка**: смещения акселерометра, нулевое смещение гироскопа, ноль
   pitch/roll доски. *Частично: на v0.6D реализована стартовая калибровка
   смещения гироскопа (только на неподвижной доске, с проверкой правдоподобия
   и блокировкой READY до завершения) — расхождение двух источников углов
   упало с 2.7° до 0.2°. НЕ сделано: смещения акселерометра и ноль монтажа
   доски. Наклон покоя +6.5° больше, чем `startup_pitch_tolerance` = 4°, —
   в этом положении доска не входит в RUNNING.*
5. **Аппаратный DRDY** вместо программного опроса, чтобы ритм задавал датчик.
6. **Детекция потери семплов** по счётчику датчика, а не только по возрасту.

### B. Реальное время

7. **Слияние задачи чтения датчика и контура в одну.** Сейчас две независимые
   задачи с одинаковым периодом конкурируют и дают 3 % опозданий
   (`realtime_timing.md` §3, гипотеза 4).
8. **Перемер времени исполнения контура на реальных данных**: сейчас
   `imu_ref_callback` работает на mock-нулях.
9. **Проверка гипотезы о вымывании кэша** (рост времени исполнения с 93 до
   179 мкс при активном I2C).

### C. Супервизор

10. **Входы ESC**: живость обоих контроллеров, их коды отказов, свежесть
    телеметрии по CAN.
11. **Напряжение батареи и температуры** как условия работы.
12. **Состояния `ARMED`/`RUNNING`** и правила перехода в них, включая явное
    действие человека.
13. **Независимый контроль.** Сейчас супервизор — задача на том же ядре 1, что
    и контур. Если ядро встанет целиком, остаётся только TWDT.
14. **Пересмотр `CONFIG_ESP_TASK_WDT_PANIC`.** Для сборки с мотором логика
    обратная: при срыве контура безопаснее перезагрузиться, чтобы тяга снялась
    по watchdog самого VESC.

### G. Проверки, появившиеся на v0.6D

26. **Направление вращения при положительном токе.** Измерено, что нос вниз
    даёт положительный запрошенный ток, а нос вверх — отрицательный. Но
    соответствие «положительный ток → колесо вперёд» определяется фазировкой
    мотора и настройками ESC и на стенде без мотора недоказуемо. Проверить с
    вывешенным колесом и ограничением тока.
27. **Единицы `imu_get_gyro()`.** Выведены из масштабов PID (°/с), а не
    прочитаны в исходниках VESC. Ошибка стоит 57-кратного промаха в
    демпфирующем члене. Подтвердить по bldc или на живом VESC.
28. **Полоса ФНЧ акселерометра против частоты контура.** 246 Гц при Найквисте
    250 Гц — на грани. Либо сузить полосу, либо обосновать, что запаса
    достаточно.
29. ~~**Механизм нуля монтажа** как отдельное платформенное понятие
    калибровки, не правкой осей датчика.~~ *Реализовано на v0.6E по модели
    прошивки VESC: `imu_calibration_architecture.md`,
    `imu_calibration_workflow.md`. Осталась калибровка смещений
    акселерометра — штатный мастер её делает отдельным шагом, у нас процедуры
    нет.*
30. **Проверка порогов калибровки гироскопа на финальном монтаже.** Сама
    калибровка реализована на v0.6D, но пороги (неподвижность 3 °/с, потолок
    правдоподобия 5 °/с) подобраны под стенд.

31. **Параметры мотора в платформенном слое — заглушки.** Сейчас
    `foc_motor_flux_linkage = 0.0045` и `l_current_max = 10 А`
    (`fc_vesc_if.c:757, 764`). Из них Refloat выводит `speed_constant`
    = 9.88 А/Н·м и полный коэффициент контура **120 ампер на градус**: при
    остаточном наклоне в сотые доли градуса запрошенный ток насыщается. До
    включения мотора эти значения обязаны прийти из реальной конфигурации ESC.
32. **Калибровка смещений акселерометра.** Модель поле предусматривает,
    процедуры нет.
33. **Пороги неподвижности при Detect** подобраны под лабораторный стенд и
    требуют подтверждения на доске, которую держат ноги.

### D. Шина и мотор

15. **Драйвер TWAI** и протокол VESC поверх него.
16. **Аппаратный watchdog команды на стороне ESC** (`timeout_msec` около
    100 мс), проверенный отключением передачи.
17. **Ограничение тока на уровне ESC**, а не только в нашей политике.
18. **Стендовая проверка** с колёсами в воздухе и ограничением тока, до
    любого человека на доске.

### F. Шина I2C — квалификация на финальном железе

Ни один пункт этого раздела не выполнен. Стенд, на котором получены текущие
измерения, временный: длина жгута, его прокладка и механическая фиксация
модуля ещё не определены, а значит результаты нельзя переносить на финальную
конструкцию.

```text
Before enabling motor output:

- IMU must be installed in final mechanical configuration.
- Final I2C harness length/routing must be used.
- SDA/SCL pull-up configuration must be documented.
- I2C stress test must be repeated on final hardware.
- Mechanical stress test must complete with:
    failed_reads == 0
    timeouts == 0
    recoveries == 0
    bus_resets == 0
```

21. **Финальная механическая конфигурация IMU** — не временное крепление.
22. **Финальные длина и прокладка жгута I2C.**
23. **Конфигурация подтяжек SDA/SCL задокументирована.** Текущее измеренное
    значение — 10 кОм на модуле, см. `i2c_stress_test.md`; для финального
    жгута его придётся подтвердить заново.
24. **Стресс-тест шины повторён на финальном железе** командой `imu_stress`.
25. **Механический стресс-тест пройден** с `failed_reads == 0`,
    `timeouts == 0`, `recoveries == 0`, `bus_resets == 0` на протяжении не
    менее двух минут воздействия. Ослаблять этот критерий ради зелёного
    результата нельзя: он и существует для того, чтобы поймать именно то, что
    уже ловил.

### E. Сборка

19. **Удаление категорий `LAB_DIAGNOSTICS` и `STATE_CHANGING`** из профиля
    мотора — уже обеспечено `FC_LAB_DIAGNOSTICS`, но требует проверки в
    собранном двоичном файле.
20. **Расширение символьных проверок** под новый профиль: там TWAI будет
    присутствовать, поэтому проверять придётся не отсутствие, а корректность
    единственного пути.

## 9. Как проверить утверждения этого документа

```bash
. ~/esp/esp-idf/export.sh
tools/esp32_smoke.sh    # символьные проверки профиля LAB_SAFE и маркеры загрузки
make test               # 120 протокольных + 11 сценариев Refloat + 29 платформы + 61 безопасности
python3 tools/esp32_serial.py --seconds 12 --send safety --send supervisor
```

Отдельно проверяется, что backend мотора нельзя зарегистрировать: компиляция
файла с вызовом `fc_motor_gate_set_backend()` в профиле LAB_SAFE падает,
потому что функции не существует.
