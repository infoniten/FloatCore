# План первого подключения мотора

**ЭТО ПЛАН, А НЕ ПРОЦЕДУРА К ИСПОЛНЕНИЮ.** Составлен на этапе v0.7C, когда
моторы физически отключены и ни одна его строка не выполнялась. Ни один шаг
не должен быть начат без отдельного решения и без закрытия блокеров из §8.

---

## 1. Порядок, а не список

Шаги строго последовательны, и каждый следующий имеет смысл только после
предыдущего. Соблазн переставить обычно возникает там, где предыдущий шаг
неудобен, — и именно там он и нужен.

## 2. Шаг 0 — до того, как что-либо подключать

| Что | Зачем |
|---|---|
| **Резервная копия конфигурации** обеих половин через VESC Tool: `Motor CFG → Read`, затем сохранить `.xml`, и то же для `App CFG` | детекция перезапишет mcconf; без копии откатиться будет не к чему |
| Сохранить сырые блобы через `tools/vesc_audit.py` | побайтовый эталон, независимый от VESC Tool |
| Записать текущие значения из `motor_parameter_model.md` | чтобы после детекции было с чем сравнить |
| **Проверить напряжение питания: `v_in > 34 В`** | при 30 В (нынешняя настройка лабораторника) `l_battery_cut_end = 31 В` даёт входной ток **ноль**, и прокрут не состоится — тест покажет ложный отрицательный результат |
| Проверить `app_to_use` | см. §6 |

Порядок копирования важен: сначала копия, потом всё остальное. Копия,
сделанная после первого изменения, — это уже не копия.

## 3. Шаг 1 — механика

* Колесо **вывешено**. Не «придержано», не «на подставке, но касается» —
  вывешено так, чтобы свободно вращалось и чтобы его вращение никого не
  задевало.
* Доска закреплена: при подаче тока она попытается развернуться.
* Ничего вращающегося не находится рядом с руками, кабелями и лицом.
* Питание — от источника с ограничением тока, а не от батареи. Ограничение
  источника — ещё один барьер, единственный по-настоящему независимый от
  прошивок.

## 4. Шаг 2 — один мотор, не два

Подключается **одна половина**, ID 118. Вторая остаётся отключённой.

Причина: половины Dual FSESC различаются измеренными R и L (0.3196 против
0.3162 Ом, 730 против 866 мкГн), то есть детекция для них делалась раздельно.
Если что-то пойдёт не так, разбираться с одним мотором вдвое проще, а
вероятность перепутать половины — нулевая.

## 5. Шаг 3 — детекция: через VESC Tool по USB, не через FloatCore

**Решение: детекцию делать штатным VESC Tool по USB.**

| | VESC Tool по USB | FloatCore по CAN |
|---|---|---|
| Код, который крутит мотор | отлажен годами на тысячах аппаратов | будет написан ради одного применения |
| Что нужно добавить в FloatCore | ничего | `COMM_DETECT_*` в белый список, то есть право крутить мотор |
| Обратимость | штатный откат в VESC Tool | наша |
| Наблюдение за процессом | готовый интерфейс с графиками | пришлось бы делать |

Автоматизация здесь не выигрывает ничего, а стоит того, что в белый список
передачи пришлось бы внести команды детекции — то самое право крутить мотор,
отсутствие которого и есть главная гарантия этапов v0.7A–v0.7C.

**Белый список остаётся неизменным:** `PING`, `FW_VERSION`, `GET_VALUES`,
`GET_MCCONF`, `GET_APPCONF`. FloatCore на этом шаге — наблюдатель.

### Что детекция изменит в mcconf

| Параметр | Меняется | Обязателен к перечитыванию после |
|---|---|---|
| `foc_motor_r` | да | да |
| `foc_motor_l` | да | да |
| `foc_motor_flux_linkage` | да | да |
| `foc_observer_gain` | да | да |
| `foc_current_kp` / `foc_current_ki` | да | да |
| `si_motor_poles` | **нет** | детекция его не определяет (см. §5.1) |
| `l_current_max` / `min` | **не должна** | проверить, что не изменились |
| отсечки по напряжению | **не должна** | проверить, что не изменились |

Сразу после детекции — перечитать конфигурацию **через CAN средствами
FloatCore** и сверить с копией: это заодно ещё раз проверит, что канал
чтения работает, и покажет ровно то, что детекция изменила.

### 5.1. Число полюсов — отдельным измерением

Детекция полюса не определяет. Измерение: раскрутить вывешенное колесо на
известных оборотах, сравнить механическую скорость с ERPM.

```
число пар полюсов = ERPM / (механические об/мин)
si_motor_poles = 2 × число пар
```

Нынешнее значение 14 (7 пар) не подтверждено ничем и для мотор-колеса
выглядит нетипично — у них обычно 30 (15 пар). Пока измерение не сделано,
любой расчёт, где участвует скорость, недостоверен.

## 6. Шаг 4 — `app_to_use`

**Вывод: `UART` можно оставить, `No App` строго безопаснее, разница
практическая — нулевая.**

Обоснование по исходникам. `app_to_use = UART` запускает `app_uartcomm`
(`applications/app_uartcomm.c`), который читает байты с UART-разъёма и
отдаёт их в `commands_process_packet()`. Это **транспорт, а не источник
команд**: сам он ничего мотору не задаёт. Команда появится, только если
кто-то физически подключится к UART-разъёму ESC и пришлёт её.

К UART-разъёму ESC не подключено ничего — FloatCore говорит по CAN. Значит
разница между `UART` и `No App` сейчас теоретическая.

Дополнительно проверено: `app_adc_conf.ctrl_type = 0` и
`app_ppm_conf.ctrl_type = 0` — оба «выключено». Даже при смене `app_to_use`
на ADC или PPM локального управления не возникло бы без отдельной настройки.

Что важно: **на CAN-управление `app_to_use` не влияет вовсе.** Обработчики
`CAN_PACKET_SET_*` живут в `comm_can.c` и работают независимо от приложения.
Так же и USB: `comm_usb` не зависит от приложения, поэтому VESC Tool будет
работать при любом значении.

Рекомендация: **не менять на этом этапе.** Проверить непосредственно перед
первым подключением мотора, что там по-прежнему `UART` или `No App`, а не
ADC/PPM/балансировочное приложение — последнее означало бы второй
балансировочный контроллер на одной доске.

### Точные байты изменений в конфигурации ESC

```
si_battery_cells   mcconf,  смещение 457 (в ответе COMM 458), 1 байт
                   03  ->  0a

timeout_msec       appconf, смещение 5 (в ответе COMM 6), 4 байта
                   00 00 03 e8  ->  00 00 00 32
```

**Путь записи:** VESC Tool по USB. У FloatCore возможности записи нет и не
появится — `COMM_SET_MCCONF` и `COMM_SET_APPCONF` не входят в белый список и
не могут быть собраны.

**Постоянство:** обе команды сохраняют конфигурацию во flash и применяют её
немедленно (`commands.c`, `conf_general_store_mc_configuration` +
`mc_interface_set_configuration`). Перезагрузка не требуется.

**Важно про механизм:** записывается **весь блок целиком**, а не одно поле.
VESC Tool отправит те 484 (или 279) байт, что у него в памяти. Отсюда
обязательный порядок: прочитать конфигурацию в VESC Tool непосредственно
перед правкой → изменить одно поле → записать → прочитать обратно **через CAN
средствами FloatCore** → сверить с эталоном побайтово. Отличаться должны
ровно те байты, что перечислены выше.

Дополнительно: `COMM_SET_MCCONF` прогоняет конфигурацию через
`commands_apply_mcconf_hw_limits()` и на двухмоторном железе принудительно
выставляет `motor_type = MOTOR_TYPE_FOC`. Первое может подрезать значения под
пределы платы, второе безвредно (там и так FOC) — но обнаружить это можно
только сверкой после записи.

Порядок применения, если решение будет положительным: сначала изменения
FloatCore (наша сторона, откат мгновенный), потом пределы тока, потом
`timeout_msec`, и только в самом конце — косметические
`si_wheel_diameter`/`si_gear_ratio`. Каждое изменение — отдельно, с
перечитыванием и сверкой после.

## 8. Шаг 6 — проверка направления

После детекции, до любого балансирования:

1. Подать **малый положительный ток** (в пределах 5 А) через VESC Tool.
2. Убедиться, что колесо крутится в сторону, соответствующую движению
   **вперёд** для той ориентации доски, которая записана в
   `imu_orientation_mapping.md` (нос — сторона контейнера с электроникой).
3. Если направление обратное — исправлять **инверсией в конфигурации ESC**,
   а не знаком в коде FloatCore. Знак в коде спрятан от глаз и обязательно
   будет забыт; настройка ESC видна в интерфейсе.

Проверка знака запрошенного тока уже сделана на v0.6D для наклона доски,
но она проверяла **знак запроса**, а не физическое направление вращения.
Это разные утверждения, и второе без мотора недоказуемо.

## 9. Шаг 7 — вторая половина

Повторить шаги 2–6 для ID 100 отдельно. Сверить полученные параметры между
половинами: значительное расхождение R, L или flux при одинаковых моторах
означает, что что-то не так с одним из них или с проводкой.

## 10. Откат

На любом шаге:

1. Снять питание.
2. Отключить мотор физически.
3. Восстановить mcconf и appconf из копии шага 0.
4. Перечитать через CAN и сверить с сохранёнными блобами побайтово.

Отдельно: если детекция не сошлась или дала неправдоподобные значения —
**не повторять её вслепую.** Неправдоподобный результат детекции чаще
означает проблему с проводкой или с самим мотором, чем случайность.

## 11. Блокеры, которые обязаны быть закрыты до шага 0

1. Финальная квалификация I²C на реальном жгуте
2. Изменения конфигурации из §7 приняты или явно отклонены
3. Пределы тока для прокрута выставлены
4. `timeout_msec` приведён к политике (`vesc_watchdog_policy.md`)
5. Напряжение питания выше `l_battery_cut_start`
6. Механика: колесо вывешено, доска закреплена
7. Резервная копия конфигурации сделана и проверена чтением

# Что получилось (v0.8A, выполнено)

План выше написан до подключения мотора. Этот раздел — что произошло на самом
деле. Расхождения с планом отмечены явно.

## Соответствие разъёма — измерением, а не осмотром

План предполагал визуальную трассировку от USB к фазным выводам. Нашёлся
способ лучше, не требующий ни осмотра, ни моторных команд: **вращение колеса
от руки**.

VESC отслеживает угол и накапливает тахометр постоянно, пока плата включена,
даже не подавая тока. Значит вращение видно в телеметрии, и её можно читать
через CAN.

```
проворот колеса рукой:
  id=118   Δtach +8, Δ|tach| +88     <- мотор здесь
  id=100   Δtach  0, Δ|tach|   0
```

Разница между знаковым и абсолютным приростом сразу показала, что первый
проворот был в обе стороны, и потребовала повтора. Второй заход в одну сторону
дал `Δtach = Δ|tach| = 899` — совпадение доказывает, что счёт чистый.

**ID 118 — половина с тем USB-разъёмом, которым пользовались всё время**
(UUID `32002b00…`, пометка `local` в списке CAN-Devices).

## Число полюсов — то же измерение дало и его

Побочный результат, закрывший блокер, который план считал требующим вращения
под питанием.

```
899 шагов / 10 оборотов = 89.9 на оборот
тахометр считает 6 шагов на электрический оборот (mcpwm_foc.c:3765)
полюса = 899 / (3 × 10) = 29.97  ->  30
```

**Записанные 14 неверны.** Ближайший другой кандидат требовал бы 840 шагов.
Разбор — `motor_parameter_model.md` §5.

## Детекция — расхождение с планом

План говорил «штатная детекция FOC». На месте выяснилось, что `RL` и `λ` —
**отдельные кнопки**, и разделение оказалось не усложнением, а штатной
возможностью:

```
шаг A   RL   впрыск тока на стоящем моторе, вращения нет
шаг B   λ    раскрутка в открытом контуре, вращение есть
```

Мастер настройки (`Welcome & Wizards → Setup Motors FOC`) **не использовался
намеренно**: он переписывает пределы тока, конфигурацию батареи и ограничения
скорости, то есть снёс бы все пять только что записанных изменений.

### Шаг A прошёл сразу

```
             измерено     было        расхождение
R            318.76 mΩ    319.6 mΩ    −0.26 %
L            873.74 µH    730.42 µH   +19.6 %
Lq−Ld        333.37 µH    215.22 µH   +54.9 %
```

Сопротивление совпало — значит записанное мерили на этом моторе.
Индуктивность разошлась из-за положения ротора: `Lq−Ld` составляет 38 % от
`L`, и измеренное значение зависит от того, где стоит ротор.

### Шаг B провалился с первой попытки, и это важнее самого результата

Колесо чуть провернулось, встало и завибрировало. Процедура вернула
**положительное** `λ = 0.605 мВб` и пометила поле зелёным — то есть выглядела
успешной.

Значение нефизично: при таком λ напряжение 41 В соответствовало бы 43 000
об/мин. Разбор алгоритма (`conf_general.c:967`) показал, почему отказ не был
замечен: цикл разгона выходит по достижению заданной скважности, а скважность
растёт от самой частоты даже при стоящем роторе. Отказные ветки помечают
результат отрицательными значениями, и ни одна не сработала.

**Урок: зелёное поле в VESC Tool означает «процедура вернулась», а не
«результат физичен».** Проверка на правдоподобие обязательна.

Причина отказа — ток детекции 1.67 А, который VESC Tool вычислил как
`l_current_max / 3` из нашего временного предела 5 А. Со второй попытки при
`I = 4 А` и `α = 500` вместо 2000 ERPM/s (требуемый момент пропорционален
темпу разгона) колесо раскрутилось плавно и держало скорость. **Предел 5 А
при этом не поднимали.**

```
λ = 19.600 мВб      было 100.000     в 5.1 раза меньше
Observer Gain 2.60  было 0.10        следствие λ, отношение квадратов
```

Проверка правдоподобия: 19.6 мВб дают максимум ~770 об/мин ≈ 40 км/ч,
записанные 100 мВб дали бы 151 об/мин ≈ 8 км/ч — для моноколеса невозможно.


Проверено десятью повторами в одну сторону и одним в обратную: при −0.05
колесо дёргается к хвосту. Детерминировано и симметрично.
`m_invert_direction = 0` — инверсия не требуется, положительная команда уже
означает движение вперёд.

## Побочное подтверждение сторожевого таймера

Проверка направления дала неожиданный результат: при одиночном нажатии кнопки
колесо только дёргалось. Причина — наш собственный `timeout_msec = 50`:
команда живёт 50 мс, дальше ESC снимает тягу.

**Это первое физическое подтверждение, что политика таймаута работает.** На
v0.7D.1 проверялся только конфигурационный контракт, потому что мотор был
отключён.

Следствие для MOTOR_CAPABLE: команды придётся слать непрерывно с частотой
контура. Спроектированные 500 Гц дают 2 мс между командами — запас
двадцатипятикратный.

## Напряжение — отступление от плана, принятое осознанно

План требовал окна 37–40 В. Фактически было **40.8 В** (измерено
мультиметром). Владелец разрешил детекцию как исключение после разбора:
детекция рекуперации не создаёт — R и L меряются на стоящем моторе, λ
раскруткой и **свободным выбегом** без тока. Тормозное и проверку под
нагрузкой отложили.

Разрядить 10S-сборку без мотора было нечем, а детекция сама опускает
напряжение незначительно.

## Что осталось неподтверждённым

* Половина **100**: мотор не подключён, её `si_motor_poles = 14` и
  `flux = 0.1` по-прежнему не подтверждены. Предполагать, что там такой же
  мотор, мы не стали.
* **Диаметр колеса 0.083 м и передаточное 3.0** — не измерены, заведомо от
  другого аппарата.
* **Термистор мотора** — `temp_motor` около −88 °C, защита по перегреву
  мотора неработоспособна.
* Пределы **5 / −3 / 5 / −1 А** — временные, только для прокрута.
