# Архитектура прошивки ESP32 (проект, этап 0)

Документ описывает целевое устройство системы, вытекающее из аудита
([refloat_vesc_api_dependencies.md](refloat_vesc_api_dependencies.md)) и выбранной
Strategy B ([porting_strategy.md](porting_strategy.md)). Код на этом этапе не пишется.

## 2. Задачи FreeRTOS и приоритеты

| Задача | Ядро | Приоритет | Период | Содержание |
|---|---|---|---|---|
| `imu_task` | 1 | 24 (максимум прикладного) | по DRDY, 500 Гц (MVP) | чтение ICM-20948 → деротация → AHRS → `imu_ref_callback()` → отправка CAN |
| `refloat_main` | 1 | 22 | 500 Гц | `refloat_thd()` из Refloat |
| `can_rx_task` | 1 | 20 | по событию | разбор STATUS 1–6 от обоих VESC в двойной буфер |
| `refloat_aux` | 0 | 10 | ~30 Гц | `aux_thd()`: LED, одометр |
| `comms_task` | 0 | 5 | по событию | BLE/UART, VESC Tool, логирование |
| `supervisor` | 1 | 25 | 100 Гц | независимый watchdog: проверяет живость IMU, CAN, контура |

**Оба потока Refloat пиннятся на ядро 1** — обязательное требование: Refloat не использует
синхронизацию, и на разных ядрах чтение/запись общей структуры `Data` даст гонки.
Wi-Fi/BLE полностью на ядре 0.

Ключевые решения:

* **IMU-задача, не ISR.** На ESP32 FPU нельзя использовать в обработчике прерывания
  (ленивое сохранение контекста FPU). ISR только делает `vTaskNotifyGiveFromISR`.
* **Отправка CAN — из той же задачи, синхронно.** `mc_set_current()` внутри
  `imu_ref_callback` кладёт кадр в аппаратную очередь TWAI без блокировки. Никакой очереди
  сообщений между Refloat и CAN, чтобы не добавлять задержку в контур.
* **Приоритет supervisor выше контура** — он должен успеть отработать даже при перегрузке.

## 3. Модель времени

| Refloat API | ESP32 |
|---|---|
| `system_time_ticks()` (100 мкс тик) | `esp_timer_get_time() / 100` |
| `system_time()` | `esp_timer_get_time() * 1e-6f` |
| `timer_time_now()` / `timer_seconds_elapsed_since()` | `esp_timer_get_time()` |
| `sleep_us(n)` | `vTaskDelayUntil` при периоде ≥1 тика, иначе таймер высокого разрешения |

`configTICK_RATE_HZ` поднять до 1000. Для 500 Гц главного цикла достаточно `vTaskDelayUntil`
с периодом 2 тика; ритм IMU задаётся аппаратно (DRDY), а не таймером.

## 4. IMU

```
ICM-20948 ──SPI 7 МГц──► DRDY GPIO ──ISR──► notify ──► imu_task
                                                        │
        ┌───────────────────────────────────────────────┘
        ├─ чтение 12 байт (accel+gyro) одной транзакцией
        ├─ применение офсетов и матрицы ориентации (аналог CFG_PARAM_IMU_rot_*)
        ├─ обновление AHRS «прошивки» (Mahony) → roll/pitch/yaw/quaternions
        │     ← отдаётся Refloat через imu_get_roll/pitch/yaw/quaternions
        └─ imu_ref_callback(acc, gyro, NULL, dt)
              ← dt считается по esp_timer между семплами, не по номиналу
```

Требования ТЗ §7 и их выполнение:

* стабильная частота → аппаратный DRDY, не программный таймер;
* timestamp → `esp_timer_get_time()` в момент входа ISR, передаётся в задачу;
* без аллокаций в RT-пути → все буферы статические;
* трансформация ориентации и офсеты → в compat-слое, как в прошивке VESC;
* конфигурируемая частота → регистры ODR ICM-20948; отдаётся Refloat через
  `get_cfg_int(CFG_PARAM_IMU_sample_rate)`;
* детекция зависших/потерянных семплов → supervisor: отсутствие DRDY >5 мс, а также
  побитовая идентичность двух подряд семплов N раз → fault.

**Двойной AHRS.** Refloat использует одновременно свой Mahony (`balance_filter`) и AHRS
прошивки (`imu_get_pitch`). Значит, compat-слой обязан иметь собственный AHRS — это не
дублирование по ошибке, это воспроизведение поведения VESC.

## 5. Motor abstraction и агрегация

```c
// compat/motor
typedef struct {
    uint8_t  can_id;
    bool     invert;
    float    scale;          // 0.0…1.0
    float    current_limit;  // per-motor, A
} VescNodeConfig;

typedef struct {
    float erpm, duty, motor_current, batt_current, v_in, temp_fet, temp_motor;
    mc_fault_code fault;
    int64_t tacho;
    uint32_t last_rx_us;     // возраст телеметрии
    bool   online;
} VescNodeTelemetry;
```

Правила агрегации — обоснование в аудите §3:

| Величина | Правило |
|---|---|
| ERPM | среднее (A+B)/2; `\|A−B\| > порог` → fault |
| Duty | `max(\|A\|,\|B\|)` |
| Motor current / directional | **среднее** (не сумма — см. аудит §3.1) |
| Battery current | среднее (лимиты берутся per-ESC) |
| Input voltage | среднее; расхождение >1 В → флаг |
| Температуры | `max(A,B)` |
| Fault | первый ненулевой из A, B; оба сохраняются для UI |
| Distance / speed | среднее |
| Amp/watt hours, ток батареи для дисплея | сумма |

### Supervisor (уровень безопасности)

Сидит **между** `mc_set_*` Refloat и CAN. Refloat о нём не знает.

Условия немедленного перехода в fault state (ТЗ §11):

| Условие | Проверка | Действие |
|---|---|---|
| нет семпла IMU | >5 мс без DRDY | zero current, затем release |
| зависший IMU | N идентичных семплов | fault |
| NaN/Inf в запрошенном токе | `isfinite()` | fault, ток не отправляется |
| ток вне диапазона | `\|I\| > current_limit` | клип + fault-счётчик |
| VESC A или B offline | телеметрия старше 100 мс | fault |
| fault на любом ESC | `mc_get_fault() != NONE` | пробрасывается в Refloat + логируется |
| расхождение ERPM A/B | > порога | fault |
| over/under voltage, over duty | пороги из конфигурации | fault |
| зависание контура | supervisor не видел итерации >10 мс | fault + TWDT |

Safe state = **прекратить отправку команд тока**. Через `timeout_msec` (сконфигурировать на
обоих FSESC в ~100 мс) VESC самостоятельно снимает тягу. Это выполняет требование ТЗ §11 о
собственном watchdog CAN-команды и работает даже при полном зависании ESP32.

Дополнительно: ESP32 Task Watchdog на `imu_task` и `refloat_main`.

## 6. CAN

* TWAI, **1 Мбит/с** (обоснование — расчёт нагрузки ниже), 29-битные ID протокола VESC.
* Исходящие: `CAN_PACKET_SET_CURRENT` (0x01), `SET_CURRENT_BRAKE` (0x02), `SET_DUTY` (0x00) —
  по кадру на каждый ESC на каждую итерацию контура.
* Входящие: `CAN_PACKET_STATUS` 1–6 от обоих ESC.
* Конфигурация ESC (лимиты тока, flux linkage, полюса) читается редко через
  `COMM_GET_MCCONF` поверх `PROCESS_SHORT_BUFFER`, либо в v1 задаётся в конфиге ESP32 вручную.

**Расчёт нагрузки шины** — уточнён в [can_bandwidth.md](can_bandwidth.md) с учётом точной
длины кадра, битстаффинга, ACK/IFS и приоритетов арбитража. Прикидка ниже сохранена как
исторический ориентир; актуальные числа и рекомендация — в отдельном документе.

(29-битный кадр, 8 байт данных, ≈150 бит со стаффингом):

| Трафик | Кадров/с | При 500 кбит/с | При 1 Мбит/с |
|---|---|---|---|
| Команды тока, контур 500 Гц × 2 ESC | 1000 | 30 % | 15 % |
| Команды тока, контур 832 Гц × 2 ESC | 1664 | 50 % | 25 % |
| STATUS 1–6 × 2 ESC @ 50 Гц | ~600 | 18 % | 9 % |
| **Итого при 832 Гц** | ~2264 | **68 %** | **34 %** |

При 500 кбит/с и частоте контура 832 Гц шина загружена почти на 70 % — это зона роста
джиттера арбитража. **Решение: 1 Мбит/с, а частота контура в MVP — 500 Гц.**
Снизить частоту публикации STATUS-сообщений на обоих ESC до необходимого минимума.

## 7. Конфигурация и хранение

* Конфигурация Refloat: `store_eeprom_var`/`read_eeprom_var` → NVS ESP32,
  namespace `refloat`, ключи `cfg_%02u`, 80 слов по 4 байта. Запись только по
  `COMMAND_CFG_SAVE`.
* Конфигурация железа ESP32 (пины, CAN ID, инверсия, scale, лимиты) — отдельный namespace,
  недоступный Refloat.
* Одометр — отдельный ключ, запись при `store_backup_data()`.

## 8. Транспорт UI (после MVP)

Для работы существующего Refloat UI достаточно двустороннего канала байтов:
`set_app_data_handler` ← вход, `send_app_data` → выход. Вся логика ~25 команд уже внутри
Refloat.

Для подключения **VESC Tool** к ESP32 дополнительно нужна эмуляция VESC packet protocol:
`COMM_FW_VERSION`, `COMM_GET_VALUES`, `COMM_CUSTOM_APP_DATA`, `COMM_GET_CUSTOM_CONFIG`,
`COMM_GET_CUSTOM_CONFIG_XML`, `COMM_SET_CUSTOM_CONFIG` + механика обнаружения пакета.
В первую реализацию не входит (ТЗ §10).

## 9. Тестирование каждого слоя без человека на доске (ТЗ §17.12)

| Слой | Метод | Критерий |
|---|---|---|
| Агрегация телеметрии | host-тесты (собираются под x86, чистый C) | таблицы вход→выход §5 |
| Compat `vesc_c_if` | host-сборка Refloat + фейковая платформа, «симулятор доски» (модель мотора + IMU) | контур сходится, ток ограничен |
| Драйвер ICM-20948 | стенд: вращение по осям, сверка с эталоном | знаки и оси совпадают с VESC |
| Тайминг IMU | GPIO-toggle на каждый семпл + логический анализатор | джиттер периода < 5 % |
| Тайминг контура | `latency_tracker`/`frequency_tracker` уже внутри Refloat, отдаются в UI | частота стабильна |
| CAN-драйвер | один FSESC на столе, мотор без нагрузки/отключён; сверка запрошенного и фактического тока | ошибка < 5 % |
| Supervisor | инъекция отказов: отключить CAN, IMU, подать NaN, отключить один ESC | во всех случаях снятие тяги ≤100 мс |
| Watchdog VESC | остановить отправку команд | тяга исчезает через `timeout_msec` |
| Дуальный мотор | доска на подставке, колёса в воздухе, ограничение тока 5 А | оба колеса вращаются синхронно |
| Полный контур | «flywheel»-режим Refloat (уже есть в пакете) | балансирует одно колесо на весу |

Порядок ввода: host-тесты → стенд IMU → стенд CAN с ограничением тока → колёса в воздухе →
только потом человек.
