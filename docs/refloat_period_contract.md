# Период главного потока Refloat: почему он был вдвое меньше номинала

Этап v0.9E §2-§6. Документ закрывает блокер, из-за которого v0.9D дал NO-GO.

---

## 1. Что наблюдалось

```
timing refloat_thd   mean 1000.0 мкс   min 201   (номинал 2000)
imu / main freq      515.9 / 1812.3 Гц
```

Главный поток Refloat шёл вдвое чаще, чем задумано. Следствия выстроились в
цепочку: он перестал оставлять время вспомогательному потоку с меньшим
приоритетом, тот не сбрасывал сторожевой таймер задач, TWDT раз в пять секунд
печатал блок с обратной трассировкой, печать блокировала всё на 34-40 мс, и
получался зазор IMU больше 40 мс — то есть отказ по политике.

Важно: **прибор не врал**. Политика v0.9C защёлкивала `LOST` правильно, зазор
был настоящим. Неверен был период.

## 2. Как Refloat просит поспать

```c
// refloat-upstream/src/main.c:770, 777
uint32_t sleep_ticks = d->main_loop_ticks;          // 20 тиков по 100 мкс
VESC_IF->sleep_us(sleep_ticks * 1000000 / SYSTEM_TICK_RATE_HZ);

// main.c:1058-1059, в конце каждой итерации
int32_t ticks = lrintf(timer_seconds_elapsed_since(loop_timer) * SYSTEM_TICK_RATE_HZ);
sleep_ticks = max(d->main_loop_ticks - ticks, 1);
```

Refloat **вычитает из номинала время своей итерации**. То есть он просит не
«поспать период», а «поспать остаток периода». Первый запрос — полный,
2000 мкс; все последующие — меньше, и величина плавает вместе с нагрузкой.

## 3. Что делала наша реализация

`fc_vesc_if.c` переводит это в `xTaskDelayUntil` с абсолютной отметкой (так
было сделано на v0.7D, и это правильно: компенсацию делает сам планировщик, а
делать её дважды значило бы ускорять цикл). Период брался из **первого**
запроса:

```c
if (t->period_ticks == 0) {
    uint32_t ticks = (us + 500u) / 1000u;
    t->period_ticks = ticks ? ticks : 1;
}
```

Расчёт был на то, что первый запрос — полный период. На бумаге верно. На
плате — нет: поток попадает в нашу таблицу не мгновенно, и к этому моменту
первая, самая медленная итерация может быть уже позади. Тогда защёлкивался
**скомпенсированный** запрос. При итерации около 1000 мкс это давало
`(1000+500)/1000 = 1` тик вместо двух.

Обратной дороги не было: дальше `us` игнорировался намеренно.

**Это мой просчёт на v0.7D.** Выводить постоянную величину из одной ранней
выборки — значит поймать стартовый переходный процесс и жить с ним до
перезагрузки.

## 4. Исправление

Период берётся из **максимума** запросов, а не из первого:

```c
uint32_t want = (us + 500u) / 1000u;
if (want > t->period_ticks) { t->period_ticks = want; }
```

Корректно по построению: Refloat из номинала только **вычитает**, никогда не
добавляет, поэтому ни один запрос не может превысить номинальный период.
Максимум сходится к номиналу и не зависит от того, на какой итерации поток
попал в таблицу.

Схема остаётся абсолютной: `xTaskDelayUntil` по сохранённой отметке, без
накопления ошибки, без догоняющих пачек, одна логическая итерация на период.

## 6. Про сторожевой таймер

Его **не маскировали**. ТЗ на этом настаивает, и по существу это верно: если
бы TWDT продолжал срабатывать после исправления периода, это означало бы
настоящий отказ планирования, а не докучливую диагностику. Он перестал
срабатывать сам, потому что исчезла причина — голодание вспомогательного
потока.

Печать TWDT действительно тяжёлая и идёт из контекста, где ей не место, но
трогать её не понадобилось, и трогать чужой аварийный путь без нужды не
стоит: он для того и существует, чтобы шуметь громко.

## 7. Чего это не решает

Приоритеты остались прежними (главный 12, вспомогательный 10), общих
блокировок между ними нет, инверсии приоритета не обнаружено. Голодание было
следствием одного лишнего пробуждения на период, а не структуры приоритетов —
поэтому поднимать приоритет вспомогательного потока не потребовалось, и по
ТЗ этого делать и не следовало.
