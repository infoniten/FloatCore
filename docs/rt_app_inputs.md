# RT App: декодированные входы (COMM_GET_DECODED_PPM / _ADC / _CHUK)

## 1. Зачем это понадобилось

При открытии страницы **RT App** VESC Tool начинает периодически опрашивать три
приложения ввода прошивки: PPM (радиоприёмник), ADC (педали газа/тормоза) и
Nunchuk. До версии 0.4.2 FloatCore считал команды 31/32/33 неизвестными и
молчал: страница оставалась пустой, а счётчик `unknown_commands` рос на каждом
цикле опроса.

FloatCore ни одного из этих приложений не имеет. Но ADC — это те же выводы,
с которых Refloat читает педали, поэтому один из трёх ответов может нести
настоящие данные, а не заглушку.

## 2. Формат ответов

Источник — `bldc/comm/commands.c`, приёмная сторона — `vesc_tool/commands.cpp`
(`Commands::processPacket`). Оба проверены в состоянии на 2026-08-26.

```c
// bldc/comm/commands.c
case COMM_GET_DECODED_PPM:
    send_buffer[ind++] = COMM_GET_DECODED_PPM;
    buffer_append_int32(send_buffer, (int32_t)(app_ppm_get_decoded_level() * 1000000.0), &ind);
    buffer_append_int32(send_buffer, (int32_t)(servodec_get_last_pulse_len(0) * 1000000.0), &ind);
```

```cpp
// vesc_tool/commands.cpp
case COMM_GET_DECODED_PPM: {
    mTimeoutDecPpm = 0;
    double dec_ppm = vb.vbPopFrontDouble32(1e6);
    double ppm_last_len = vb.vbPopFrontDouble32(1e6);
    emit decodedPpmReceived(dec_ppm, ppm_last_len);
} break;
```

Итого — все значения одного вида: `int32` big-endian со шкалой 1e6.

| Команда | ID | Payload | Длина | Поля по порядку |
|---|---|---|---|---|
| `COMM_GET_DECODED_PPM` | 31 | `[31][i32][i32]` | 9 | `decoded_level`, `last_pulse_len` (с) |
| `COMM_GET_DECODED_ADC` | 32 | `[32][i32][i32][i32][i32]` | 17 | `level`, `voltage` (В), `level2`, `voltage2` (В) |
| `COMM_GET_DECODED_CHUK` | 33 | `[33][i32]` | 5 | `decoded_y` (ось Y нунчака) |

Порядок полей ADC — `level, voltage, level2, voltage2`, а не «сначала оба
уровня, потом оба напряжения». Перепутать их местами легко, и VESC Tool такую
ошибку не заметит: он просто покажет напряжение как долю хода. Порядок
зафиксирован тестом.

**Усечение, а не округление.** Прошивка пишет `(int32_t)(value * 1000000.0)` —
дробная часть отбрасывается, вычисление идёт в `double`. Поэтому
`decoded_inputs.c` не пользуется `vb_append_float32()`, который округляет через
`lrintf`: для побайтного совпадения повторены и тип промежуточного вычисления,
и способ усечения. Единственное отличие от оригинала — явное ограничение
диапазона `int32`: в прошивке переполнение было бы неопределённым поведением.

## 3. Что именно отдаёт FloatCore

| Поле | Значение | Обоснование |
|---|---|---|
| PPM `level` | 0 | Приёмника нет. Ноль — это «газ отпущен», а не «газ в пол» |
| PPM `pulse_len` | 0 | Импульсов не приходит. Подставить «нейтральные» 1.5 мс значило бы нарисовать в UI несуществующий приёмник |
| ADC `voltage` | напряжение на выводе **ADC1** | То же, что читает `footpad_sensor.c` через `VESC_IF->io_read_analog(VESC_PIN_ADC1)` |
| ADC `voltage2` | напряжение на выводе **ADC2** | То же для `VESC_PIN_ADC2` |
| ADC `level` / `level2` | `voltage / 3.3`, ограничено 1.0 | Полная шкала АЦП VESC — 3.3 В. Отображение линейное и без настроек: приложения ADC с его `voltage_start`/`voltage_end` у FloatCore нет, а выдумывать кривую нельзя |
| CHUK `level` | 0 | Нунчака нет; 0 — нейтраль, эквивалент «не подключён» |

Каналы нумеруются **по выводам**, а не по педалям «левая/правая». Соответствие
вывода педали задаётся настройкой Refloat `hardware.swap_footpad_adcs` и
меняется вместе с ней, а страница RT App подписывает поля именно как
Voltage / Voltage 2.

Если провайдер не задан (`decoded_inputs_provider == NULL`), сервер отвечает
нейтральными нулями, а не молчит: страница заполняется, счётчик неизвестных
команд не растёт.

## 4. Безопасность

Путь строго односторонний — read-only, как и Virtual mcConfig:

```
mock/платформа (напряжения ADC)
        │  только чтение
        ▼
decoded_inputs_provider()  ──►  decoded_*_encode()  ──►  VESC Tool
```

Обработчик в `commands.c` не вызывает ни одной функции записи: ни конфигурации,
ни состояния Refloat, ни мотора. Обратного направления нет вообще — команды
31/32/33 не несут аргументов, а `COMM_SET_SERVO_POS` и прочие управляющие
команды в этот путь не входят.

Safety Supervisor эти значения не читает и читать не должен: педали он получает
от `footpad_sensor.c` напрямую, а не через протокольный слой.

Проверено:

* `tests/protocol/test_protocol.c` — после 60 опросов `motor_commands_blocked == 0`,
  `unknown_commands == 0`, запись конфигурации не вызывалась;
* `tests/host_integration/vesc_tool_sim.py` — на живом сокете 60 опросов подряд,
  после них телеметрия мотора (ток, duty, rpm) не изменилась;
* `tests/host_integration/run.sh` — в итоговых счётчиках сессии
  `неизвестных команд 0`.

## 5. Как посмотреть вручную

```bash
build/floatcore_host --trace --adc 1.65,1.20
```

В VESC Tool: подключиться по TCP, открыть **RT App**. На вкладке ADC должны
появиться `Voltage ≈ 1.65 В` (level ≈ 0.50) и `Voltage 2 ≈ 1.20 В`
(level ≈ 0.36); PPM и Nunchuk останутся на нуле.

Флаг `--adc` задаёт напряжения на выводах ADC1/ADC2 для mock-платформы: их
видит и Refloat, и страница RT App — источник один. Значения по умолчанию
`0,0` означают «педали не нажаты».

Осторожно: порог срабатывания педали по умолчанию — 2.0 В
(`fault_adc1`/`fault_adc2`). Значения выше него Refloat воспримет как нажатую
педаль со всеми вытекающими последствиями для состояния доски. В фикстуре
интеграционного прогона выбраны 1.65 и 1.20 В — ниже порога.

## 6. Чего здесь нет

`COMM_SET_SERVO_POS` (12), `COMM_GET_IMU_DATA` (65) и прочие страницы RT
остаются нереализованными — см. [unsupported_commands.md](unsupported_commands.md).
Реализовано ровно то, что RT App действительно шлёт периодически и что без
ответа портит счётчики.
