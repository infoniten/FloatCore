# Привязка осей ICM-20948 к системе координат доски

Этап **v0.6B-0**. Задача одна: экспериментально определить соответствие между
осями датчика и осями доски. Ни одна строка прошивки на этом этапе не
изменена, реальный IMU к Refloat не подключён.

> **Статус на момент checkpoint v0.6C.** Mapping ниже — **measured**, и он не
> пересматривался: ни одной перестановки и ни одного знака после этих
> измерений не менялось. Но получен он **до переборки железа** этапа v0.6C, в
> ходе которой менялись плата ESP32, жгут и (временно) модуль IMU, а сам
> модуль снимался и перепаивался. Соответствие осей — свойство того, как
> кристалл ориентирован в корпусе доски, поэтому смена экземпляра модуля или
> его посадки может его изменить. Перед подключением реального IMU к Refloat
> mapping обязан быть **подтверждён повторно** на финальном монтаже
> (`esp32_safety.md` §8, пункт A.2). Числовые смещения покоя из §2 и §9.2 к
> текущей сборке уже не относятся: положение датчика с тех пор менялось.

Все числа получены на собранном корпусе, в котором ICM-20948 стоит на своём
окончательном месте. Датчик не снимался и не перемещался между измерениями.

Инструмент измерения — `tools/imu_orientation.py`: он периодически отправляет
существующую read-only команду консоли `imu` и разбирает строки «последний
семпл». Команды `imuraw` в прошивке нет; `imu` — её эквивалент
(`platform/esp32/main/fc_console.c:90`, категория SAFE_READONLY). Частота
опроса самого датчика при этом не менялась: задача `fc_imu_hw` как читала
500 Гц, так и читает, консоль показывает `last_good`. Частота вывода — 8 Гц.

## 3. Определения

* **Нос** — сторона контейнера с электроникой. **Корма** — сторона

## 6. Проверка согласованности

### 6.1 Три оси — три независимых канала

Тангаж использует X (accel) / Y (gyro), крен — Y (accel) / X (gyro), рыскание —
только Z (gyro). Ни одна ось не задействована в двух каналах. Перекрёстных
откликов не наблюдалось: при тангаже acc_y держался в пределах sd 0.009, при
крене gyro_y и gyro_z оставались на уровне шума покоя.

### 6.2 Пара accel/gyro внутри каждого канала

Для правой тройки координат и вращения тела с угловой скоростью **ω** вектор
«вверх», выраженный в осях датчика, эволюционирует как
`u_b(t) = R(t)ᵀ · u_b(0)`. Отсюда для малых углов:

* `ω_y > 0` ⇒ `acc_x = −sin θ` (отрицательный);
* `ω_x > 0` ⇒ `acc_y = +sin φ` (положительный).

Измерено: A/B дают gyro_y **+** вместе с acc_x **−**; C/D дают gyro_x **+**
вместе с acc_y **+**. **Оба канала совпадают с предсказанием**, то есть
акселерометр и гироскоп внутри датчика согласованы и правая тройка
подтверждается измерением, а не принимается на веру.

### 6.3 Хиральность тройки доски

`forward × right = (−X) × (+Y) = −Z = down`. Для правой системы координат
`forward × right` действительно даёт `down` (как `north × east = down`).
Тройка `(forward, right, down) = (−X, +Y, −Z)` имеет определитель +1 —
правая. Перестановки не подобраны, а вытекают из измерений.

### 6.4 Рысканье согласуется с осью «вверх»

`board_up = +Z` получено из акселерометра в baseline. По правилу правой руки
поворот против часовой стрелки при взгляде сверху — положительный вокруг
«вверх». Измерено: CCW → gyro_z **+**. Предсказание и измерение совпадают;
знак не подбирался.

**Противоречий нет.** Все шесть измерений укладываются в одну правую тройку.

## 7. Соглашение Refloat

Все ссылки — на `refloat-upstream/`, версия из репозитория. Единицы и общий
контракт уже разобраны в `docs/imu_contract.md`; здесь — только знаки.

### 7.1 Откуда Refloat берёт углы

`src/imu.c:36-41`:

```c
float roll_rad = VESC_IF->imu_get_roll();  // in Radians
imu->pitch = rad2deg(VESC_IF->imu_get_pitch());
imu->roll = rad2deg(roll_rad);
imu->yaw = rad2deg(VESC_IF->imu_get_yaw());
imu->balance_pitch = rad2deg(balance_filter_get_pitch(bf));
```

То есть `pitch`, `roll`, `yaw` приходят из **AHRS платформы**, а
`balance_pitch` Refloat считает сам, своим фильтром Mahony
(`src/balance_filter.c`), из сырых массивов `gyro` и `acc`, переданных в
`imu_ref_callback` (`src/main.c:734,742`). Это два независимых источника, и
compat-слой обязан сделать их согласованными по знаку.

### 7.2 Что считается положительным Pitch

`src/pid.c:59` — единственное место, где знак тангажа влияет на ток:

```c
float error = setpoint - imu->balance_pitch;
```

Знак `setpoint` определяется, в частности, duty-pushback, `src/main.c:507-512`:

```c
} else if (d->motor.duty_cycle.value > d->float_conf.tiltback_duty) {
    if (d->motor.erpm > 0) {
        d->setpoint_target = d->float_conf.tiltback_duty_angle;
    } else {
        d->setpoint_target = -d->float_conf.tiltback_duty_angle;
    }
```

Pushback по определению **поднимает нос**, чтобы заставить райдера сбросить
скорость. При движении вперёд (`erpm > 0`) он задаёт **положительный**
setpoint, а контур приводит `balance_pitch` к setpoint. Следовательно:

> **Положительный Pitch в Refloat = нос вверх.**

Независимая перепроверка через PID: если райдер наклоняется вперёд и нос
опускается, `balance_pitch` уходит в минус, `error = 0 − (−) > 0`, ток
положительный, доска ускоряется вперёд. Это ровно та физика, которая нужна
самобалансирующейся доске.

### 7.3 Какие направления gyro ожидаются

`src/imu.c:43-51`:

```c
float gyro[3];
VESC_IF->imu_get_gyro(gyro);
...
imu->pitch_rate = cos_roll * cos_roll * gyro[1] + sin_roll * cos_roll * gyro[2];
```

`gyro[1]` — скорость тангажа, `gyro[2]` — скорость рыскания (входит с
поправкой на крен), значит `gyro[0]` — скорость крена. Порядок массива:
**`[0] = roll rate (X), [1] = pitch rate (Y), [2] = yaw rate (Z)`**.

Знак `gyro[1]` выводится из самого фильтра. `src/balance_filter.c:115-124`
интегрирует `q̇ = ½ q ⊗ ω`; при старте из `q = (1,0,0,0)` и `ω = (0, g_y, 0)`
получается `q2 ≈ ½ g_y dt`, а `src/balance_filter.c:145-155`:

```c
float sin = -2.0 * (data->q1 * data->q3 - data->q0 * data->q2);
...
return asinf(sin);
```

даёт `pitch ≈ g_y · dt`. То есть:

> **Положительный `gyro[1]` ⇒ растущий Pitch ⇒ нос поднимается.**

Это же подтверждается демпфированием в `src/pid.c:69`:
`pid->rate_p = -imu->pitch_rate * config->kp2` — при поднимающемся носе ток
отрицательный, то есть контур опускает нос обратно. Знак верен только при
`gyro[1] > 0 = нос вверх`.

### 7.4 Что считается положительным Roll

`src/balance_filter.c:136-142`:

```c
return -atan2f(q0 * q1 + q2 * q3, 0.5 - (q1 * q1 + q2 * q2));
```

Ведущий минус — сознательная модификация Refloat («modified for
self-balancing skateboard», `src/balance_filter.c:28`). При `ω = (g_x, 0, 0)`
получается `roll ≈ −g_x · dt`, то есть:

> **Положительный `gyro[0]` ⇒ убывающий Roll.**

**Важно:** знак Roll в Refloat **не влияет ни на одно решение контура**. Во
всей логике он используется только по модулю: `fabsf(imu.roll) > fault_roll`
(`src/main.c:422`), `startup_roll_tolerance` (`src/main.c:1016`), детектор
darkride около ±180° (`src/main.c:433, 1024`), `fabsf(imu.roll) < 40`
(`src/main.c:362`). Знак уходит только в телеметрию
(`src/main.c:1289, 1343, 2133`). Поворотами управляет turn tilt, и он берёт
**рысканье**, а не крен, причём по модулю: `abs_yaw_change`
(`src/turn_tilt.c:98,108`), а направление добавляет из `erpm_sign`
(`src/turn_tilt.c:135`).

То же относится к Yaw: `src/turn_tilt.c:63,73` работают с приращением
`imu->yaw` и его модулем, знак используется лишь для сброса агрегата при
смене направления (`src/turn_tilt.c:76`).

> **Итог: единственный знак, критичный для безопасности и управления, —
> знак Pitch. Знаки Roll и Yaw влияют только на телеметрию и на
> согласованность двух источников углов между собой.**

### 7.5 Ожидание по акселерометру

`src/balance_filter.c:99-101`: при единичном кватернионе оценка гравитации
равна `(0, 0, +0.5)`. Значит в покое платформа обязана отдавать
`acc = (0, 0, +1)` g — иначе Mahony начнёт «доворачивать» доску. Подробнее —
`docs/imu_contract.md` §3.

## 8. Transform: ICM raw → Board → Refloat

```
                     ICM raw (оси датчика, ±4 g / ±500 °/с)
                     acc  = (ax, ay, az)  g
                     gyro = (gx, gy, gz)  °/с
                                │
                                ▼
                     ┌──────────────────────┐
                     │   Board transform    │   §5 этого документа
                     └──────────────────────┘
                     forward = −X    right = +Y    up = +Z
                     pitch_rate = +gy   (нос вверх +)
                     roll_rate  = +gx   (правый край вверх +)
                     yaw_rate   = +gz   (CCW сверху +)
                                │
                                ▼
                     ┌──────────────────────┐
                     │  Refloat transform   │   §7 этого документа
                     └──────────────────────┘
                     acc[]  = { ax, ay, az }            g
                     gyro[] = { gx, gy, gz } · π/180    рад/с
                                │
                                ▼
                     imu_ref_callback(acc, gyro, NULL, dt)
```

**Refloat transform оказался тождественным** — ни перестановок, ни инверсий.
Это не совпадение и не удобная подгонка, а следствие двух независимо
установленных фактов:

| Требование Refloat | Источник | Что даёт датчик |
|---|---|---|
| в покое `acc = (0,0,+1)` | `balance_filter.c:99-101` | baseline: `(−0.060, −0.029, +0.996)` |
| `gyro[1] > 0` ⇒ нос вверх | `balance_filter.c:115-155` + `pid.c:69` | измерение A: нос вверх ⇒ `gyro_y` **+** |
| `gyro[1]` согласован с `acc_x` | кинематика §6.2 | измерение A: `gyro_y` **+** при `acc_x` **−** |

Если бы датчик был повёрнут иначе, здесь стояла бы матрица перестановки.
Здесь она единичная — и это проверяемое утверждение, а не умолчание.

### Следствия, которые получаются «бесплатно»

* **Pitch** — правильный: нос вверх даёт положительный `balance_pitch`.
* **Roll** — правый край вверх даёт **отрицательный** Refloat Roll (§7.4).
  На управление не влияет (только модуль), на телеметрию влияет. Это
  соответствует авиационному соглашению «крен вправо (правый борт вниз) —
  положительный».
* **Yaw** — поворот по часовой стрелке при взгляде сверху даёт **растущий**
  Refloat Yaw.
* Ось `+X` датчика смотрит в корму. Внутренняя «вперёд» у AHRS оказывается
  противоположна носу доски, но на знак тангажа это не влияет и потому
  безвредно.

### Что обязан обеспечить compat-слой на v0.6C

`imu_get_pitch/roll/yaw()` (AHRS платформы) и массивы, уходящие в
`imu_ref_callback`, — **два независимых источника** (§7.1). Refloat сравнивает
их косвенно: `imu.pitch` идёт в отказы и quickstop (`src/main.c:386,1040`), а
`imu.balance_pitch` — в PID. Чтобы они не разъехались по знаку, AHRS
compat-слоя следует строить **по тем же формулам**, что
`balance_filter_get_pitch/roll/yaw()` (`src/balance_filter.c:136-164`). Тогда
согласованность гарантируется конструкцией, а не проверкой.

## 9. Открытые вопросы и неоднозначности

### 9.1 Перемежающийся отказ I²C, зависящий от положения корпуса

Главная находка этапа, не относящаяся к ориентации.

| Окно | Положение доски | ok | failed | доля отказов |
|---|---|---|---|---|
| baseline, 12 с | горизонт, покой | 5923 | 0 | **0 %** |
| статика, 45 с | горизонт, покой | 15035 | 0 | **0 %** |
| A, движение | тангаж | 4577 | 2415 | 34.5 % |
| B, движение | тангаж | 4245 | 2666 | 38.6 % |
| B, статика | нос вниз 15°, покой | 2419 | 0 | **0 %** |
| C, движение | крен | 3684 | 3236 | 46.8 % |
| **C, статика** | **правый край вверх 29°, покой** | 1309 | 1116 | **46.0 %** |
| **D, статика** | **левый край вверх 37°, покой** | 1399 | 1001 | **41.7 %** |
| E, движение | рысканье, горизонт | 6937 | 0 | **0 %** |
| F, движение | рысканье, горизонт | 6924 | 0 | **0 %** |

Ключевое наблюдение: в окне C доска стояла **неподвижно** (`sd(acc) = 0.004 g`),
а отказы держались на 46 %. При рысканье — движении не менее энергичном, но в
горизонтальной плоскости — отказов **ноль**. Значит дело не в тряске:
**частота отказов определяется положением/нагружением корпуса**, прежде всего
креном.

Это картина непропая или подламывающегося проводника на SDA/SCL или на питании
IMU: в одном положении контакт есть, в другом — на грани. Проблема появилась
после того, как IMU снимали для пайки и собирали корпус; в измерениях v0.6A
(`docs/icm20948_driver.md` §5) за 62 с было `failed = 0`.

Последствия:

* Сами данные **не искажаются**: сбойная транзакция помечается `valid = false`,
  `fc_imu_health` её отбрасывает, консоль показывает `last_good`, и \|a\|
  во всех окнах оставался 0.99…1.00. Поэтому измерения этого этапа валидны.
* `fc_imu_health` переходит в `READ_ERROR`, Supervisor уходит в
  `FAULT / IMU_UNHEALTHY` с защёлкиванием. Именно это и произошло: предусловие
  ТЗ §1 «Supervisor не в Fault» выполнялось на старте (boot #85, `DISARMED`,
  `faults none`), но нарушалось после каждого наклона.
* Для реальной езды это **блокер**: 40 % потерь семплов в крене — ровно в том
  режиме, где доска и работает.

Починка выходит за рамки этапа (ТЗ §8 запрещает менять настройки IMU;
пайка — вопрос железа). Задача для v0.6C: найти и устранить контакт, затем
повторить прогон C/D и получить `failed = 0` в наклоне.

Дополнительно, в первой же сессии (boot #84) наблюдался тот же отказ
(`ok=27292 errors=4156`, `stale=16`) без всяких манипуляций с доской, а после
перезагрузки он на горизонтальной доске исчез — это согласуется с версией
«контакт на грани», а не с версией «ошибка в драйвере».

### 9.2 Монтажный наклон

В baseline `acc = (−0.060, −0.029, +0.996)`. Под тождественным Refloat
transform это даст в покое `balance_pitch ≈ +3.45°` и `roll ≈ +1.67°`.
Постоянное смещение такого размера напрямую войдёт в `error = setpoint −
balance_pitch` и станет постоянным током.

Причину нельзя разделить по имеющимся данным: это может быть наклон посадочного
места датчика, наклон самой доски на опоре, или и то и другое. Калибровка,
zero calibration и авто-ориентация запрещены ТЗ §8 — здесь только фиксируется
факт. Разбирать на v0.6C, после устранения §9.1.

### 9.3 Нулевое смещение гироскопа

+1.155 / +0.484 / −0.352 °/с. Смещение по оси тангажа (`gyro_y`, +0.484 °/с)
попадёт прямо в `pid->rate_p` и даст небольшой постоянный ток. Штатное
явление; калибровка запрещена, только документируется.

### 9.4 Углы измерений вышли за 10–20°

Фактические углы удержания: 30.8° (A), 15.2° (B), 29.2° (C), −36.6° (D).
На определение осей и знаков это не влияет — наоборот, увеличивает отношение
сигнала к шуму. Отмечено для полноты.

### 9.5 Абсолютная величина угла рыскания не измерялась

E и F дают знак и ось, но не масштаб: угол поворота не фиксировался
инструментально. Для рыскания этого достаточно — Refloat использует только
приращения и модуль (§7.4). Масштаб гироскопа задан шкалой ±500 °/с и
проверен на этапе v0.6A.
