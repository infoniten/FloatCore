# Архитектура совместимости с VESC Tool

## 1. Идея

Своего приложения, GUI и конфигуратора у FloatCore нет и не планируется.
Интерфейсом пользователя служит официальный VESC Tool, а FloatCore говорит на
его родном протоколе.

```
             ┌───────────────────────────────────────────────┐
             │                  VESC Tool                    │
             │   вкладка Refloat (QML, полученный с прибора) │
             └──────────────────────┬────────────────────────┘
                                    │ протокол VESC
                                    │ (TCP сейчас; UART/BLE позже)
             ┌──────────────────────▼────────────────────────┐
             │              platform/host                    │
             │   Transport  ·  TCP-сервер  ·  цикл приёма     │
             ├───────────────────────────────────────────────┤
             │           compat/vesc_protocol                │
             │  packet · commands · firmware_info            │
             │  telemetry · config_bridge · custom_app       │
             ├───────────────────────────────────────────────┤
             │        mock-платформа VESC (74 функции)       │
             ├───────────────────────────────────────────────┤
             │        refloat-upstream (без изменений)       │
             ├───────────────────────────────────────────────┤
             │      LogicalMotor — mock, вывода на CAN нет   │
             └───────────────────────────────────────────────┘
```

## 2. Слои и их границы

### `compat/vesc_protocol` — чистый C99

Не зависит ни от ESP-IDF, ни от FreeRTOS, ни от Refloat, ни от libc сверх
`<stdint.h>`, `<string.h>`, `<math.h>`, `<stdio.h>` (только для трассировки).
Одинаково собирается на host, на ESP32 и в тестах.

Доказательство, а не декларация: `tests/protocol/test_protocol.c` линкуется
**только** с этим каталогом — ни Refloat, ни mock, ни pthread. Если бы
зависимость просочилась, бинарник не собрался бы.

| Файл | Ответственность |
|---|---|
| `packet.{h,c}` | Кадрирование и CRC. Порт `bldc/comm/packet.c` |
| `vesc_buffer.{h,c}` | Big-endian сериализация чисел |
| `commands.{h,c}` | Идентификаторы, имена и **диспетчер** `VescServer` |
| `firmware_info.{h,c}` | Ответ `COMM_FW_VERSION`, виртуальный UUID |
| `telemetry.{h,c}` | `COMM_GET_VALUES` из `LogicalMotorTelemetry` |
| `config_bridge.{h,c}` | Чанки XML-схемы, чтение и запись конфигурации |
| `custom_app.{h,c}` | Обёртка `COMM_CUSTOM_APP_DATA` |

Состояние сервера — одна структура `VescServer` без глобальных переменных:
на ESP32 можно поднять несколько экземпляров (например, BLE и UART) независимо.

### `platform/host` — транспорт и склейка

`transport.h` описывает транспорт четырьмя функциями (`accept`, `recv`, `send`,
`disconnect`) и ничего не знает о протоколе. Сейчас реализован TCP; UART и BLE
встанут на то же место без изменений в протокольном слое.

`floatcore_host.c` собирает всё вместе и добавляет поток симуляции, который
гонит виртуальное время mock-платформы в реальном темпе 500 Гц — чтобы Refloat
действительно жил, а не стоял.

## 3. Модель потоков

Refloat не использует синхронизацию вообще (см. `threading_model.md`), поэтому
FloatCore Host воспроизводит семантику одного ядра **одной блокировкой**:

```
refloat_lock  ── держит поток симуляции на время такта (advance + IMU tick)
              └─ держит сетевой поток на время любого вызова в Refloat
                 (custom app data, чтение и запись конфигурации)

tx_lock       ── сериализует запись в сокет: RX-обработчик и сам Refloat
                 (через send_app_data) пишут независимо
```

Это ровно та схема, которая на ESP32 превращается в «всё, что трогает Refloat,
живёт на core 1»: сетевой стек принимает байты где угодно, но входит в Refloat
только через одну дверь.

## 4. Конфигурация: одна модель, без второй системы параметров

```
refloat-upstream/src/conf/settings.xml
        │ tools/gen_conf.py (замена vesc_tool --xmlConfToCode)
        ▼
confparser.c / confxml.c / conf_default.h
        │
        ├──► Refloat: RefloatConfig, значения по умолчанию, сериализация
        │
        ├──► conf_custom_add_config(get_cfg, set_cfg, get_cfg_xml)
        │           │
        │           ▼
        │    config_bridge ──► COMM_GET_CUSTOM_CONFIG_XML  (та же схема)
        │                 ──► COMM_GET_CUSTOM_CONFIG       (тот же блоб)
        │                 ──► COMM_SET_CUSTOM_CONFIG       (тот же парсер)
        │
        └──► store_eeprom_var → NVS (на host — файл)
```

Источник истины один — конфигурация Refloat. FloatCore не хранит копию
параметров, не переводит их в свой формат и не имеет собственных умолчаний.
Запись идёт прямо в `set_cfg()` Refloat, который сам сохраняет её в постоянную
память и вызывает `configure()`.

Практическое следствие: параметр, добавленный в upstream `settings.xml`,
появляется в VESC Tool после пересборки — без единой правки в FloatCore.

## 5. Идентификация

Централизована в `firmware_info.c`, значения по умолчанию — в
`firmware_info_defaults()`:

| Поле | Значение | Почему |
|---|---|---|
| `hw_name` / `fw_name` | `FloatCore` | Собственное устройство, не подделка под VESC |
| `hw_type` | `HW_TYPE_CUSTOM_MODULE` | VESC Tool не требует mcconf/appconf и не предлагает обновлять прошивку ESC |
| версия | 6.06 | Версия протокола, известная VESC Tool. Незнакомая переводит его в limited mode, где Refloat UI не открывается |
| UUID | FNV-1a от строки-seed | Стабилен между запусками: VESC Tool кэширует схему и QML по UUID |
| `custom_config_num` | 1 | Конфигурация Refloat |
| `qml_app` | 1 | Интерфейс Refloat отдаётся прибором |

Компромисс осознанный: имена и тип железа — свои, номер версии протокола —
совместимый. Это не выдача себя за VESC, а заявление «я говорю на диалекте 6.06».

## 6. Телеметрия

Единственный источник — `LogicalMotorTelemetry`, то есть агрегированные
показания двух VESC по правилам `motor_semantics.md`. На этом этапе за ней
стоит mock, реального CAN нет.

`Id`/`Iq` отдаются нулями, а не выдуманными значениями: STATUS-сообщения VESC
их не содержат, и подставлять туда ток мотора было бы враньём в интерфейсе.

`has_timeout` в поле статуса поднимается, если хотя бы один ESC не на связи —
так VESC Tool покажет проблему без отдельного канала.

## 7. Безопасность

Три независимых барьера:

1. **Диспетчер** блокирует все команды управления мотором до разбора аргументов.
2. **`LogicalMotor` — mock**: отвергает NaN/Inf и выход за лимит, считает
   «сколько кадров ушло бы», но не отправляет ни одного.
3. **CAN отсутствует физически**: драйвера нет, платы нет.

Проверяется тестом: семь команд управления мотором подряд, включая
`COMM_SET_CURRENT` на 1000 А, — ток мотора в телеметрии остаётся нулевым,
соединение живо.

## 8. Трассировка

```
build/floatcore_host --trace
```

```
RX  id=0   FW_VERSION               len=1
TX  id=0   FW_VERSION               len=47
RX  id=92  GET_CUSTOM_CONFIG_XML    len=10
TX  id=92  GET_CUSTOM_CONFIG_XML    len=410
!!  id=6   SET_CURRENT              len=5   motor command BLOCKED
..  id=14  GET_MCCONF               len=1   known but not implemented — ignored
```

Трассировка — поле структуры `VescServer` (`trace` + `trace_sink`), а не
глобальный флаг: на ESP32 можно включить её для одного транспорта.

## 10. Границы проверенного

Автоматически проверено на настоящем сокете: подключение, идентификация,
телеметрия, загрузка QML и XML-схемы целиком, чтение конфигурации, запись
параметра, сохранение через переподключение и через перезапуск процесса,
двусторонний обмен `COMM_CUSTOM_APP_DATA` (команда `INFO` Refloat отвечает
«Refloat 1.3.0»), блокировка команд мотору.

**Не проверено:** работа с живым VESC Tool — GUI в этой среде отсутствует.
Отрисовка вкладки Refloat, поведение кнопок Read/Write на странице конфигурации
и realtime-графики требуют ручной проверки.
