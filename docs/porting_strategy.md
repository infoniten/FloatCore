# Выбор стратегии переноса (ТЗ §13)

## Краткий ответ

**Выбрана Strategy B** — сборка нативных исходников Refloat под ESP32 поверх собственной
реализации интерфейса `vesc_c_if`, **с нулевыми изменениями в `refloat-upstream/src/`**
(исключается только LED-драйвер, который заменяется файлом с тем же интерфейсом).

Strategy A в формулировке ТЗ («запуск оригинального Refloat поверх LispBM») **невыполнима
по причине отсутствия предмета**, а не по причине сложности. Strategy C отвергнута.

## Почему Strategy A отпадает

ТЗ исходило из предположения, что Refloat — это Lisp-программа для LispBM. Аудит показал
обратное:

* `src/` — 40 файлов C (~7000 строк), компилируемых `arm-none-eabi-gcc` в
  position-independent бинарник `package_lib.bin`;
* `lisp/package.lisp` — **17 строк**: `load-native-lib`, передача версии прошивки,
  запуск BMS-потока;
* `lisp/bms.lisp` — 47 строк опционального BMS-поллера, выключен по умолчанию;
* балансировочная математика (Mahony, PID, ATR, tiltback-и) в Lisp **отсутствует полностью**.

Порт LispBM на ESP32 дал бы возможность выполнить эти 17 строк — и ничего больше. Более того,
`load-native-lib` загружает **ARM-машинный код**, который на Xtensa не исполним в принципе.
Чтобы «Strategy A» заработала, пришлось бы портировать LispBM *и* написать ESP32-версию
`load-native-lib` *и* всё равно перекомпилировать Refloat под Xtensa — то есть проделать всю
работу Strategy B плюс лишний интерпретатор в системе.

Единственный полезный остаток от Lisp-слоя — две extension-функции
(`ext-set-fw-version`, `ext-bms`). Они вызываются один раз при старте и 5 раз в секунду
соответственно, и заменяются 20 строками заглушек `lbm_*` (см. аудит §2.15).

## Почему Strategy B

Аудит выявил свойства кодовой базы, которые делают B почти механическим:

1. **Единственная точка контакта с платформой.** Refloat обращается к прошивке только через
   `VESC_IF->…` — 74 члена структуры. Мы предоставляем собственный экземпляр этой структуры
   и собственный `vesc_c_if.h`.
2. **`vesc_c_if.h` не принадлежит Refloat.** Он лежит в `vesc_pkg_lib/` — это SDK VESC.
   Все STM32-специфичные макросы (`VESC_IF` по адресу `0x1000F800`, `PROG_ADDR`, `HEADER`,
   `INIT_FUN`, `ARG`, `SYSTEM_TICK_RATE_HZ`) определены именно там. Заменив этот один файл
   своим, мы снимаем всю платформенную привязку, **не трогая `src/`**.
3. **Чистый C99.** Кроме `led_driver.{c,h}`, ни один файл не включает ничего, кроме
   `<math.h>`, `<string.h>`, `<stdint.h>`, `<stdbool.h>`, `<stddef.h>`, `<stdlib.h>` и
   `vesc_c_if.h`.
4. **Нет прямой работы с CAN.** Абстракция «два VESC как один мотор» полностью скрывается за
   `mc_*`.
5. **Самонастройка частот.** `frequency_tracker` измеряет реальные частоты контуров и
   пересчитывает все фильтры — порт не обязан воспроизводить точные 832 Гц VESC.
6. **Нет мьютексов/семафоров** — нечего отображать на примитивы FreeRTOS (но см. риск R-08:
   отсутствие синхронизации требует пиннинга задач на одно ядро).

Результат: обновление upstream сводится к `git submodule update` + пересборка. Конфликтов
слияния быть не может, потому что мы не редактируем чужие файлы.

### Что конкретно надо написать (это и есть compat-слой)

| Слой | Содержание | Объём (оценка) |
|---|---|---|
| `compat/vesc_api` | собственный `vesc_c_if.h` + экземпляр структуры, макросы `INIT_FUN`/`ARG`/`PROG_ADDR` | 400–600 строк |
| `compat/imu` | ICM-20948 → деротация/офсеты → AHRS прошивки → вызов `imu_ref_callback` | 600 строк |
| `compat/motor` | `MotorController`, агрегация телеметрии A/B, supervisor безопасности | 800 строк |
| `compat/adc` | 2 канала ADC + фильтр | 150 строк |
| `compat/storage` | NVS ↔ `eeprom_var` | 150 строк |
| `compat/events` | транспорт `send_app_data`/`set_app_data_handler` | 200 строк |
| `platform/esp32` | задачи, приоритеты, таймеры, `spawn`/`sleep_us`/`should_terminate` | 400 строк |
| `drivers/vesc_can` | TWAI + протокол VESC CAN (SET_CURRENT, STATUS 1–6) | 700 строк |
| `drivers/icm20948` | SPI/I2C драйвер | 500 строк |
| `drivers/led` | замена `led_driver.c` на RMT (не MVP) | 300 строк |

Порядок ~4000 строк собственного кода против ~7000 строк неизменённого Refloat.

### Известные шероховатости Strategy B

| Проблема | Решение | Тяжесть |
|---|---|---|
| `src/led_driver.c` пишет регистры STM32 | исключить из сборки, дать свой файл с тем же `led_driver.h`; `leds.c` патчить не нужно (проверено) | низкая |
| `src/time.h` объявляет `typedef uint32_t time_t` | не втягивать заголовки ESP-IDF в единицы трансляции Refloat | низкая |
| `confparser.c`/`confxml.c` генерируются бинарником `vesc_tool` | иметь `vesc_tool` в CI либо вендорить сгенерированные файлы с фиксацией версии | средняя |
| стек `spawn(…, 1536, …)` мал для Xtensa | масштабировать размер стека в реализации `spawn` | низкая |
| double-литералы в коде | флаг `-fsingle-precision-constant` (как в upstream `rules.mk`) | низкая |
| отсутствие синхронизации между потоками Refloat | пиннить IMU-задачу и главный поток на одно ядро | средняя |

## Почему не Strategy C

Перенос алгоритма в собственную прошивку означает:

* потерю связи с upstream: каждый релиз Refloat пришлось бы переносить вручную;
* потерю UI, протокола команд, формата конфигурации, документации, экосистемы;
* принятие на себя ответственности за корректность тюнинга, который сообщество отлаживало
  годами; ошибка в переносе ATR или duty tiltback — это падение с доски.

Единственный аргумент за C — «проще стартовать». Аудит показывает, что он неверен: Strategy B
не требует понимания алгоритма вообще, только реализации 74 функции с известной семантикой.
ТЗ прямо запрещает выбирать C ради простоты прототипа, и в данном случае C ещё и **сложнее**.

## Гибридная нота

Strategy B не исключает частичной «A»-подобности в будущем: если однажды понадобится
исполнять пользовательские Lisp-скрипты (как это делает VESC), LispBM можно добавить как
отдельный необязательный компонент, не влияющий на контур баланса. Это не нужно ни для MVP,
ни для полной функциональности Refloat.
