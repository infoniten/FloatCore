# Планирование потоков Refloat: настоящий VESC против FloatCore

Документ этапа v0.7D. Разбор по исходникам плюс измерения на плате. Итог —
одно изменение в платформенном слое, upstream Refloat не тронут.

---

## 1. Что делает настоящий VESC

Refloat — нативный пакет, загружаемый через LispBM, и потоки он создаёт
через `VESC_IF->spawn()`. Реализация — `lispBM/lispif_c_lib.c:99`:

```c
lib_thread lispif_spawn(void (*func)(void*), size_t stack_size,
                        const char *name, void *arg) {
    void *mem = lbm_malloc_reserve(stack_size);
    ...
    thread_t *thd = chThdCreateStatic(mem, stack_size, NORMALPRIO, lib_thd, info);
```

**Оба потока создаются с `NORMALPRIO`.** Приоритет в сигнатуре `spawn()`
отсутствует — попросить другой при создании нельзя.

Но это ещё не вся картина. `aux_thd` **сам понижает свой приоритет** первым
же действием (`refloat-upstream/src/main.c:1112-1114`):

```c
static void aux_thd(void *arg) {
    Data *d = (Data *) arg;
    if (VESC_IF->thread_set_priority) {
        VESC_IF->thread_set_priority(-1);
    }
```

А на стороне VESC это `chThdSetPriority(NORMALPRIO + priority)`
(`lispif_c_lib.c:708-711`, диапазон обрезается до ±5).

**То есть на настоящем VESC приоритеты потоков Refloat РАЗНЫЕ:** главный
остаётся на `NORMALPRIO`, вспомогательный уходит на `NORMALPRIO−1`.

### Исправление к документу v0.7C

В `esp32_safety.md`, пункт 42, было записано, что оба потока идут с
одинаковым приоритетом и что `aux_thd` поэтому задерживает главный. **Это
неверно.** `thread_set_priority` у нас реализован (`fc_vesc_if.c:253`), и
проверка на живой плате подтверждает:

```
name          state prio stack  num core
Refloat Main   	R	12	11564	11	1
Refloat Aux    	S	10	11492	12	1
fc_imu_rt      	R	14	3256	9	1
fc_super       	B	15	3548	13	1
```

Aux на 10, Main на 12. Вытеснить главный поток вспомогательный не может в
принципе, и объяснение из v0.7C было построено на неверной посылке.

## 2. Таблица соответствия

| | Настоящий VESC / ChibiOS | FloatCore / FreeRTOS |
|---|---|---|
| Приоритет при создании | `NORMALPRIO` = 64 | `FC_PRIO_REFLOAT` = 12 |
| После `thread_set_priority(-1)` | `NORMALPRIO−1` = 63 | 12 + (−1)·2 = **10** |
| Модель ядер | один Cortex-M4 | два ядра, оба потока закреплены за ядром 1 |
| Вытеснение | приоритетное | приоритетное |
| Квант между равными | `CH_CFG_TIME_QUANTUM = 4` при `ST_FREQUENCY = 10000` → **0.4 мс** | `configUSE_TIME_SLICING`, тик 1000 Гц → **1 мс** |
| Отображение `spawn` | `chThdCreateStatic`, стек из кучи LBM | `xTaskCreatePinnedToCore`, стек ×`FC_STACK_SCALE`, минимум 4096 |
| Семантика сна | `chThdSleepMicroseconds`, пробуждение в обработчике системного тика, 100 мкс | см. §3 — здесь и была разница |
| Мьютексы | ни одного в Refloat | ни одного, оба потока на одном ядре |
| Разделяемое состояние | `Data *d`, без блокировок | то же, потому и одно ядро |

Единственное существенное расхождение в этой таблице — **разрешение
системного тика**: 10 кГц у ChibiOS против 1 кГц у нас. Оно и определило
выбор механизма сна, и оно же оказалось источником проблемы.

## 3. Механизм сна — где была ошибка

Refloat просит не «поспать столько-то», а «проснуться к началу следующего
периода»: он вычитает из запроса время своей итерации
(`main.c:1058-1059`):

```c
int32_t ticks = lrintf(VESC_IF->timer_seconds_elapsed_since(loop_timer) * SYSTEM_TICK_RATE_HZ);
sleep_ticks = max(d->main_loop_ticks - ticks, 1);
```

Значит любая задержка механизма пробуждения **напрямую замедляет контур**:
она не компенсируется, а складывается с периодом.

### Как было

`esp_timer_start_once()` + ожидание уведомления. Разрешение таймера 1 мкс —
на первый взгляд идеально. Но обработчик `esp_timer` исполняется **в задаче
`esp_timer`**, а та закреплена за ядром 0 (`CONFIG_ESP_TIMER_TASK_AFFINITY_CPU0`),
тогда как потоки Refloat живут на ядре 1. Каждое пробуждение было
межъядерным уведомлением, ожидающим постановки чужой задачи на выполнение.

Измерено на плате (окно 45 с, установившийся режим):

```
Refloat Main   n=16896  просил 1800.7 мкс, спал 2037.1 мкс
               задержка mean 236.4  min 37  max 964
               гистограмма: 0-99:6051  100-199:8023  200-299:225
                            700-799:330  800-899:2001  900+:239
```

Отчётливый второй горб на 700-900 мкс. Проверка причастности CAN — тот же
двоичный файл, приём остановлен командой `can-stop`:

```
задержка mean 171.8  max 922
горб 700-899 сократился с 2331 до 1190 выборок из ~16600 (14 % -> 7 %)
```

То есть примерно половину хвоста давала активность приёма CAN на ядре 0,
вторая половина оставалась.

**Следствие:** главный поток Refloat работал на **~400 Гц вместо 500** —
период 2502 мкс при номинале 2000. Виноватым по прежней статистике выглядело
время исполнения, которое тут ни при чём.

## 4. Что было испробовано и отвергнуто

**Аппаратный таймер `gptimer` с пробуждением прямо из прерывания.** Идея
правильная — убрать задачу-посредника и межъядерный переход. Результат
измерения:

```
задержка mean 1662 мкс, 11129 выборок из 12052 в корзине 900+
период refloat_thd 3948 мкс, пропусков дедлайна 5718
```

Стало заметно хуже. Причина не разобрана до конца (вероятно, накладные
расходы перезапуска таймера на каждой итерации), и разбираться дальше не
стали: у механизма был более простой конкурент. Изменение откачено.

Запись здесь оставлена намеренно. Отрицательный результат — это тоже
результат, и он объясняет, почему в коде не `gptimer`.

## 5. Что сделано

`xTaskDelayUntil` по абсолютной отметке, с периодом, выведенным из первого
запроса потока.

```c
if (t->period_ticks == 0) {
    uint32_t ticks = (us + 500u) / 1000u;
    t->period_ticks = ticks ? ticks : 1;
    t->last_wake = xTaskGetTickCount();
}
xTaskDelayUntil(&t->last_wake, t->period_ticks);
```

Почему это ближе к замыслу, а не дальше:

* **Пробуждение в обработчике системного тика, на том же ядре.** Ровно как
  `chThdSleepMicroseconds` на ChibiOS: посредника нет.
* **Отметка абсолютная**, поэтому ошибка не накапливается, а компенсацию
  делает сам механизм — то же, ради чего Refloat вычитает время итерации.
* **Период берётся из первого запроса.** Главный поток на первой итерации
  просит полный период без компенсации (`main.c:770`), вспомогательный просит
  константу всегда (`main.c:1143`). Оба значения точные.
* Дальше запрошенная величина игнорируется **намеренно**: компенсацию уже
  делает `xTaskDelayUntil`, и делать её дважды значило бы ускорять цикл.

Цена — квантование тиком: 2000 мкс это ровно 2 тика, 33333 мкс округляются до
33 тиков (−1 % у потока светодиодов, что для 30 Гц безразлично).

Вызовов `sleep_us` в Refloat всего два, и оба — тела периодических циклов
(`main.c:777` и `main.c:1143`). Периодическая трактовка безопасна, потому что
другой в этом коде и не встречается.

Главный поток Refloat пошёл ровно на 500 Гц: число его итераций совпало с
числом итераций контура. Заявленная в upstream частота `MAIN_THREAD_FREQ 500`
наконец соответствует действительности.

### Решение по §12

**Вариант B — отображение механизма сна было неверным, исправлена
платформенная реализация.** Приоритеты не трогали, upstream не трогали,
семантика вызовов сохранена. Изменение уменьшает расхождение с настоящим
VESC, а не увеличивает его.

## 7. Поправка к измерению

Отметка периода потоков Refloat перенесена с момента засыпания на момент
**пробуждения**.

Прежняя точка мерила «пробуждение плюс исполнение», и разброс времени
исполнения выглядел как опоздание планировщика: при идеально периодическом
пробуждении половина периодов оказывалась бы «поздними» просто потому, что
предыдущая итерация была короче. Период потока — это интервал между
пробуждениями.

Добавлена отдельная статистика качества сна (`compat`-независимая часть —
`platform/esp32/main/fc_sched.{h,c}`, команда `sched`): сколько поток просил,
сколько спал, гистограмма задержки. Это **не время исполнения**: в этот
момент поток спит, и смешивать их было ошибкой прежней инструментовки.

## 8. Про метрику «late»

После перехода на тиковое пробуждение доля «поздних» периодов показывает
около 50 % на всех каналах при среднем ровно 2000.0 мкс и p50 около 1600-1900.
Это не деградация.

Порог «поздно» — превышение номинала на 20 %, то есть 2400 мкс. При точно
периодическом пробуждении период, измеренный в момент пробуждения, всё равно
колеблется: у контура — из-за биения между частотой обновления регистров
датчика (1126 Гц) и децимацией до 500 Гц, у потоков Refloat — из-за
квантования тиком. Среднее при этом остаётся ровно номинальным.

Значимые величины — **пропуски** (период больше двух номиналов) и
**максимум**. Обе улучшились: пропусков ноль, максимум 2740 мкс против 4381
до изменения, то есть контур ни разу не приблизился к удвоенному периоду.
