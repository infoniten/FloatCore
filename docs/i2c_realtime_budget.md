## B. Транзакция I²C

### Сколько операций на один семпл

Ровно **одна** транзакция в установившемся режиме. Банк регистров ICM-20948
кэшируется (`D.current_bank`) и сбрасывается только после ошибки,
инициализации или восстановления шины. Путь:

```
select_bank(0)          — кэш, на шину не выходит
i2c_master_transmit_receive:
  START · адрес+W · 0x2D (ACCEL_XOUT_H) · повторный START · адрес+R ·
  14 байт · STOP
разбор 7 слов, масштабирование, температура
```

14 байт — это непрерывный блок банка 0: ACCEL_XOUT_H..ACCEL_ZOUT_L (6),
GYRO_XOUT_H..GYRO_ZOUT_L (6), TEMP_OUT_H/L (2). Разбивать нельзя: между
чтениями датчик обновит регистры, и оси окажутся из разных семплов.
Температуру можно было бы не читать (минус 2 байта, ~47 мкс провода), но она
используется в диагностике дрейфа; семантика измерения не менялась.

### Конфигурация шины (§3)

| параметр | значение | откуда |
|---|---|---|
| порт | I2C_NUM_0 | `icm20948.c:334` |
| SDA / SCL | GPIO21 / GPIO22 | конфигурация драйвера |
| запрошено | 400 000 Гц | `scl_speed_hz` |
| источник тактов | APB 80 МГц | `I2C_CLK_SRC_DEFAULT` на ESP32 |
| scl_low_period / scl_high_period | 99 / 87 | **регистры периферии I2C0** |
| фильтр SCL и SDA | включён, порог 7 тактов | регистры |
| по регистрам | 400 000 Гц | обратный пересчёт по TRM |
| внутренние подтяжки | включены | `enable_internal_pullup = true` |
| таймаут транзакции | 100 мс | `reg_read` |
| режим драйвера | синхронный (`async_trans == false`) | `i2c_master.c:1332` |

Регистры говорят, что записали в железо, — но это ещё не частота на проводе:
высокий полупериод ESP32 отсчитывает лишь после того, как вход увидел SCL
высоким, и медленный фронт удлиняет каждый такт.

### Частота на проводе — измерена программно (§5, §6)

Осциллографа в работе не было. Вместо него — **развёртка по длине чтения**:
время вызова для N = 1, 2, 4, 8, 14, 20, 26 байт, по 100 повторов, оценщик —
минимум. На проводе время строго линейно по N (9 тактов на байт):

```
T(N) = a + b·N
b — время байта на проводе, СО ВСЕМ, что удлиняет такт, включая фронты
a — служебные 3 байта + START/rSTART/STOP + накладные расходы драйвера
```

Результат на спокойном ядре 0:

```
наклон b           23.53 мкс/байт       (при честных 400 кГц — 22.50)
ЧАСТОТА НА ПРОВОДЕ 382 559 Гц           (−4.4 % от заданной)
отклонение от прямой 3 мкс              модель линейна, годна
для 14 байт:       провод ~408 + накладные ~193 = 599 мкс
```

Повтор при работающем Refloat — 378 550 Гц, те же 3 мкс отклонения.

Медленные фронты удлиняли бы **каждый** такт на микросекунды, и наклон вышел
бы около 48 мкс/байт. Он 23.5. Шина работает практически на 400 кГц.

Арифметика подгонки вынесена в `compat/diag/fc_i2c_fit.c` и проверена тестами
на данных с заранее известным ответом (`tests/safety/test_i2c_fit.c`),
включая ровно тот случай, в котором я ошибся на v0.9H.

## D. Узкое место I²C

### Раскладка вызова по ядру

Прямой замер: во время вызова I²C считается, сколько процессора ядра 1
получили ДРУГИЕ задачи (Refloat Main, простой, супервизор). Счётчик FreeRTOS
обновляется при снятии задачи с процессора, поэтому каждый отрезок чужой
работы, закончившийся возвратом к задаче датчика, попадает в разность
целиком.

```
                              драйвер во flash     драйвер в IRAM
настенное время                   903.2 мкс           616.2 мкс
получили ДРУГИЕ задачи            418.5 мкс           400.3 мкс   ← провод
держала сама задача               484.6 мкс           215.9 мкс   ← собственный CPU
```

«Другие» ≈ провод: на проводе задача **блокируется**, как и написано в
драйвере (`xQueueReceive`, `i2c_master.c:589`). Активного ожидания нет —
моё утверждение из v0.9H было неверным.

### Причина: промахи кэша инструкций

Тот же код драйвера стоит ~180–190 мкс на спокойном ядре 0 и ~480 на ядре 1.
Функция одна, различается только кэш: у каждого ядра ESP32 свой кэш
инструкций на 32 КБ, код драйвера лежит во flash, и на ядре 1 его между
вызовами вытесняют Refloat и AHRS.

Доказано вмешательством: драйвер помещён в IRAM (`platform/esp32/main/i2c_iram.lf`,
весь `libesp_driver_i2c.a` и `i2c_hal`), и собственный процессор вызова упал
до 215.9 мкс — ровно к значению на спокойном ядре. Провод при этом не
изменился (418 → 400 мкс).

Цена — 11 КБ IRAM (59 675 → 70 719 из 131 072, свободно 60 КБ).

### Что было проверено и отвергнуто

| гипотеза | проверка | результат |
|---|---|---|
| шина медленнее 400 кГц | развёртка по длине | **отвергнута**: 382 кГц |
| внутренние подтяжки тормозят | наклон развёртки | **отвергнута** как причина стоимости |
| активное ожидание в драйвере | чужое время внутри вызова ≈ провод | **отвергнута** |
| несколько транзакций на семпл | путь кода | **отвергнута**: одна |
| межъядерное пробуждение (прерывание на ядре 0) | A/B размещения | **отвергнута**: 923 → 914 мкс |
| промахи кэша инструкций | перенос драйвера в IRAM | **подтверждена**: 485 → 216 мкс |

### Размещение прерывания

Исходно `I2C_EXT0` обслуживался на CPU 0: шину создавал старт датчика из
`app_main`. Теперь шина создаётся на ядре 1 — там же, где ждущая задача и где её
и так пересоздаёт путь повторной инициализации. A/B после переноса драйвера в
IRAM: простой ядра 1 17.09 % (прерывание на ядре 0) против 18.75 % (на ядре 1)
— разница в пределах шума. Диагностический вариант сохранён переключателем
сборки `-DFC_IMU_I2C_ISR_ON_CORE0=1`.

## E. Запись во flash

### Найденный достижимый путь в RUNNING

Политика супервизора (`config_write_allowed`, только DISARMED) проверялась
лишь при записи в RAM-зеркало. Сам коммит задача сброса делала по таймеру, не
глядя на состояние:

```c
if (g_st.commit_requested || due) {
    fc_storage_commit();      // состояние НЕ проверялось
}
```

Запрос, принятый в DISARMED за мгновение до `ready`, уходил во flash уже в
READY или RUNNING и останавливал оба ядра на ~5.8 мс.

### Отложенная запись

`compat/safety/fc_flash_policy.c`: решение принимается в момент коммита. Если
писать нельзя, запрос не выполняется и **не теряется** — остаётся ожидающим и
выполняется при первом DISARMED. Неудачная запись ожидание не снимает.
Автоматической записи в момент отказа нет. При невосстановимом отказе
(`FC_FAULT_INTERNAL`) запись остаётся отложенной до перезагрузки и видна в
телеметрии как ожидающая.

Телеметрия (`persist`): ожидает / просьб / эпизодов отсрочки / выполнено /
ошибок / длительность последней и худшей записи.

Все пути записи после загрузки:

| путь | кто просит | достижим в RUNNING до | после |
|---|---|---|---|
| коммит NVS по таймеру | задача `fc_nvs`, ядро 0 | **да** (узкое окно) | нет, откладывается |
| `imu-cal-save` | оператор | запрос только в DISARMED, коммит — нет гарантии | откладывается |
| `store_eeprom_var` Refloat | Refloat | запись отклоняется вне DISARMED | без изменений, отказ явный |
| `store_backup_data` Refloat | Refloat, только `!running` | нет | нет |
| счётчик загрузок | `app_main` | нет, до запуска контура | нет |

## F. Учёт процессора без двойного счёта

```
ядро 1
├── fc_imu_rt (приоритет 14) — ОДНА задача, внутри неё последовательно:
│   ├── вызов I²C            собственный CPU ~216 мкс (провод ~400 — блокировка)
│   ├── icm20948 read        разбор, конвейер, калибровка, AHRS ~290 мкс
│   └── control              колбэк Refloat ~520 мкс
├── Refloat Main (12)        отдельная задача
└── fc_super (15)            отдельная задача, 100 Гц

ядро 0
├── Refloat Aux (10)         с v0.9H
├── fc_can_rx, fc_log, fc_nvs, консоль
└── обработчики TWAI
```

`control`, `icm20948 read` и вызов I²C — участки **одной** задачи, а не три
задачи. Их измерения не вложены друг в друга. Итоговые доли по задачам берутся
из статистики FreeRTOS (`cpu`), а не складываются из каналов.

### Два дефекта собственного учёта, исправленные по ходу

1. **Накопитель занятости был один на систему.** Пока все измеряемые задачи
   жили на ядре 1, это было незаметно. Но в v0.9H на ядро 0 переехал
   вспомогательный поток Refloat и добавились каналы CAN RX и журнала — их
   работа вычиталась из окон ядра 1, хотя работа на соседнем ядре идёт
   параллельно и никого там не вытесняет. Теперь накопитель свой у каждого ядра.
2. **Арифметика окон жила только в платформенном коде** и проверялась глазами —
   ровно там в v0.9H и была ошибка с настенным временем. Она вынесена в
   `compat/diag/fc_cpu_account.c` и закрыта тестом на вложенное вытеснение
   (`tests/safety/test_cpu_account.c`): сумма собственных времён трёх вложенных
   окон равна настенному времени ядра, а не больше.

## H. Размещение по ядрам (§16, §17, §18)

| вариант | результат | решение |
|---|---|---|
| A. Main на ядре 1, удешевить I²C | простой ядра 1 с 0 % до ~18 % | **выбран** |
| B. Main на ядро 0 | не испытывался — см. ниже | отвергнут |
| C. прерывание I²C на ядре 0 | в пределах шума (17.1 % против 18.8 %) | не нужен |

**Почему Main остаётся на ядре 1.** Main и колбэк IMU делят ПИД,
`balance_current`, setpoint и пишут их на каждой итерации 500 Гц. На VESC
(ChibiOS, одно ядро) они никогда не исполняются одновременно. Разнести их по
ядрам — значит создать класс гонок, которого в upstream нет. После переноса
драйвера I²C в IRAM это и не нужно.

**Цена исправления v0.9H.** `Refloat Aux` на ядре 0 теперь исполняется
параллельно с Main, чего на ChibiOS не бывает. Aux пишет из колбэков
перенастройки коэффициенты фильтров, которые читают Main и колбэк IMU
(`pid_configure`, `ema_configure(&d->balance_current)`, `motor_control_configure`
и др., `main.c:154-178`). Класс опасности при этом тот же, что в upstream: на
ChibiOS Main с более высоким приоритетом тоже может вытеснить Aux посреди
перенастройки и прочитать наполовину обновлённый набор. Одиночные выровненные
32-битные записи на Xtensa атомарны, внутренняя SRAM общая и без кэша данных.
Перенастройка срабатывает только при заметном сдвиге измеренной частоты цикла —
при стабильных 500 Гц практически никогда. Риск принят и зафиксирован.

## Критерий запаса (§19)

`missed = 0` недостаточен: он может держаться на удаче. Критерий выведен из
того, что ляжет на ядро 1 при замыкании контура.

| статья | доля ядра 1 | источник |
|---|---|---|
| путь мотору (гейт → координатор → 2 кадра) | 3.1 % mean, 5 % p99 | v0.9G §7; в контуре исполняется в контексте Refloat Main, на ядре 1 |
| пик супервизора | ~2.3 % | 227 мкс раз в 10 мс |

**Критерий:**

1. простой ядра 1 **не меньше 10 %** в худшем безопасном режиме — после
   вычета пути мотору остаётся не меньше 5 %;
2. `missed = 0` во всех каналах;
3. p99 периода `refloat_thd` и `control` **не больше 2500 мкс** (1.25 номинала);
4. фактическая частота обоих — 500 Гц.

## I. 500 Гц: дрожание периода и его причина

### Что было видно

После переноса драйвера в IRAM пропуски ушли, но первая пятнадцатиминутная
приёмка показала **late 36.9 %** и p99 периода 2840 мкс — при среднем ровно
2000 и простое ядра 1 в 26 %. Процессора хватало с избытком. Гистограмма
периода не была размазана: острые пары, в сумме дающие 4000 мкс (1480 + 2520,
1235 + 2765). Короткий период, затем длинный.

### Что было проверено и отвергнуто

| версия | проверка | результат |
|---|---|---|
| лотерея фазы между задачами при загрузке | 4 перезагрузки | **отвергнута**: 20–40 % во всех |
| RUNNING или вооружение | 4 режима EXP | **отвергнута**: 39 % даже без RUNNING |
| энергосбережение, снижение частоты | конфигурация | **отвергнута**: `CONFIG_PM_ENABLE` выключен |
| колебания длительности чтения I²C | гистограмма вызова | **отвергнута**: чтение одногорбое, 600–650 мкс |
| критическая секция в Refloat Main | перекрёстный снимок | **отвергнута**: Main в момент поздних пробуждений спит |

Решающим был канал **«imu пробуждение»** — отметка сразу после
`vTaskDelayUntil`. Каналы `control` и `icm20948 read` отмечали период после
чтения I²C, и это расходилось с принципом v0.7D. Новый канал показал: дрожит
само пробуждение (late 49.99 % в LAB_SAFE без RUNNING), а не чтение.

### Причина — доказана измерением

В многоядерном IDF FreeRTOS счётчик тиков увеличивает **только ядро 0**
(`port_systick.c`: `core 0 calls xTaskIncrementTick(), core 1 calls
xTaskIncrementTickOtherCores()`). Задачу, закреплённую за ядром 1 и спящую в
`vTaskDelayUntil`, разблокирует обработчик тика ядра 0, а подхватывает её —
либо сразу, либо на собственном тике ядра 1. Таймеры тиков у ядер независимые.

На тики обоих ядер повешены крючки (`esp_register_freertos_tick_hook_for_cpu`),
и в момент каждого пробуждения записано, сколько прошло от тика каждого ядра:

```
фаза тика ядра 1 относительно ядра 0:   765 мкс
ПОЗДНИЕ пробуждения:   через  25 мкс после тика ЯДРА 1,   789 мкс после тика ядра 0
```

Задача просыпалась то от одного тика, то от другого, и период прыгал ровно на
разность фаз. От чего зависел источник пробуждения, от того и доля
«опозданий» — отсюда её зависимость от загрузки ядра. Главный поток Refloat
спит на том же механизме и показывал ту же долю.

### Исправление

`platform/esp32/main/fc_rt_clock.c`: таймер общего назначения с прерыванием на
ядре 1 (запускается из задачи датчика, поэтому прерывание размещается там же —
подтверждено `esp_intr_dump`: `TG0_T0_LEVEL` на CPU 1). Обработчик будит
подписанные задачи уведомлением напрямую, без участия ядра 0. Подписаны задача
датчика и главный поток Refloat (если его защёлкнутый период совпадает с
ритмом). Семантика прежняя: абсолютная сетка, пропущенное срабатывание не
догоняется. Если таймер не поднимется, остаётся прежний ритм от тика.

```
LAB_SAFE, без RUNNING (прежде 50 % опозданий), 30 с:
                       late      p99     p99.9    min–max
control               0.00 %    2240     2280    1715–2307
refloat_thd           0.00 %    2160     2160    1778–2222
imu пробуждение       0.00 %    2160     2200    1766–2234
```

## J. Диагностика, ломавшая реальное время

Единственный зазор IMU первой приёмки (5620 мкс) пришёлся на отметку 943 с —
после окна, на мои же диагностические команды. `vTaskList` и
`uxTaskGetSystemState` для каждой задачи побайтно сканируют стек, пока
планировщик остановлен. Проверено напрямую:

```
10 × прежняя tasks   missed 5 во всех каналах, период до 6806 мкс
10 × новая tasks     зазоров 0, пропусков 0
10 × новая cpu       зазоров 0
```

Обе команды переписаны на явный список задач: `vTaskGetInfo` без подсчёта стека
и `uxTaskGetStackHighWaterMark` по одной задаче — он читает память стека, не
останавливая планировщик.

## K. Стоимость собственных зондов

Вторая пятнадцатиминутная приёмка (уже с аппаратным ритмом) прошла по всем
пропускам и дрожанию, но показала **простой ядра 1 2.78 %** — при 26 % в
первой. Выросли обе задачи: датчик на ~270 мкс за итерацию, Refloat Main на ~195.

Кандидатов было два: сам ритм (обе задачи теперь просыпаются в один момент, и
их код в каждом периоде перемежается) и зонды в цикле датчика, добавленные на
этом этапе. Разведены матрицей 2×2 на одной прошивке, в одном режиме:

```
             ритм   зонды    fc_imu_rt   Main     простой ядра 1   control late
on_off        on     off      44.9 %    27.4 %      26.15 %          0.00 %
off_off       off    off      47.4 %    23.6 %      27.61 %         39.96 %
off_on        off    on       49.1 %    27.5 %      21.64 %          9.80 %
```

Аппаратный ритм стоит около полутора процентов простоя и убирает дрожание

штатной сборке им не место. Они вынесены в диагностическую сборку
`-DFC_DIAG_LOOP_PROBES=1`; в штатной остались только настенное время и
гистограмма вызова I²C, которые ничего не стоят.

Урок этапа, повторённый дважды: **инструмент измерения сам входит в
измеряемое**. Первый раз — `vTaskList`, рвавший контур на 6 мс, второй — зонды,
съедавшие запас ядра. Оба раза это обнаружилось только потому, что сравнение
шло с вариантом без инструмента.

## Q. Что осталось

1. Подтяжки SDA/SCL — НЕИЗВЕСТНО до прозвонки.
2. Процессор работает на 160 МГц, а не на 240: запас на +50 %, не
   использованный намеренно.
3. Код будильника на `esp_timer` в `fc_vesc_if.c` создаётся, но не
   запускается с v0.7D — мёртвый, удаление отложено.
4. «Refloat Aux» на ядре 0 исполняется параллельно с Main — класс риска тот
   же, что в upstream при вытеснении, принят (раздел H).
5. Инструменты по умолчанию смотрят на порт `usbserial-3120`, а плата сейчас
   на `usbserial-1130` — передавать `--port`.
