# Параметры мотора: что известно, что прочитано и что подтверждено

Документ этапов v0.7C и v0.8A. **Мотор подключён к половине 118, детекция
выполнена. Выхода на мотор у FloatCore по-прежнему не существует как кода.**

Что изменилось на v0.8A: пять параметров половины 118 перешли из
«не подтверждено» в «подтверждено на моторе», и заодно выяснилось, что
записанная конфигурация была неверна в двух местах независимо. Половина 100
осталась без мотора, и её значения по-прежнему только прочитаны — поэтому
доверие в модели теперь хранится **отдельно по половинам**.

Модель в исполняемом виде: `compat/motor/fc_motor_model.{h,c}`, проверки —
`tests/safety/test_motor_prep.c`.

---

## 1. Зачем понадобилась степень доверия

Проект уже дважды получал правдоподобное, но неверное число.

Сначала заглушки FloatCore (`flux = 0.0045`, `poles = 30`) дали расчётный
коэффициент **120 А/градус** — величину, при которой доска насыщает ток на
наклоне в одну двенадцатую градуса. Аномалия была замечена на v0.6E.

Потом реальная конфигурация ESC (`flux = 0.1`, `poles = 14`) дала
**11.6 А/градус** — величину правдоподобную. Но правдоподобие не равно
истине: обе цифры прочитаны из настроек, которые кто-то когда-то ввёл, и ни
одна не измерена на моторе, который будет подключён.

Поэтому у каждого параметра здесь есть не только значение, но и
происхождение, и степень доверия.

## 2. Три степени доверия

| Степень | Что означает |
|---|---|
| `НЕ ПОДТВЕРЖДЕНО` | значение известно, но ничем физически не подкреплено |
| `прочитано из ESC` | прочитано при нас и сверено двумя независимыми путями — доверие к **каналу**, не к числу |
| `подтверждено на моторе` | измерено или проверено на физически подключённом моторе |

Состояние после v0.8A: **пять параметров из десяти подтверждены на половине
118**, на половине 100 — ни одного. Модель в целом не готова: требование
«подтверждено на обеих» намеренно строгое, машина двухмоторная.

Разница между второй и третьей степенью — суть документа. На v0.7B
конфигурация была прочитана через CAN и **побайтово** сверена с независимым
чтением по USB: `FW_VERSION` и `APPCONF` совпали целиком, в `MCCONF`
разошлись только смещения датчиков, которые ESC меряет при каждом включении.
Это доказывает, что канал не врёт. Это ничего не говорит о том, к какому
мотору относятся числа.

## 3. Три категории параметров

| Категория | Смысл | Кто задаёт |
|---|---|---|
| Измеряется детекцией | FOC-детекция выдаёт результат | процедура, не человек |
| Введено человеком | детекция это не проверяет | человек |
| Предел безопасности | не свойство мотора, а наше решение | мы, и детекция не должна это трогать |

Разделение практическое: после детекции **первая** категория обязана быть
перечитана, **третья** обязана остаться нетронутой. Тест проверяет, что все
параметры первой категории помечены к обновлению.

## 4a. Критерий перехода в «подтверждено» (v0.7D §15)

У каждого параметра записан **проверяемый** критерий, а не пожелание
«убедиться». Хранится в самой модели (`verify_criterion`), проверяется тестом
на наличие у всех параметров.

| Параметр | Что переводит в VERIFIED |
|---|---|
| `foc_motor_r`, `foc_motor_l`, `foc_motor_flux_linkage` | новая детекция FOC на физически подключённом **именно этом** моторе |
| `si_motor_poles` | вращение вывешенного колеса на известной механической скорости; полюса = 2 × ERPM / об-мин |
| `l_current_max` | выбирается человеком; подтверждается проверкой на вывешенном колесе |
| `l_current_min` | то же, плюс проверка, что торможение не даёт недопустимого regen |
| `l_in_current_max` | то же, плюс измерение тока батареи под нагрузкой |
| `si_battery_cells` | измерение напряжения батареи мультиметром и сверка с числом ячеек |
| `si_wheel_diameter` | физическое измерение диаметра колеса |
| `si_gear_ratio` | подтверждение прямого привода мотор-колеса, то есть 1.0 |

Ни один параметр не меняет степень доверия «сам собой» и ни один не
повышается чтением из ESC: чтение подтверждает канал, а не число.

## 5. Число полюсов — измерено, 30

Определено **вращением от руки**, без единой моторной команды, до детекции.

```
Δtach = 899 шагов за 10 оборотов в одну сторону
Δ|tach| = 899 — совпало со знаковым, значит счёт чистый
899 / 10 = 89.9 шага на механический оборот
```

Тахометр считает **шесть шагов на электрический оборот** — это прямо
написано в `mcpwm_foc.c:3765`: *«Update tachometer (resolution = 60 deg as
for BLDC)»*. Ни `mcpwm_foc_get_tachometer_value()`, ни
`mc_interface_get_tachometer_value()`, ни `commands.c` масштабирования не
добавляют. Отсюда:

```
полюса = Δtach / (3 × оборотов) = 899 / 30 = 29.97  ->  30
```

Ближайший другой кандидат (28 полюсов) требовал бы 840 шагов — на 63 шага
меньше, то есть в шестьдесят раз дальше погрешности в один шаг.

**Записанные 14 неверны.** Подозрение из v0.7D — «у мотор-колёс обычно 30, а
14 характерно для outrunner-мотора скейта» — подтвердилось.

Детекция FOC полюса не определяет: она меряет сопротивление, индуктивность и
потокосцепление, а полюса в её выход не входят. Поэтому измерение от руки —
не обходной путь, а единственный доступный.

Половина B по-прежнему несёт 14. Почти наверняка там тот же мотор, но
предполагать это в модели мы не будем: измерим, когда подключим.

## 6. Потокосцепление — измерено, 19.6 мВб вместо записанных 100

Записанное значение было неверно **в 5.1 раза**.

Проверка на правдоподобие, которая сразу показывает, какое из значений
физично:

```
амплитуда фазного напряжения при полной модуляции ≈ 41 / √3 = 23.7 В

λ = 0.0196 Вб  ->  11 545 ERPM  ->  770 об/мин  ->  ~40 км/ч
λ = 0.1 Вб     ->   2 264 ERPM  ->  151 об/мин  ->  ~8 км/ч
```

Восемь километров в час для моноколеса невозможно. Сорок правдоподобно.

### Первая попытка измерения провалилась, и алгоритм этого не заметил

Важно для будущих измерений. При токе детекции 1.67 А колесо чуть
провернулось, встало и завибрировало — срыв синхронизма в открытом контуре.
Процедура при этом вернула **положительное** λ = 0.605 мВб и пометила поле
зелёным.

Разбор `conf_general.c:967`: цикл разгона выходит, когда измеренная
скважность достигает заданной, а скважность растёт от самой частоты даже при
стоящем роторе. Отказные ветки помечают результат отрицательными значениями
(−1, −2, −3), и ни одна не сработала. **Зелёное поле означает «процедура
вернулась», а не «результат физичен».**

Ток 1.67 А взялся как `l_current_max / 3` = 5 / 3 — то есть наш временный
предел подсказал процедуре слишком малый ток. Удалось со второй попытки при
`I = 4 А` и темпе разгона `α = 500` вместо 2000 ERPM/s: требуемый момент
пропорционален темпу, и его снижение вчетверо дало запас. **Предел 5 А при
этом не трогали.**

### Постоянная момента

```
T = 1.5 × p × λ = 1.5 × 15 × 0.0196 = 0.441 Н·м на ампер
```

**Все прежние оценки коэффициента контура недействительны** — и 120 А/градус
на заглушках, и 11.6, и 5.4. Они строились на числах, которые теперь
измерены и оказались другими. Пересчитывать надо от измеренных значений, на
этапе балансировки.

## 6a. Откуда взялась конфигурация — теперь известно

v0.8A дал ответ на вопрос, который висел с v0.7A.

| Параметр | Происхождение |
|---|---|
| `foc_motor_r` | настоящий вывод детекции **этого** мотора: совпал на 0.26 % |
| таблица Hall | настоящий вывод детекции **этого** мотора: совпала в пределах единицы из 200 |
| `foc_motor_l` | тоже отсюда; расхождение 20 % объясняется положением ротора при `Lq−Ld` = 38 % от `L` |
| `foc_motor_flux_linkage` | **введено руками** и неверно в 5.1 раза |
| `si_motor_poles` | **введено руками** и неверно в 2.14 раза |
| `si_wheel_diameter`, `si_gear_ratio` | **введены руками**, от другого аппарата |

Складывается связная картина: кто-то прогнал детекцию на этом моторе и
получил верные R, L и таблицу датчиков, а потом вписал потокосцепление и
полюса руками — и вписал неправильно. Круглое `0.1` при некруглых R и L было
признаком ручного ввода, и признак оказался верным.

## 7. Параметры, явно относящиеся к другому аппарату

`si_wheel_diameter = 0.083 м` (83 мм) и `si_gear_ratio = 3.0`.

У моноколеса диаметр порядка 0.28 м и прямой привод, то есть передаточное
отношение 1.0. Восемьдесят три миллиметра с редукцией втрое — это
конфигурация чего-то другого, скорее всего оставшаяся от прежнего
использования контроллера.

На управление это не влияет (только на расчёт скорости и одометра), но
хорошо иллюстрирует общий вывод документа: **в этой конфигурации есть
параметры, которые заведомо не относятся к нашему аппарату.** Из чего следует,
что и остальные надо перепроверить, а не принять на веру.

## 8. Почему заглушки FloatCore не приведены к прочитанным значениям

`platform/esp32/main/fc_vesc_if.c` по-прежнему отдаёт Refloat
`si_motor_poles = 30` и `flux = 0.0045`.

Забавное совпадение: заглушка полюсов всё это время содержала **30** — то
есть верное значение, — а конфигурация ESC несла неверные 14. Совпадение, а
не заслуга: заглушку выбирали как «типичное для мотор-колеса», не измеряя.

**Исключение сделано для числа ячеек:** оно приведено к 10 на v0.7D. Причина
в том, что это единственный из трёх параметров, чьё правильное значение
**известно независимо** — батарея подтверждена владельцем и согласуется с
каждой отсечкой в конфигурации ESC. Полюса и flux такой независимой опоры не
имеют: их «правильные» значения взяты из той же конфигурации, достоверность
которой и ставится под сомнение.

Соблазн подставить туда прочитанные 14 / 0.1 / 10 велик и на первый взгляд
безобиден: мотора нет, хуже не станет. Но подставить неподтверждённое число
означает сделать его невидимым — дальше оно будет выглядеть согласованным и
проверять его никто не станет. Пока значение заведомо-неверное, вопрос
остаётся открытым и заметным.

Поэтому все предложенные изменения собраны в change set
(`first_motor_bringup_plan.md` §7) и ждут отдельного решения, а модель здесь
хранит и прочитанное значение, и степень доверия к нему.

## 9. `l_in_current_min` — почему ноль означает «тормоза нет»

Разобрано на v0.7D.1, и вывод v0.7D пришлось исправить.

Предел входного тока не применяется к току батареи напрямую. Он
пересчитывается в предел тока мотора (`mcpwm_foc.c:3564-3567`):

```c
const float mod_q = motor_now->m_motor_state.mod_q_filter;
if (mod_q > 0.001) {
    utils_truncate_number(&iq_set_tmp, lo_in_current_min / mod_q, lo_in_current_max / mod_q);
} else if (mod_q < -0.001) {
    utils_truncate_number(&iq_set_tmp, lo_in_current_max / mod_q, lo_in_current_min / mod_q);
}
```

`utils_truncate_number` — обычное усечение. При `lo_in_current_min = 0`
нижняя граница равна `0 / mod_q`, то есть **ровно нулю**: отрицательный `iq`
зажимается в ноль, пока колесо вращается.

Дальше идёт ограничение по току мотора (`lo_current_min`), но оно уже ничего
не решает: ноль строже, чем −3, и применён раньше.

| Вопрос | Ответ |
|---|---|
| Запрет отрицательного тока батареи? | Да, и жёстче: ограничение наложено на `iq` |
| Даёт ли `l_current_min = −3 А` тормозной момент? | **Нет**, пока `\|mod_q\| > 0.001` |
| Куда уходит энергия торможения? | Никуда — торможения не происходит |
| Может ли подняться напряжение шины? | Только на переходном процессе |
| Как ограничивается момент? | Усечением `iq` до `lo_in_current_min / mod_q` |
| Вывешенное колесо | Раскрученное **нечем остановить электрически** |
| Едущая доска | Балансировка невозможна: момент против вращения нужен постоянно |

Отдельно: при `|mod_q| ≤ 0.001` **не выполняется ни одна ветка** — у стоящего
колеса ограничение по входному току не применяется вовсе, работает только
`l_current_min`.

**Исправление к v0.7D.** Там записано, что −3 А торможения безопасны, потому
что энергия не попадёт в батарею. Безопасны — да, но потому, что торможения
нет вообще. Это было подано как защита, хотя это функциональный дефект:
`l_in_current_min = 0.0` делает замкнутую балансировку невозможной.

Решение: **−1 А** для первого прокрута, применяется вместе с остальными
пределами непосредственно перед ним. Для езды значение будет другим и
определяется на реальной машине — это разные понятия, и смешивать их нельзя.
