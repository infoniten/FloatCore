# Контракт IMU: что именно Refloat ждёт от платформы

Документ фиксирует контракт `VESC_IF` в части IMU **по исходникам upstream**,
а не по памяти и не по документации VESC. Каждое утверждение снабжено ссылкой
на файл и строку в `refloat-upstream/`.

Он понадобится на этапе v0.6B, когда реальный датчик будет подключён к
контуру. На v0.6A этот контракт выполняет mock
(`platform/esp32/main/fc_imu_mock.c`).

---

## 1. Функции

| Функция | Кто вызывает | Частота |
|---|---|---|
| `imu_set_read_callback(cb)` | `main.c:2710`, снятие `:2658` | 1× при старте |
| `imu_startup_done()` | `main.c:844` | 500 Гц, пока не готов |
| `imu_get_roll/pitch/yaw()` | `imu.c:36-40`, `leds.c:973` | 1× на семпл |
| `imu_get_gyro(float g[3])` | `imu.c:44` | 1× на семпл |
| `imu_get_accel(float a[3])` | не используется Refloat | — |
| `imu_get_quaternions(float q[4])` | не используется Refloat | — |
| `cb(acc, gyro, mag, dt)` | платформа → Refloat | частота семплирования |

## 2. Единицы измерения

### `imu_get_roll/pitch/yaw()` — радианы

`refloat-upstream/src/imu.c:36-40`:

```c
float roll_rad = VESC_IF->imu_get_roll();  // in Radians
imu->pitch = rad2deg(VESC_IF->imu_get_pitch());
imu->roll = rad2deg(roll_rad);
imu->yaw = rad2deg(VESC_IF->imu_get_yaw());
```

Комментарий upstream и обёртка `rad2deg()` не оставляют места толкованию.

### `acc` в callback — g (единицы ускорения свободного падения)

`balance_filter.c:42-48` сравнивает модуль вектора с единицей:

```c
data->acc_mag = data->acc_mag * 0.9 + new_acc_mag * 0.1;
float confidence = 1.0 - (0.02 * sqrtf(fabsf(data->acc_mag - 1.0f)));
```

Если бы вектор приходил в м/с², в покое `acc_mag` был бы 9.81, и доверие к
акселерометру всегда оказывалось бы заниженным.

### Две разные единицы гироскопа

Здесь была ошибка, исправленная на v0.6D: раньше в этом документе
утверждалось, что и массив в callback, и `imu_get_gyro()` отдают рад/с.
Обоснование существовало только для первого.

**Массив в callback — рад/с.** `balance_filter.c:115-124` интегрирует

`balance_filter.c:114-125` интегрирует кватернион напрямую:

```c
gx *= (0.5f * dt);
data->q0 += (-qb * gx - qc * gy - data->q3 * gz);
```

Такая форма корректна только для рад/с.

**`imu_get_gyro()` — °/с.** Это ДРУГАЯ функция и другой массив. В исходниках
Refloat нет места, по которому её единицы восстанавливались бы напрямую:
результат используется только как `pitch_rate` (`imu.c:51`). Вывод сделан по
масштабам PID (`pid.c:69`):

```
rate_p = -pitch_rate · kp2 · TORQUE_CONSTANT_COMPAT = 0.3645 · pitch_rate
```

При 20 °/с в градусах это 7.3 А — сравнимо с 12 А, которые даёт P-член на
одном градусе при `kp` = 20. В радианах те же 20 °/с дали бы 0.13 А, то есть
«Rate P» с диапазоном 0…3 и значением по умолчанию 0.6 не влиял бы ни на что.
Для основного параметра настройки это неправдоподобно.

> **Подтверждено на v0.6D.1 по исходникам bldc.** `imu_get_gyro()` отдаёт
> `m_gyro`, а `m_gyro` конвертируется в радианы через `DEG2RAD_f()` перед
> подачей в AHRS — значит хранится в °/с. Пользовательский callback получает
> уже конвертированный `gyro_rad`. Косвенный вывод из масштабов PID
> подтвердился; менять ничего не потребовалось. Полная цепочка с цитатами —
> `docs/vesc_imu_semantics.md`.

### `dt` — секунды, фактический интервал

`main.c:737-741`: `dt` идёт в `latency_tracker_update()` и
`frequency_tracker_update()`, по которым Refloat вычисляет фактическую частоту
и подстраивает коэффициенты фильтров. Подставлять номинал вместо реального
интервала нельзя — это исказит всю фильтрацию.

## 3. Система координат

При единичном кватернионе `(1,0,0,0)` оценка направления гравитации в
`balance_filter.c:100` равна:

```c
float halfvz = q0*q0 - 0.5f + q3*q3;   // = 0.5 при единичном кватернионе
```

то есть вектор `(0, 0, +0.5)` — гравитация направлена по **+Z**.

Следовательно, в покое платформа обязана отдавать `acc = (0, 0, +1)` g.
Любой другой вектор заставит фильтр Mahony «доворачивать» доску до тех пор,
пока оценка не совпадёт с измерением.

Знаки осей X и Y задаются тем, как ориентирован датчик относительно доски, и
на v0.6A **сознательно не определены** — см. `icm20948_driver.md` §7.

## 4. Порядок и свежесть

* `imu_startup_done()` должен возвращать `false`, пока датчик не готов. Пока
  он `false`, Refloat остаётся в `STATE_STARTUP` — безопасном состоянии по
  умолчанию (`main.c:844`).
* `imu_get_*()` вызываются **изнутри** `imu_ref_callback` (`imu.c:36-44`),
  поэтому к моменту вызова callback все буферы уже должны быть обновлены.
  Refloat читает согласованный снимок, а не «то, что придёт».
* Частота семплирования отдаётся через
  `get_cfg_int(CFG_PARAM_IMU_sample_rate)`. **Ноль недопустим**: Refloat
  трактует его как прошивку 6.02 и подставляет выдуманные 620 Гц
  (`main.c:1186-1190`).

## 5. Что происходит при отказе

Проверено host-харнессом ещё на этапе 0.2:

| Отказ | Поведение Refloat |
|---|---|
| Callback перестал вызываться | контур молчит, команд мотору нет; тягу снимает watchdog VESC. Сам Refloat отказа не замечает |
| NaN в гироскопе | необратимо разрушает фильтр ориентации; выход молча вырождается в нулевой ток, состояние остаётся `RUNNING` |
| Замерший датчик | Refloat не обнаруживает |

Отсюда прямое следствие: **обнаружение отказов IMU — обязанность compat-слоя,
а не Refloat.** На v0.6A это реализовано в `compat/safety/fc_imu_health.c` и
Safety Supervisor.

---

## 5a. Коррекция ориентации и смещений выполняется ДО всего

В штатной прошивке VESC сырые данные датчика сначала поворачиваются матрицей,
построенной из `imu_config.rot_roll/rot_pitch/rot_yaw`, затем из них
вычитаются `accel_offsets/gyro_offsets`, и только потом результат идёт и в
AHRS, и в callback пакета. Порядок обязателен: смещения хранятся в уже
повёрнутой системе координат.

Следствие для FloatCore: слой коррекции обязан быть общим для обоих путей
углов. Разбор — `docs/imu_calibration_architecture.md`.

## 6. Частота выдачи регистров: 1125 Гц, а не ODR

Установлено измерением на v0.6D и относится к любому потребителю драйвера.

`SMPLRT_DIV` задаёт частоту флага готовности и записи в FIFO. **Регистры
данных обновляются на внутренней частоте 1.125 кГц независимо от делителя.**
Измерено: при чтении 1619 раз/с слова движения менялись 1126 раз/с.

Практическое следствие: определить границу выборки сравнением содержимого
регистров нельзя. Платформа задаёт ритм сама (500 Гц) и децимирует поток;
обоснование — `real_imu_refloat_integration.md` §2.

Температурный канал обновляется отдельно от осей и в сравнение не входит.

## 7. Состояние на v0.6D

Контракт выполняет **реальный ICM-20948** через единый realtime-тракт
(`platform/esp32/main/fc_imu_rt.c`, `compat/imu/`). Mock сохранён и
используется host-тестами.

```
IMU source: REAL ICM-20948
контур:     500 Гц, одна выборка — одна итерация
AHRS:       Mahony платформы, формулы и знаки совпадают с balance_filter
```

Подробности — `real_imu_refloat_integration.md`.

## 8. Состояние на v0.6A (историческое)

Контракт выполняет mock: покой, `acc = (0,0,+1)` g, `gyro = 0` рад/с,
кватернион `(1,0,0,0)`, углы 0 рад, `dt` — фактический интервал по
`esp_timer`, частота 500 Гц отдаётся в `CFG_PARAM_IMU_sample_rate`.

Реальный датчик читается параллельно и в контур не идёт.

> Исторический статус v0.6A. Подключение выполнено на v0.6D; калибровка
> (ноль монтажа, смещение гироскопа) по-прежнему НЕ выполнена и входит в
> условия перед включением мотора.
