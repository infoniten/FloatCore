# Политика записи конфигурации

Правило одно: **постоянная запись разрешена только в состоянии `DISARMED`.**

Документ объясняет, почему именно так, чем это измерено и как проверено на
живой плате.

---

## 1. Проблема

Операция с SPI-flash на ESP32 отключает кэш инструкций для обоих ядер. Код,
который в этот момент исполняется не из IRAM, ждёт. Для контура управления с
периодом 2 мс это прямая остановка.

Измерено на этапе v0.5, когда запись выполнялась синхронно из потока Refloat:

```
максимум периода контура во время сохранения конфигурации: 13 904 мкс
```

Почти 14 мс при номинале 2 — семь пропущенных итераций подряд. Пока мотор
заблокирован, это безвредно; во время езды — нет.

---

## 2. Решение

### Разделение по состояниям

| Состояние супервизора | Запись | Почему |
|---|---|---|
| `BOOT` | запрещена | подсистема хранилища ещё поднимается; счётчик загрузок пишется до старта контура, отдельным синхронным вызовом |
| `SELF_TEST` | запрещена | состояние подсистем ещё неизвестно |
| `DISARMED` | **разрешена** | тяги нет и быть не может, задержка контура безвредна |
| `READY` | запрещена | условия выполнены, система в шаге от активности |
| `ARMED`, `RUNNING` | запрещена | активный контур |
| `FAULT` | запрещена | неизвестно, корректна ли конфигурация в памяти; закреплять её на носителе опаснее, чем потерять |

Решение принимает `fc_supervisor_config_write_allowed()`. Проверка стоит в
`VESC_IF->store_eeprom_var()` и `store_backup_data()`, то есть **до всякого
обращения к носителю**. Refloat получает честный `false` и печатает свою
штатную ошибку.

### Отложенная запись

Даже в разрешённом состоянии realtime-задачи не выполняют запись сами:

```
Refloat  →  store_eeprom_var()  →  слово в ОЗУ + флаг dirty
                                         │
                        (≤150 мс либо явный запрос)
                                         ▼
                        задача fc_nvs, приоритет 3, ядро 0
                                         │
                            nvs_set_blob + nvs_commit
```

Задача хранилища — единственное место в прошивке, где после загрузки
происходит запись во flash. Она живёт на ядре 0, тогда как весь контур — на
ядре 1.

Почему не коммит на каждое слово: Refloat пишет конфигурацию 80 словами
подряд (`main.c:1073`). Восемьдесят отдельных `nvs_commit` износили бы flash
без всякой пользы. Слова копятся в ОЗУ, на носитель уходит один blob из 128
слов фиксированной длины.

---

## 3. Что это дало

| | v0.5: запись из потока Refloat | v0.6A: отдельная задача на ядре 0 |
|---|---|---|
| Длительность операции | не измерялась | **5.1 мс** (`nvs_set_blob` + `nvs_commit`) |
| Максимум периода контура | **13 904 мкс** | **2767 мкс** |
| Максимум периода `refloat_thd` | — | 3920 мкс |
| Максимум времени итерации `refloat_thd` | — | 1047 мкс |

Остановка контура на 14 мс исчезла. Операция с flash по-прежнему заметна —
она видна как выброс до 1 мс в потоке Refloat, — но разбита на короткие
интервалы и вынесена из realtime-пути.

---

## 4. Проверено на живой плате

### Разрешённая запись переживает сброс

```
DISARMED
  config          test param = 0.700, запись разрешена
  persist         0.700 -> 0.800, set_cfg вернул true
                  NVS: сохранено 128 слов за 5704 мкс (коммит #2)
--- аппаратный сброс ---
  boot #: 65
  config test value = 0.800
```

### Запрещённая запись отклоняется и не останавливает контур

```
ready           переход в READY выполнен, запись конфигурации запрещена
timing-reset
persist         политика записи сейчас ЗАПРЕЩАЕТ (supervisor READY)
                записей принято 1, отклонено 1
refloat         Error: Failed to write config.
timing          control: max 2766 мкс, late 3.46 %  ← обычный джиттер, не 14 мс
--- аппаратный сброс ---
  config test value = 0.800   ← значение НЕ изменилось: записи не было
```

Три факта здесь важны одновременно: Refloat получил явную ошибку, контур не
встал, и на носителе действительно ничего не изменилось.

Отдельно стоит понимать: в `READY` изменение применяется **в оперативной
памяти** (значение стало 0.900) и действует до перезагрузки, но на носитель не
попадает. Это соответствует семантике VESC, где запись в EEPROM тоже может не
удаться, и Refloat такую ситуацию обрабатывает сам.

---

## 5. Устройство хранилища

* Носитель: раздел NVS, namespace `floatcore`, ключ `eeprom`.
* Формат: 128 слов по 32 бита одним blob фиксированной длины. Длина не должна
  меняться при обновлении прошивки, иначе старая запись перестанет читаться.
* Слова 0…79 принадлежат Refloat (эмуляция `eeprom_var`), 100 — счётчик
  загрузок платформы, остальные в запасе.
* Незаписанное слово читается как `0xFFFFFFFF` — как стёртая ячейка EEPROM на
  VESC. На первом старте Refloat корректно уходит на значения по умолчанию.
* Refloat в NVS не пишет и о ней не знает: он видит только контракт
  `read_eeprom_var`/`store_eeprom_var`.

---

## 6. Что осталось

1. **Отложенная запись пока не имеет очереди с ответом.** Refloat получает
   `false` немедленно; варианта «принято, будет записано позже» нет. Для UI
   этого достаточно, для будущего протокола может понадобиться статус `busy`.
2. **Счётчик загрузок пишется синхронно** в `app_main` до старта контура. Это
   единственный синхронный коммит после загрузки, и он безопасен по времени,
   но при появлении мотора его надо будет пересмотреть.
3. **Износ flash не отслеживается.** Счётчика циклов записи нет.
