# Драйвер ICM-20948

Сырой драйвер физического IMU: `platform/esp32/drivers/icm20948.{h,c}`.

Все номера регистров и значения взяты из datasheet InvenSense **ICM-20948,
DS-000189 rev 1.6**, раздел указан у каждого решения. «Оставить по умолчанию»
нигде не используется как аргумент.

**Важное ограничение этапа v0.6A:** данные драйвера **не передаются Refloat**.
Контур работает от mock-IMU. Причина — в §7.

---

## 1. Железо

Определено на живой плате, а не принято по названию модуля:

| Параметр | Значение | Чем подтверждено |
|---|---|---|
| Датчик | ICM-20948 | `WHO_AM_I` = `0xEA` (DS-000189 §7.1) |
| Шина | I2C | скан 0x08…0x77 дал ровно один отклик |
| Адрес | **0x68** | то есть вывод AD0 притянут к земле |
| SDA / SCL | GPIO21 / GPIO22 | задано монтажом |
| Питание | 3.3 В | задано монтажом |
| Прерывание DRDY | не подключено | будет нужно в v0.6B |

## 2. Что настраивается при старте и почему

| Параметр | Значение | Обоснование |
|---|---|---|
| Частота I2C | **400 кГц** | верхний предел ICM-20948 (§11.3, «I2C fast mode»). При 100 кГц транзакция на 14 байт занимает около 1.4 мс — сопоставимо с периодом контура 2 мс |
| Сброс | `PWR_MGMT_1.DEVICE_RESET`, пауза 100 мс | известное состояние независимо от того, что делал предыдущий запуск прошивки. §10 «Power-on reset time» |
| Пробуждение | `PWR_MGMT_1 = 0x01`, пауза 40 мс | после сброса взведён бит `SLEEP`, датчик отдаёт нули. `CLKSEL = 1` — «auto select best available»: PLL гироскопа вместо внутреннего осциллятора. §10 «Gyroscope start-up time» 35 мс |
| Оси | `PWR_MGMT_2 = 0x00` | ни один из шести каналов не отключён |
| Шкала акселерометра | **±4 g** (8192 LSB/g) | ±2 g насыщается уже на умеренных ударах колеса о неровность; насыщение ломает оценку ориентации сильнее, чем потеря половины разрешения. ±8 g отдаёт разрешение без нужды. §3.2 |
| Шкала гироскопа | **±500 °/с** (65.5 LSB/(°/с)) | при балансировке доска вращается быстрее 250 °/с на резких манёврах и при падении, а насыщение — прямая потеря управления. ±2000 °/с дало бы 16.4 LSB/(°/с) — вчетверо хуже там, где как раз и работает контур. §3.1 |
| Частота выдачи | **562.5 Гц** (`SMPLRT_DIV = 1`) | ODR = 1125/(1+div), §7.1. Взято намеренно больше 500 Гц: датчик должен выдавать данные чаще, чем их забирает контур, иначе появляется риск прочитать тот же семпл. `div = 2` дал бы 375 Гц — медленнее контура |
| ФНЧ | `DLPFCFG = 0`, `FCHOICE = 1` | полоса 196.6 Гц (гироскоп) и 246.0 Гц (акселерометр). Обе ниже Найквиста для 562.5 Гц (281 Гц), то есть алиасинга нет, а фазовая задержка минимальна. `FCHOICE = 0` обошёл бы фильтр и дал полосу 12106 Гц — заведомо алиасинг. Более узкие полосы — уже тюнинг контура, запрещённый на этом этапе |
| Выравнивание | `ODR_ALIGN_EN = 1` | выдача обоих датчиков выравнивается по одному фронту (§7.2). Без этого они расходятся по фазе, и `dt` перестаёт быть общим для пары |
| I2C-мастер датчика | выключен (`USER_CTRL = 0`) | внешний магнитометр AK09916 не нужен: Refloat получает `mag = NULL` |

## 3. Контракт сырого семпла

```c
typedef struct {
    float accel_g[3];       // g, оси датчика X/Y/Z как подписаны на кристалле
    float gyro_dps[3];      // °/с, те же оси
    float temperature_c;    // °C
    int16_t raw[7];         // как пришло по шине, до пересчёта
    uint64_t timestamp_us;  // момент завершения транзакции, монотонный
    uint32_t sample_counter;
    bool valid;
} icm20948_sample_t;
```

Температура считается по формуле datasheet §8.2:
`TEMP_degC = TEMP_OUT/333.87 + 21`.

Все 14 байт читаются **одной транзакцией** начиная с `ACCEL_XOUT_H`. Разбивать
нельзя: между чтениями датчик обновит регистры, и оси окажутся из разных
семплов.

### Чего здесь нет и не будет на этом этапе

Никаких перестановок осей, инверсий знаков, вычисления pitch/roll, калибровки
и фильтрации. Драйвер отдаёт то, что измерил датчик, в его собственной системе
координат. Привязка к осям доски отложена — см. §7.

## 4. Диагностика

Слой `compat/safety/fc_imu_health.{h,c}` — платформенно-нейтральный, ничего не
знает ни о модели датчика, ни о монтаже. Состояния:

```
NOT_INITIALIZED → OK → READ_ERROR | TIMEOUT | STALE | STUCK | INVALID
```

| Проверка | Порог | Откуда |
|---|---|---|
| Конечность значений | `isfinite()` | — |
| Модуль ускорения, максимум | `шкала × √3 × 1.05` = 7.3 g при ±4 g | физический потолок при насыщении всех трёх осей плюс 5 % на разброс чувствительности |
| Модуль ускорения, минимум | 0.25 g | отделяет «датчик что-то меряет» от нулей, которые ICM-20948 выдаёт во сне. **Политика FloatCore** |
| Угловая скорость | `шкала × 1.02` | полная шкала плюс запас |
| Монотонность времени | строгая | обратный ход означает порчу источника времени |
| Зависание | 5 одинаковых семплов подряд | у живого датчика младшие разряды шумят, но одиночное совпадение возможно. **Политика FloatCore** |
| Протухание | 40 мс (20 периодов) | **Политика FloatCore** |
| Потеря связи | 200 мс (100 периодов) | **Политика FloatCore** |

Пороги правдоподобия следуют за настройкой драйвера
(`fc_imu_health_config_for()`): при ±4 g порог от шкалы ±2 g отвергал бы
валидные данные.

## 5. Измерения на живой плате

За 62 секунды непрерывного чтения на 500 Гц:

```
транзакции  ok=31406  failed=0
            средняя 630 мкс, худшая 1141 мкс
health      OK, семплов 31434, ошибок 0, stuck 0, stale 0, timeout 0
покой       acc +0.358 +0.008 +0.926 g  |a| = 0.992
            gyro +0.79 +0.72 -0.24 °/с, 28.9 °C
```

Что здесь стоит отметить:

* **`|a| = 0.992` без всякой калибровки** — отклонение 0.8 %. При шкале ±2 g
  тот же датчик давал 1.033…1.045 (отклонение 3–4 %): у разных шкал разные
  заводские калибровочные коэффициенты. Это наблюдение, а не повод что-то
  подкручивать: калибровка на v0.6A запрещена.
* **Нулевое смещение гироскопа 0.2…1.1 °/с** — штатный zero-rate offset.
* **Транзакция 630 мкс** заметно больше теоретических 340 мкс для 136 бит на
  400 кГц: остальное — накладные расходы драйвера I2C (семафор, прерывание).
  Влияние на тайминг контура разобрано в `realtime_timing.md` §3, гипотеза 4.
* **Датчик не горизонтален**: гравитация распределена между X и Z, наклон
  около 21°. Модуль закреплён временно, и это ровно та причина, по которой
  привязка осей отложена.

## 6. Восстановление залипшей шины

Ситуация штатная и воспроизводимая: если ESP32 сбрасывается посреди чтения,
датчик остаётся в середине выдачи байта и удерживает SDA в нуле. Мастер после
этого не может выдать даже START — контроллер сообщает `I2C hardware timeout`,
а GPIO помечаются как занятые.

Наблюдалось на живой плате: примерно **одна загрузка из трёх** после сброса во
время активного обмена.

Лечение стандартное: вручную выдать до девяти тактов SCL, чтобы ведомый
дотолкал свой байт и отпустил SDA, затем сформировать условие STOP. Одного
цикла оказалось мало — инициализация повторяется до трёх раз с паузой 20 мс.

Проверено: **пять подряд циклов сброса**, датчик поднялся во всех пяти.

## 7. Что отложено до финального монтажа

> **DEFERRED UNTIL FINAL MECHANICAL INSTALLATION**

Корпус электроники не собран, и положение датчика относительно доски пока не
зафиксировано. Поэтому отложено:

1. **Привязка осей датчика к осям доски** — какая ось даёт pitch, какая roll,
   какие знаки.
2. **Ориентация модуля** — матрица поворота, аналог `CFG_PARAM_IMU_rot_*`.
3. **Передача реальных данных в Refloat** через `VESC_IF->imu_*`.
4. **Проверка pitch/roll** ручным наклоном с эталоном.
5. **Включение реального IMU в контур балансировки** и его отказов в активную
   защиту.
6. **Калибровка**: смещения акселерометра, нулевое смещение гироскопа,
   ноль pitch/roll доски, настройка Mahony.

Подбирать знаки «пока UI не выглядит правильно» запрещено: каждая перестановка
и инверсия должна иметь физическое обоснование, полученное на собранном
корпусе.
