# Модель потоков, гонки и воспроизводимость сборки

## Часть I. Модель потоков Refloat

### 1. Кто вызывает код Refloat

Ровно четыре точки входа. Всё остальное — внутренние вызовы.

| Точка входа | Кем вызывается на VESC | Частота | Что делает |
|---|---|---|---|
| `imu_ref_callback(acc, gyro, mag, dt)` `main.c:734` | поток IMU прошивки, через `imu_set_read_callback` | частота семплирования IMU (832 Гц на VESC, 500 Гц у нас) | AHRS Refloat → PID → **команда мотору** |
| `refloat_thd(arg)` `main.c:767` | собственный поток, `spawn` | 500 Гц, задаётся `sleep_us` | телеметрия, футпады, автомат состояний, фолты, setpoint |
| `aux_thd(arg)` `main.c:1109` | собственный поток, `spawn`, приоритет −1 | 30 Гц | LED, одометр, **пересчёт коэффициентов фильтров** |
| `on_command_received(data, len)` `main.c:2400` | поток обмена прошивки, через `set_app_data_handler` | по запросу UI | ~25 команд, включая запись конфигурации |

Плюс редкие: `get_cfg`/`set_cfg`/`get_cfg_xml` (из потока обмена), `ext_bms`/
`ext_set_fw_version` (из потока LispBM), `stop_fun` (при выгрузке пакета).

### 2. Разделяемое состояние

Единственная структура `Data *d` (~несколько КБ), выделяемая одним `malloc` в `init()`.
**Ни одного мьютекса, семафора или атомарной операции во всём Refloat.**

Проверено: `grep -c 'mutex_\|sem_\|atomic' refloat-upstream/src/` → 0.

| Область `Data` | Пишет | Читает | Опасность |
|---|---|---|---|
| `imu`, `balance_filter`, `pid`, `balance_current` | IMU-callback | главный (`imu.roll`, `imu.balance_pitch`), aux (`imu_get_pitch` через `leds.c:973`) | низкая: одиночные 32-битные float, чтение атомарно |
| `motor_control.requested_current` | IMU-callback | IMU-callback | нет |
| `setpoint`, `setpoint_target*` | главный | IMU-callback (`pid_control`) | средняя: PID может взять setpoint посреди его обновления → один такт с промежуточным значением |
| `motor.*` (телеметрия, фильтры) | главный | IMU-callback (`pid_control`, лимиты тока) | **высокая**: структура многополевая, обновляется целиком в `motor_data_update()` |
| `state.*` | главный | IMU-callback, aux | средняя: несколько полей меняются не атомарно (`state`, `sat`, `stop_condition`) |
| `time.*` | главный | IMU-callback, aux | низкая |
| коэффициенты фильтров (`pid`, `booster`, `atr`, `torque_tilt`, `ema`, `biquad`, `sma`) | **aux** через `frequency_tracker_check` → `*_freq_update_reconfigure` | IMU-callback и главный | **высшая**: aux переписывает коэффициенты, пока контур ими пользуется |
| `motor.current_max/min`, `battery_current_*`, `speed_constant` | **aux** (`motor_data_refresh_motor_config`, 2 Гц) | IMU-callback (ограничение тока в `pid_control`) | **высокая**: лимит тока может быть прочитан в момент обновления |
| `float_conf` (вся конфигурация) | поток команд (`set_cfg`, `COMMAND_CFG_RESTORE`) | все три потока | **высшая**: конфигурация меняется целиком, без остановки контура |
| `leds` | aux | поток команд | средняя |
| `data_record` | IMU-callback (сэмплирование) и поток команд (выгрузка) | оба | средняя |

### 3. Какие допущения делает Refloat об однопроцессорности

Явно нигде не задокументировано, но код рассчитан на модель ChibiOS/STM32:

1. **Одно ядро с вытеснением.** Два контекста никогда не выполняются одновременно;
   возможна только чересполосица. Поэтому «порванным» может оказаться логическое
   состояние из нескольких полей, но не отдельное 32-битное поле.
2. **Выровненные 32-битные чтения/записи атомарны.** Все разделяемые поля — `float`,
   `int32_t`, `bool` или указатели.
3. **Нет переупорядочивания между контекстами.** Компилятор не может переносить обращения
   через вызов функции с неизвестными побочными эффектами (`VESC_IF->…`), а на одном ядре
   этого достаточно.
4. **Приоритеты фиксированы:** IMU-callback вытесняет главный поток, главный вытесняет aux.

Пункт 1 — ключевой. Именно он делает безопасной, например, ситуацию, когда `pid_control`
читает `d->motor.current_max` посреди `motor_data_refresh_motor_config()`: значение будет
либо старым, либо новым, но не мусором.

### 4. Что ломается на ESP32

| # | Проблема | Последствие | Мера |
|---|---|---|---|
| 1 | Два ядра дают **настоящий параллелизм** | Допущение 1 перестаёт действовать: главный поток может читать `d->motor` ровно в тот момент, когда IMU-callback… — а хуже, aux может переписывать коэффициенты фильтра, который в этот же момент вычисляется | **Пиннить все три задачи Refloat на одно ядро (core 1).** Тогда семантика идентична STM32 |
| 2 | `on_command_received` приходит из BLE/Wi-Fi стека на **core 0** | Запись `float_conf` параллельно контуру | Не вызывать обработчик напрямую: класть пакет в очередь и разбирать в задаче на core 1 |
| 3 | Компилятор агрессивнее переупорядочивает при `-O2`/LTO | Возможен вынос чтения общей переменной из цикла | Сборка контура без LTO между модулями Refloat; при сомнении — `-O1` |
| 4 | FPU на ESP32 — **пер-ядерный, с ленивым сохранением контекста** | Использование float в ISR портит контекст задачи | ISR только `vTaskNotifyGiveFromISR`; вся арифметика — в задачах |
| 5 | Стек, запрошенный Refloat (`spawn(..., 1536, ...)`) | Переполнение стека на Xtensa | Масштабировать в реализации `spawn` ×4…×8; включить проверку переполнения |
| 6 | Wi-Fi/BLE берут длинные критические секции на core 0 | Джиттер, если контур на том же ядре | Радио строго на core 0, контур строго на core 1 |

### 5. Предлагаемая архитектура FreeRTOS

```
┌─ Core 1 — «детерминированное ядро» ───────────────────────────────┐
│  imu_task           prio 24   по DRDY ICM-20948, 500 Гц           │
│                               → imu_ref_callback() → CAN TX       │
│  refloat_main       prio 22   refloat_thd(), 500 Гц               │
│  supervisor         prio 25   100 Гц, независимый контроль         │
│  can_rx             prio 20   разбор STATUS 1..6 в двойной буфер   │
│  refloat_aux        prio 10   aux_thd(), 30 Гц                     │
│  cmd_task           prio  8   разбор пакетов UI из очереди         │
└───────────────────────────────────────────────────────────────────┘
┌─ Core 0 — «всё остальное» ────────────────────────────────────────┐
│  BLE / Wi-Fi стек, логирование, телеметрия наружу                  │
│  приём пакетов UI → очередь в cmd_task (core 1)                    │
└───────────────────────────────────────────────────────────────────┘
```

Обоснование отличий от наброска в ТЗ:

* **`can_rx` перенесён на core 1.** В ТЗ он был на core 0. Но телеметрию читает главный
  поток Refloat без синхронизации; держа писателя и читателя на одном ядре, мы сохраняем
  исходную семантику. Стоимость — единицы процентов загрузки ядра.
* **`cmd_task` на core 1.** Обработчик команд пишет `float_conf`, который читают все
  потоки. Приём байтов остаётся на core 0, разбор — на core 1.
* **Добавлен `supervisor` с приоритетом выше контура.** Он единственный, кто снимает тягу:
  сценарии 6–10 показали, что сам Refloat этого не делает ни при пропаже IMU, ни при
  фолте ESC, ни при разрушении фильтра NaN-ом.
* **Двойная буферизация снимка телеметрии** вместо мьютекса: `can_rx` заполняет неактивный
  буфер и переключает индекс одной 32-битной записью. Refloat читает согласованный снимок,
  блокировок в контуре нет.

Более безопасная альтернатива, если измерения покажут нехватку одного ядра: вынести на
core 0 только `can_rx` с двойной буферизацией (она корректна и при параллелизме), оставив
на core 1 все три потока Refloat. Разносить сами потоки Refloat по ядрам нельзя ни при
каких условиях.

### 6. Как это проверено

`tests/host` реализует ровно эту модель: планировщик mock-платформы гарантирует, что в
любой момент выполняется **только один** контекст Refloat, а `imu_ref_callback`
вызывается лишь когда обе задачи припаркованы. Задача считается припаркованной, только
если она спит **и** её срок пробуждения ещё не наступил — без этого условия тест
возобновлялся раньше, чем успевала отработать задача, которой пора просыпаться
(эта ошибка была допущена и исправлена; до исправления сценарии 7 и 8, идентичные по
коду, давали разный результат).

Итог: 4 прогона подряд дают побитово одинаковый вывод.

### 8. Генерация конфигурационных файлов

`src/conf/confparser.{c,h}`, `confxml.{c,h}`, `conf_default.h` не хранятся в репозитории
Refloat — их порождает `vesc_tool --xmlConfToCode` из `src/conf/settings.xml`.
Это зависимость сборки от GUI-бинарника, непригодная для CI.

Поэтому написан `tools/gen_conf.py`. Формат выведен из эталонных файлов, сгенерированных
VESC Tool (`refloat-upstream/vesc_pkg_lib/examples/config/conf/`), и воспроизводит их
структуру:

| `type` | `vTx` | Сериализация |
|---|---|---|
| 1 (double) | 7 | `buffer_append_float16(x, vTxDoubleScale)` |
| 1 (double) | 9 | `buffer_append_float32_auto(x)` |
| 2 (int) | 1 / 2 / 3 | `uint8` / `int8` / `buffer_append_uint16` |
| 4 (enum), 5 (bool) | — | один байт |

Команда:

```bash
python3 tools/gen_conf.py \
    --settings refloat-upstream/src/conf/settings.xml \
    --out build/gen \
    --version "$(cat refloat-upstream/version)" \
    --package-name "$(cat refloat-upstream/package_name)" \
    --git-hash "$(git -C refloat-upstream rev-parse --short=8 HEAD)"
```

Результат для v1.3.0: 172 параметра, 282 байта сериализованной конфигурации
(лимит Refloat — 320), confxml 27 463 байта.

**Граница применимости.** Сигнатура конфигурации считается нашим алгоритмом (CRC32 по
описанию параметров) и не совпадает с сигнатурой VESC Tool. Для host-тестов это неважно:
и писатель, и читатель — один бинарник. Для прошивки, которая должна принимать
конфигурацию от VESC Tool, источником истины остаётся зафиксированная версия `vesc_tool`;
сгенерированные ею файлы следует завендорить и сверять хешем. Это риск R-12.

### 9. Ограничения сборки, выявленные на практике

| Ограничение | Причина | Решение |
|---|---|---|
| **Минимум `-O1`** | `src/time.h` объявляет функции как C99 `inline` без внешнего определения. На `-O0` они не инлайнятся и не находятся линковщиком | `-O1` в Makefile; на устройстве `-Os`, как в upstream |
| `-include stddef.h` | `src/conf/buffer.c` использует `size_t`, полагаясь на транзитивное подключение из заголовков newlib | флаг сборки, не патч |
| `-fsingle-precision-constant` | double-литералы в контуре баланса; на ESP32 double эмулируется программно | флаг (clang его не поддерживает и в host-сборке пропускается автоматически) |
| Изоляция `time_t` | `src/time.h` объявляет `typedef uint32_t time_t`, конфликтуя с libc | заголовки Refloat не смешивать с системными в одной единице трансляции; см. `tests/host/harness/refloat_facade.h` |
| Исключить `src/led_driver.c` | регистры TIM/DMA STM32 | своя реализация того же `led_driver.h`; `st_types.h`-заглушка позволяет **не менять** upstream-заголовок |
| Имя объектного файла | у Refloat и у харнесса есть `main.c` | файл раннера назван `runner.c` |

### 10. Docker

```bash
docker build -t refloat-host -f Dockerfile .
docker run --rm refloat-host          # прогон всех сценариев
```

`Dockerfile` фиксирует Debian bookworm, gcc и Python 3.11; конфигурационные файлы
генерируются внутри образа, поэтому результат не зависит от машины разработчика.

### 11. Команды

```bash
git submodule update --init            # зафиксировать upstream на 47a2c5ce
make -C tests/host gen                 # сгенерировать conf/* из settings.xml
make -C tests/host                     # собрать
make -C tests/host test                # прогнать 10 сценариев
build/host/refloat_host_tests -v       # с логами Refloat
build/host/refloat_host_tests "NaN"    # один сценарий по подстроке имени
```
