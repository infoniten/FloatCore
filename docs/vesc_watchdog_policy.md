# Сторожевой таймер команд мотору: как он работает у VESC и какой нам нужен

Документ этапа v0.7C. Политика **спроектирована и проверена на host**;
конфигурация ESC не менялась. Реализация проверок —
`compat/safety/fc_command_watchdog.{h,c}`, тесты — `tests/safety/test_motor_prep.c`.

---

## 1. Что делает VESC, когда команды перестают приходить

Разобрано по исходникам `vedderb/bldc`, ветка `release_6_06`, файл
`timeout.c` — ровно та версия, что стоит на стенде.

```
timeout_init()          timeout_msec = 1000 по умолчанию,
                        поток Timeout создаётся с NORMALPRIO

timeout_reset()         запоминает момент последней команды;
                        вызывается КАЖДЫМ обработчиком SET_* по CAN и по UART
                        (comm_can.c:1590, 1601, 1607, 1613, 1619, 1798…1816)

поток Timeout           просыпается КАЖДЫЕ 10 мс:
                            chThdSleepMilliseconds(10)

срабатывание            if (timeout_msec != 0 &&
                            прошло больше timeout_msec) {
                            mc_interface_release_motor_override();
                            mc_interface_unlock();
                            для ОБЕИХ половин:
                                mc_interface_set_brake_current(timeout_brake_current);
                            has_timeout = true;
                        }
```

Четыре вывода, каждый с последствием:

**1. Дискретность — 10 мс.** Поток просыпается раз в тик, поэтому фактическое
срабатывание округляется вверх до тика. Значения меньше 20 мс на этом железе
бессмысленны, и проверка политики их отвергает.

**2. `timeout_msec = 0` отключает проверку целиком.** Условие звучит как
`timeout_msec != 0 && прошло больше`. Ноль читается как «строже некуда», а
означает «никогда». Это ровно та ошибка, которую легко сделать и невозможно
заметить, пока не понадобится. Проверка политики отвергает ноль отдельным
правилом с отдельным сообщением.

**3. Периодический STATUS таймер НЕ сбрасывает.** `timeout_reset()` зовут
только обработчики команд. Это правильно: STATUS — телеметрия, которую ESC
рассылает сам, и она ничего не говорит о том, жив ли контроллер. Значит
поддерживать сторожевой таймер «живым» одним лишь наблюдением за шиной
нельзя — нужны команды.

**4. `COMM_ALIVE` (30) сбрасывает таймер, ничего больше не делая**
(`commands.c:700`). Это штатный способ держать ESC «в готовности», не задавая
тока. На v0.7B он намеренно **не** попал в белый список: держать чужой
сторожевой таймер, не имея права давать команды, — это притворяться живым
контроллером, ничем не управляя.

## 2. Что происходит с мотором после срабатывания

```
mc_interface_set_brake_current(timeout_brake_current)
```

На стенде `timeout_brake_current = 0.0` на обеих половинах.

**Ноль означает выбег, а не торможение, и для балансировочной доски это
верно.** Затормозить под ногами водителя — значит бросить его вперёд;
отпустить — значит дать доске катиться, пока водитель сходит. Но значение
обязано быть осознанным, а не унаследованным, поэтому оно записано здесь и
входит в проверочный список перед первым подключением мотора.

Отдельно: у ESC есть **независимый аппаратный сторожевой таймер IWDG на
12 мс**, который следит за его собственными потоками FOC и CAN и
перезагружает микроконтроллер, если они встанут (`timeout.c`,
`IWDG_SetReload(140)`). К потере связи с FloatCore он отношения не имеет и
политикой не настраивается.

## 3. Цепочка целиком

```
контур FloatCore, 500 Гц
        │  каждые 2000 мкс
        ▼
Motor Gate ── единственная точка выхода
        │
        ▼
CAN_PACKET_SET_CURRENT ──► шина 500 кбит/с ──► обработчик на ESC
        │                                              │
        │                                     timeout_reset()
        ▼                                              │
поток Timeout ESC, тик 10 мс ◄─────────────────────────┘
        │
        │  молчание дольше timeout_msec
        ▼
set_brake_current(0.0) на обе половины ── выбег
```

## 4. Предлагаемая политика

Проверена `fc_command_watchdog_policy_valid()`; каждое число ниже нарушает
хотя бы одно правило, если его подвинуть.

| Параметр | Значение | Почему так |
|---|---|---|
| Темп команд | **500 Гц** (2000 мкс) | темп контура: одна принятая выборка IMU — одна команда |
| Допуск на пропуски | **4 подряд** (10 мс) | переживает единичный всплеск на шине, не переживает отказ |
| Свой таймаут (Supervisor) | **20 мс** | FloatCore обязан снять тягу сам, раньше ESC |
| `timeout_msec` на ESC | **50 мс** | два тика запаса над своим таймаутом, вдвое меньше границы в 200 мс |
| `timeout_brake_current` | **0.0** (не менять) | выбег, а не торможение |

Худшее удержание последней команды при **полном** отказе FloatCore
(перезагрузка ESP32, когда ни один наш барьер не работает):

```
50 мс таймаут + 10 мс тик округления = 60 мс
```

### Правила, которые проверяются, и что каждое ловит

| Правило | Что ловит |
|---|---|
| `timeout_msec != 0` | «строгий ноль», отключающий защиту целиком |
| `timeout ≥ 2 тика ESC` | значения, которые всё равно округлятся, но добавят ложных срабатываний |
| `свой таймаут < таймаут ESC` | порядок барьеров: иначе собственные проверки не успевают ни на что повлиять |
| `период × (допуск+1) ≤ свой таймаут` | допуск, который не успевает реализоваться и потому существует лишь на бумаге |
| `таймаут ESC ≤ 200 мс` | слишком долгое удержание тяги после нашего отказа |

Текущее значение стенда — `timeout_msec = 1000` — отвергается последним
правилом: секунда удержания последней команды после отказа контроллера для
балансировочной доски недопустима.

## 5. Наблюдатель за потоком команд

`FcCommandStream` — конечный автомат с четырьмя состояниями, проверяемый на
host без платы и без мотора:

```
IDLE ──первая команда──► OK ──пропуск сверх допуска──► LATE ──свой таймаут──► LOST
                          ▲                                                    │
                          └──────────────── команда пришла ────────────────────┘
```

Важное свойство: **LOST запрещает, но OK не разрешает.** Возврат в OK
означает лишь, что поток команд восстановился; разрешение выхода на мотор —
дело Supervisor и Motor Gate, и оно требует ещё пятнадцати условий
(`motor_safety_architecture.md` §2).

## 6. Поведение в конкретных сценариях

| Сценарий | Кто реагирует первым | Через сколько | Что делает мотор |
|---|---|---|---|
| Потеря CAN | наш `fc_can_health` + поток команд | 20 мс | выбег |
| Отказ IMU | Supervisor | ~10 мс | FloatCore прекращает слать → выбег |
| Зависание контура | Supervisor | ~10 мс | то же |
| **Перезагрузка ESP32** | **только ESC** | **60 мс** | выбег |
| Отказ потока FOC на ESC | IWDG самого ESC | 12 мс | перезагрузка ESC |

Строка про перезагрузку ESP32 — главная причина, по которой `timeout_msec`
надо менять до первого подключения мотора: это единственный сценарий, где
никакой наш барьер не работает.

## 7. Что не решено

* **Число 50 мс проверено на непротиворечивость, но не на живой доске.**
  Слишком короткий таймаут даст ложные срабатывания на нагруженной шине,
  слишком длинный — лишние миллисекунды тяги после отказа. Подтвердить можно
  только измерением частоты пропусков команд на собранной машине.
* Темп 500 Гц добавит к шине около 500 кадров/с поверх нынешних 100. При
  500 кбит/с и кадре примерно 110 мкс это около 7 % загрузки — приемлемо, но
  измерить надо на настоящем трафике, а не на расчёте.
* `timeout_brake_current = 0.0` подтверждён как правильный по смыслу, но
  поведение выбега на вывешенном колесе не наблюдалось ни разу.
