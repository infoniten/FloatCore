# v0.7B — активный диагностический CAN: только запросы на чтение

Этап, на котором FloatCore впервые что-то передаёт в шину. Разрешены ровно
пять запросов, ни один из них не меняет состояние ESC, и ни одна команда
мотору не может быть собрана — не «запрещена», а отсутствует как код.

Мотор физически отключён весь этап. `MOTOR_CAPABLE` не создан. Motor Gate:
`allowed = 0`, `sent = 0`, backend `none (blocked)`.

Перечень типов пакетов и обоснование каждого разрешения — в
[`vesc_protocol_inventory.md`](vesc_protocol_inventory.md), раздел 5. Здесь —
архитектура, доказательства и то, что реально произошло на стенде.

---

## 1. Профиль сборки

Профиль CAN ортогонален профилю сборки и выбирается при сборке:

```
idf.py -DFLOATCORE_CAN_PROFILE=passive build       # TWAI listen-only
idf.py build                                       # active_diag, умолчание v0.7B
```

Три уровня передачи различаются намеренно и не сводятся к одному флагу:

| Макрос | Смысл | passive | active_diag | motor_capable |
|---|---|---|---|---|
| `FC_CAN_RX_AVAILABLE` | приём кадров | 1 | 1 | 1 |
| `FC_CAN_DIAG_TX_AVAILABLE` | read-only запросы | **0** | **1** | — |
| `FC_CAN_TX_AVAILABLE` | транспорт команд мотору | **0** | **0** | 1 |

`ACTIVE_DIAG` не переиспользует `FC_CAN_TX_AVAILABLE`: этот макрос означает
«мотору можно послать команду», и он обязан оставаться нулём весь v0.7B.
Несовместимость закреплена директивами `#error` в `fc_build_profile.h` —
собрать `ACTIVE_DIAG` вместе с моторным транспортом или с backend-ом вывода
нельзя.

Режим контроллера — следствие профиля, а не настройка:

```c
#if FC_CAN_DIAG_TX_AVAILABLE
#define FC_CAN_MODE TWAI_MODE_NORMAL
_Static_assert(FC_CAN_MODE == TWAI_MODE_NORMAL, "…");
#else
#define FC_CAN_MODE TWAI_MODE_LISTEN_ONLY
_Static_assert(FC_CAN_MODE == TWAI_MODE_LISTEN_ONLY, "…");
#endif
```

## 2. API уровня намерения, а не кадра

Обобщённой функции `can_send(id, data)` в проекте нет ни в одном профиле.
Наружу выставлено перечисление намерений:

```c
typedef enum {
    FC_CAN_DIAG_PING = 0,
    FC_CAN_DIAG_FW_VERSION,
    FC_CAN_DIAG_VALUES,
    FC_CAN_DIAG_MCCONF,
    FC_CAN_DIAG_APPCONF,
    FC_CAN_DIAG_REQUEST_COUNT
} FcCanDiagRequest;
```

Вызывающий код **не может назвать тип пакета** — его нет в сигнатуре. Номер
COMM тоже не приходит снаружи: он берётся из таблицы внутри `fc_can_diag.c`.

Единственная функция во всей прошивке, вызывающая `twai_transmit()`, —
`static bool transmit_whitelisted(const FcCanDiagFrame *, uint32_t)` в
`fc_can_bus.c`. Она статическая, то есть в таблице символов не внешняя, и
принимает уже собранный белым списком кадр.

## 3. Четыре уровня, на которых команда мотору невозможна

**1. Перечисление.** Моторного намерения в `FcCanDiagRequest` нет. Попытка
назвать его — ошибка компиляции «use of undeclared identifier».

**2. Отравленные имена.** `fc_can_diag.h` содержит

```c
#pragma GCC poison fc_can_diag_send_raw fc_can_diag_transmit_eid fc_can_diag_send_comm
#pragma GCC poison fc_can_set_current fc_can_set_duty fc_can_set_rpm fc_can_set_pos
#pragma GCC poison fc_can_set_current_brake fc_can_set_handbrake
```

Отравление действует **в обоих профилях**: разрешение передавать диагностику
не открыло обобщённую отправку.

**3. Проверка на этапе компиляции.** Белый список проверяется не только
функциями во время работы, но и `_Static_assert` в заголовке — то есть в
каждой единице трансляции, которая его включает:

```c
_Static_assert(!FC_CAN_TYPE_IS_MOTOR(FC_CAN_PACKET_PING), "…");
_Static_assert(!FC_CAN_TYPE_IS_MOTOR(FC_CAN_PACKET_PROCESS_SHORT_BUFFER), "…");
_Static_assert(FC_COMM_IS_READ_ONLY(FC_COMM_FW_VERSION), "…");
_Static_assert(FC_COMM_IS_READ_ONLY(FC_COMM_GET_VALUES), "…");
_Static_assert(FC_COMM_IS_READ_ONLY(FC_COMM_GET_MCCONF), "…");
_Static_assert(FC_COMM_IS_READ_ONLY(FC_COMM_GET_APPCONF), "…");
```

Макросная и функциональная формы белого списка сверяются между собой тестом
по всем 256 номерам: разъехаться незаметно они не могут.

**4. Таблица символов.** `tools/esp32_smoke.sh` определяет профиль по самому
образу и проверяет соответствующее:

```
профиль CAN в образе: active_diag
PASS  точка передачи статическая (локальный символ)
PASS  единственный внешний вход в передачу: fc_can_bus_diag_request
PASS  обобщённая отправка кадра: символов нет
PASS  моторные обёртки CAN из bldc: символов нет
PASS  регистрация backend-а мотора: символов нет
```

Сравнение двух сборок одного дерева:

| Символ | passive | active_diag |
|---|---|---|
| `twai_transmit` | отсутствует | `T` (драйвер, вызывается только из static-обёртки) |
| `transmit_whitelisted` | отсутствует | **`t`** — локальный |
| `fc_can_bus_diag_request` | отсутствует | `T` |
| `fc_can_transmit` | отсутствует | отсутствует |
| `fc_motor_gate_set_backend` | отсутствует | отсутствует |

### Негативные тесты компиляции

`make can-negative-test` — четыре проверки, успех каждой это **провал
компиляции**:

| Что пробуем | Профиль | Результат |
|---|---|---|
| обобщённая передача | passive | `attempt to use a poisoned identifier` |
| обобщённая передача | active_diag | `attempt to use a poisoned identifier` |
| моторная команда | active_diag | три ошибки: нет элемента перечисления, отравлено имя, нет обобщённой отправки |
| диагностическая передача | passive | `use of undeclared identifier 'FcCanDiagFrame'` |

## 4. Адресация

Собственный номер FloatCore — **50**, закреплён `_Static_assert` как
отличный от 118, 100 и 255.

Широковещательный адрес 255 **не собирается**: на него ответят обе половины
сразу, и разобрать, чей ответ пришёл, будет нечем. Запрос самому себе тоже
отвергается.

## 5. Темп

```
FC_CAN_DIAG_MIN_INTERVAL_US = 200000   // не чаще 5 запросов в секунду
```

Ограничитель отделён от транспорта и проверяется на host. Периодический
`STATUS` (50 Гц от каждой половины) остаётся основным источником телеметрии;
диагностический запрос — редкое событие. Попытки с шагом 2 мс проходят ровно
пять раз в секунду — это проверено тестом, а не заявлено.

Внутри диагностической сессии в UART не печатается ничего: известно, что
печать сама даёт опоздание контура, и мешать одно с другим нельзя.

## 6. Первая передача

Первым выбран `PING` — самый безобидный запрос из существующих. Обработчик,
`comm_can.c:1819-1825`, не делает ничего, кроме ответа:

```c
case CAN_PACKET_PING: {
    uint8_t buffer[2];
    buffer[0] = is_replaced ? utils_second_motor_id() : id;
    buffer[1] = HW_TYPE_VESC;
    comm_can_transmit_eid_replace(data8[0] | (CAN_PACKET_PONG << 8), buffer, 2, true, 0);
} break;
```

Ни обращения к `mc_interface_*`, ни `timeout_reset()`, ни записи.

Перед первой передачей прошивка печатает преамбулу — разрешение передавать
должно быть видно в логе, а не подразумеваться:

```
ACTIVE_DIAG_CAN: передача read-only запросов РАЗРЕШЕНА
  motor physically disconnected  (условие этапа v0.7B)
  Motor Gate backend             none (blocked)
  MOTOR_CAPABLE                  absent
  наш номер на шине              50
  TX whitelist                   PING, FW_VERSION, GET_VALUES, GET_MCCONF, GET_APPCONF
  темп не чаще                   5.0 запросов/с
  всё остальное                  недоступно на этапе компиляции
```

### Контрольная точка 1 — контроллер 118

```
запрос PING -> контроллер 118 (тип пакета 17, COMM-уровень не используется)
ответ 2 байт за 673 мкс
  ответил id=118, тип железа 0

0x00001232 ext n=1 dlc=2  VESC id=50  PONG   76 00
ошибок шины 0, потерь арбитража 0, неудач передачи 0
счётчик ошибок TX 0, RX 0, BUS_OFF 0
motor requested=6358 rejected(disarmed=6358) allowed=0 sent=0 backend=none (blocked)
```

`0x1232` = `50 | (18 << 8)` — ответ адресован именно нам; `76` = 0x76 = 118.

### Контрольная точка 2 — контроллер 100

```
запрос PING -> контроллер 100
ответ 2 байт за 522 мкс
  ответил id=100, тип железа 0
```

Половины отвечают независимо и различимы по номеру в теле ответа. Обращение к
одной не вызывает ответа другой.

## 8. Сверка USB и CAN

Сравнивались сырые блобы: эталон снят по USB на v0.7A (`vesc_audit_full.json`),
второй прочитан теперь через ESP32 по CAN.

| Запрос | Результат |
|---|---|
| `FW_VERSION` 118 и 100 | **совпадает байт в байт** |
| `GET_APPCONF` 118 и 100 | **совпадает байт в байт** |
| `GET_MCCONF` 118 | различаются 4 поля из 200 |
| `GET_MCCONF` 100 | различаются 4 поля из 200 |
| `GET_VALUES` | различается — живая телеметрия, совпадения и не ожидалось |

Различающиеся поля mcconf определены не на глаз, а разбором сериализатора
`confgenerator_serialize_mcconf()` из `release_6_06`. Проверка модели: сумма
размеров всех полей даёт **483 байта**, ответ — 484 (`[COMM id]` + 483), то
есть раскладка сошлась точно. Сигнатура `MCCONF_SIGNATURE = 2efd0142`
одинакова в обоих блобах, значит и версия раскладки та же.

Изменились только:

```
foc_offsets_current[0], foc_offsets_current[1]
foc_offsets_voltage[0..2]
```

Это **смещения датчиков тока и напряжения, которые VESC измеряет при каждом
включении**, а не настройки. Между двумя чтениями было снятие питания. Ни
один настраиваемый параметр не отличается.

Именованная сверка по требованию §11 — всё прочитано **через CAN**:

| Параметр | id 118 | id 100 | эталон USB (v0.7A) |
|---|---|---|---|
| FW / hw | 6.6 / 410 | 6.6 / 410 | 6.6 / 410 |
| UUID | `32002b0014…` | `2f002b0014…` | совпадают |
| `controller_id` | 118 | 100 | 118 / 100 |
| `l_current_max` | 25.0 A | 25.0 A | 25 A |
| `l_current_min` | −5.0 A | −5.0 A | −5 A |
| `l_in_current_max` | 15.0 A | 15.0 A | 15 A |
| `foc_motor_flux_linkage` | 0.1 | 0.1 | 0.1 |
| `si_motor_poles` | 14 | 14 | 14 |
| `foc_motor_r` | 0.3196 Ω | 0.3162 Ω | 0.3196 / 0.3162 |
| `foc_motor_l` | 0.730 мГн | 0.866 мГн | 0.730 / 0.866 |
| `si_battery_cells` | 3 | 3 | 3 |
| `app_to_use` | 3 (UART) | 3 (UART) | UART |
| `timeout_msec` | 1000 | 1000 | 1000 |
| `can_baud_rate` | 2 (500 к) | 2 (500 к) | 2 |
| `can_status_rate_1` | 50 Гц | 50 Гц | 50 Гц |

Путь через CAN возвращает ровно то же, что путь через USB. Конфигурация VESC
не изменялась ни в одном параметре — и изменить её этой сборкой нечем.

**Параметры мотора использованы только для сверки.** В Motor Gate и в путь
вывода они не попадают: пересчёт коэффициента (11.6 А/градус против 120 у
заглушек, `can_bringup.md`, раздел 10) остаётся оценкой по конфигурации, а число
полюсов по-прежнему не подтверждено физически — мотор отключён.

## 9. Здоровье узлов

Модель в `compat/can/fc_can_health.c` считает для каждого контроллера время
последнего кадра, последнего `STATUS`, последнего ответа на запрос, число
таймаутов и число падений доступности. Порог молчания — **500 мс**, то есть
25 подряд пропущенных `STATUS` при 50 Гц.

**Политика: наблюдение, а не управление.** Модуль не знает про Motor Gate, не
вызывается из него и не вызывает его. Ни одно значение отсюда не открывает
выход на мотор. Соблазн «оба VESC живы — можно ехать» создал бы второй путь к
моторной команде помимо Motor Gate, и проверять пришлось бы уже два места
вместо одного. Отсутствие VESC обязано только запрещать.

Поэтому входы Supervisor `esc_a_alive`, `esc_b_alive`, `can_fresh` на v0.7B
намеренно **не заполняются** из этой модели, и консоль это прямо говорит:
«наблюдение CAN есть, к разрешению не подключено».

Отдельное правило: таймаут диагностического запроса при живом `STATUS` узел
не хоронит. `STATUS` — независимый и более частый признак жизни, и молчание в
ответ на запрос при живом статусе означает проблему с запросом, а не с узлом.
Это разные диагнозы, и путать их нельзя.

## 10. Потеря CAN

Проверено программно, без выдёргивания проводов и без единой моторной
команды: `can-stop` останавливает и выгружает драйвер.

```
узлы CAN (порог молчания 500 мс):
  id=118 ожидаемый НЕДОСТУПЕН статусов 440 ответов 0 таймаутов 0 падений 1 молчит 5556 мс
  id=100 ожидаемый НЕДОСТУПЕН статусов 440 ответов 0 таймаутов 0 падений 1 молчит 5566 мс
все ожидаемые доступны: НЕТ

supervisor      DISARMED, faults none, motor output запрещён
motor           requested=6358 allowed=0 sent=0 backend=none (blocked)
запрос PING -> 118: ОТВЕТА НЕТ, запросов 0 (передача не состоялась)
```

Запрос при выгруженном драйвере отвергается **до** передачи, а не падает по
таймауту. После `can-start` шина поднимается в normal mode, оба узла
отвечают.

## 11. Политика BUS_OFF

Контроллер уходит в `BUS_OFF` сам, когда счётчик ошибок передачи переваливает
255, и сам оттуда не возвращается. Молча остаться выключенным хуже, чем
попробовать восстановиться: приём — единственный источник телеметрии, и его
потеря должна быть заметна и обратима.

Поэтому переход в `BUS_OFF` считается один раз на переход, запускается
`twai_initiate_recovery()`, и **число восстановлений считается отдельно от
числа переходов**. Если счётчики начнут расти, это будет видно, а не
спрячется за автоматическим перезапуском. Искусственно шину не коротили:
ошибочные состояния покрыты host-тестами.

За весь этап: `BUS_OFF 0`, восстановлений 0, `tx_error_counter 0`,
`rx_error_counter 0`, потерь арбитража 0, неудач передачи 0.

## 12. Низкотемповая сессия

70 секунд, один запрос в секунду, ротация `PING 118 → PING 100 →
FW_VERSION 118 → FW_VERSION 100`, без единого печатного символа внутри окна.

```
сессия завершена: успешно 70, без ответа 0
запросов 70, ответов 70, таймаутов 0
отказов передачи 0, ошибок CRC 0, отклонено списком 0, придержано 0
RTT максимум 2323 мкс

кадров 8856 за 86.0 с (103.0/с)
STATUS по-прежнему 50.1/с от каждой половины
ошибок шины 0, потерь арбитража 0, неудач передачи 0, приёма 0
счётчик ошибок TX 0, RX 0, BUS_OFF 0
```

103.0 кадра/с против 100.2 в пассиве — разница это наши `PONG` и кадры
ответов. Периодический `STATUS` не пострадал.

## 13. Тайминг

Три состояния, все измерены одинаково: чистое окно от сброса платы, ни одной
консольной команды внутри окна.

| | late | missed | p99 | p99.9 | max |
|---|---|---|---|---|---|
| A. пассивный CAN | 19.35 % | 1 | 2920 | 2920 | 4322 |
| B. active_diag без запросов | 18.40 % | 1 | 2880 | 2920 | 4381 |
| C. active_diag, 1 запрос/с | **18.12 %** | **1** | 2880 | 2920 | 4372 |

Активная диагностика контур не ухудшает: доля опозданий даже чуть ниже, чем в
пассиве, а единственный пропуск дедлайна воспроизводится во всех трёх
состояниях одинаково и объясняется загрузочным баннером в UART — известный
блокер, не связанный с CAN. Приписывать его шине было бы неверно.

`refloat_thd` во всех трёх состояниях: mean ≈ 2387 мкс, p99 3200, missed 1.

## 14. Что этап не сделал

* Мотор не подключался, детекция не выполнялась, число полюсов и параметры
  мотора **по-прежнему не подтверждены физически**.
* Конфигурация VESC не изменена ни в одном параметре; `timeout_msec` = 1000
  остаётся открытым вопросом и здесь не трогался.
* `MOTOR_CAPABLE` не создан, backend вывода на мотор не появился.
* Здоровье узлов CAN к разрешающей логике не подключено — сознательно.
* Квалификация шины I2C по-прежнему **PENDING** и с CAN не смешивается.
