# Безопасность прошивки FloatCore v0.5

Документ отвечает на один вопрос: **почему эта прошивка физически не может
сформировать команду мотору или кадр CAN через реализованный программный
путь.** Не «мы не будем», а «нечем».

Область действия — этап v0.5 (ТЗ). Как только появится реальный передатчик,
документ обязан быть переписан целиком.

---

## 1. Единственный путь от Refloat к мотору

Refloat запрашивает тягу ровно через пять функций `VESC_IF`
(`docs/vesc_if_contract.md` §1):

```
motor_control.c  →  VESC_IF->mc_set_current()
                    VESC_IF->mc_set_brake_current()
                    VESC_IF->mc_set_duty()
                    VESC_IF->mc_set_current_off_delay()
                    VESC_IF->timeout_reset()
```

Других способов у него нет: Refloat не знает ни про CAN, ни про GPIO, ни про
регистры. В нашей прошивке эти пять указателей ведут в
`platform/esp32/main/fc_vesc_if.c`, а оттуда — в
`platform/esp32/main/fc_motor_blocked.c`:

```
Refloat → VESC_IF->mc_set_current(I)
        → logical_motor_request_current(I)
        → block(FC_MOTOR_CMD_CURRENT, I)
              ├─ ++счётчик
              ├─ запомнить значение для диагностики
              └─ запись в лог не чаще 1 раза в секунду
        ← возврат. Всё.
```

Дальше кода нет. Функция `block()` — конец пути.

## 2. Четыре независимых причины, почему выхода нет

Каждая из них по отдельности достаточна.

### 2.1 В прошивке нет драйвера CAN

`fc_motor_blocked.c` не включает `driver/twai.h` и не вызывает ни одной
функции `twai_*`. Компоновщик это подтверждает — в `.elf` **ноль** символов
TWAI:

```
$ xtensa-esp32-elf-nm build/floatcore_esp32.elf | grep -i twai
(пусто)
```

Проверка автоматизирована и входит в `tools/esp32_smoke.sh` (шаг 4): наличие
хотя бы одного символа TWAI объявлено stop condition и валит прогон.

Единственные совпадения по подстроке `can_` в прошивке —
`can_engage` (функция состояния самого Refloat, к шине отношения не имеет),
`fc_can_backend_name` (наша строка для консоли) и `s_flash_op_can_start`
(внутреннее имя ESP-IDF).

### 2.2 Пины не сконфигурированы

Ни один GPIO не переводится в режим CAN: нет ни `gpio_set_direction`, ни
подключения к матрице периферии. `VESC_IF->io_set_mode()` и
`VESC_IF->io_write()` реализованы как заглушки, возвращающие `false`, — даже
пищалка не заводится.

### 2.3 Трансивера нет физически

К плате не подключён ни CAN-трансивер, ни VESC, ни мотор (ТЗ §19). Даже если
бы драйвер существовал и пины были настроены, на шине не было бы уровней.

### 2.4 Логический мотор всегда объявляет себя нерабочим

`logical_motor_healthy()` возвращает `false` всегда,
`logical_motor_telemetry()` отдаёт нулевой снимок с флагами
`LM_FAULT_ESC_A_TIMEOUT | LM_FAULT_ESC_B_TIMEOUT` и `esc_*_alive = false`.
Телеметрия не выдумывается: ESC нет — значит нули и явные флаги, а не
правдоподобные числа.

**Снять блокировку одним флагом или параметром нельзя.** Нужно написать новый
код передачи, включить компонент драйвера, настроить пины, подключить
трансивер. Это отдельный этап с отдельной ревизией.

## 3. Что видно в трассе

Блокировка не молчаливая. В serial (`ТЗ §6`):

```
W (2901) motor: blocked command: set_current(0.000) — всего 502, подавлено с прошлой записи 500
```

Логи ограничены по частоте: не чаще одного сообщения в секунду на каждый вид
команды, с указанием числа подавленных. Без этого контур на 500 Гц забил бы
UART полностью (при 115200 бод одна такая строка занимает около 9 мс).

Полные счётчики доступны в любой момент командой `safety`:

```
motor backend     blocked
can backend       unavailable (TWAI не инициализирован, трансивер не подключён)
blocked total     30587
  set_current     30587 (последний запрос 0.000 A)
  set_brake       0
  set_duty        0
timeout_reset     30587
footpad           NONE — disengaged, как и требуется
```

Соотношение «одна команда на семпл IMU» совпадает с тем, что предсказывал
аудит и что показал host-харнесс: 30 587 команд за 60 с ≈ 500 Гц.

## 4. Footpad: почему доска считается неактивированной

Решение Refloat принимает так (`refloat-upstream/src/footpad_sensor.c:31`):

```c
bool adc1_on = config->fault_adc1 == 0.0f || adc1 > config->fault_adc1;
```

Датчик считается нажатым, если напряжение **выше** порога. Пороги по
умолчанию — 2.00 В (`settings.xml`, `fault_adc1`/`fault_adc2`). Платформа
отдаёт **0.00 В**, что ниже любого допустимого ненулевого порога из диапазона
0.01…3.30 В — это перебором проверено host-тестом.

Значение −1.0 В («пина нет на железе») намеренно не используется: оно тоже
ниже порога, но означало бы «канала не существует», а мы сообщаем «канал есть
и он отпущен».

**Отдельный опасный случай, который значением ADC не лечится.** Если порог
выставлен в 0, первая ветка условия делает зону нажатой **всегда**, при любом
напряжении. Поэтому фактическое состояние проверяется не по ADC, а по самому
Refloat: прошивка после старта печатает

```
[floatcore] footpad: NONE, adc 0.00/0.00 V, пороги 2.00/2.00 V -> DISENGAGED (ok)
```

и логирует ошибку, если состояние окажется не `FS_NONE`. Это прямая проверка
stop condition из ТЗ («mock ADC приводит Refloat в engaged state»).

## 5. Mock IMU: почему покой — это покой

Контракт выведен из upstream, а не назначен (подробности —
`platform/esp32/main/fc_imu_mock.c`):

| Величина | Значение | Обоснование |
|---|---|---|
| `imu_get_roll/pitch/yaw` | 0 рад | `imu.c:36-40` оборачивает в `rad2deg()` |
| `acc` в callback | (0, 0, +1) g | `balance_filter.c:100` при единичном кватернионе даёт направление гравитации +Z; любой другой вектор заставил бы Mahony доворачивать доску |
| `gyro` | (0, 0, 0) рад/с | `balance_filter.c:114-125` интегрирует `q += 0.5*q*g*dt` |
| кватернион | (1, 0, 0, 0) | покой |
| `dt` | реальный интервал `esp_timer` | `frequency_tracker`/`latency_tracker` считают частоту по нему |

Результат на плате: `pitch/roll 0.000 / 0.000 deg` и `imu 500.0 Hz` по
счётчикам самого Refloat.

`imu_startup_done()` возвращает `false` первые 1.5 секунды — как время
калибровки гироскопа на VESC. Пока он `false`, Refloat остаётся в
`STATE_STARTUP`, то есть в безопасном состоянии по умолчанию.

## 6. Радио выключено

`CONFIG_BT_ENABLED=n`, `CONFIG_ESP_WIFI_ENABLED=n` в `sdkconfig.defaults`.
Ни Wi-Fi, ни BLE не инициализируются, provisioning не делается, транспорт
VESC Tool на плату не переносился (ТЗ §18). Ядро 0 остаётся свободным, контур
целиком на ядре 1.

---

## 7. Консоль не умеет управлять

`platform/esp32/main/fc_console.c` не имеет доступа ни к одной функции,
способной что-то запросить у мотора. Команд `set_current`, `set_duty`,
`set_rpm`, `motor_test` нет и добавить их нечем: единственная точка входа в
мотор — `logical_motor_*`, а она заблокирована (§2).

Из всех команд состояние меняет только одна — `persist`, и она пишет
косметический параметр яркости LED ради проверки хранилища.

Две команды требуют явного подтверждения прямо в имени:
`wdtest-confirm` (останавливает контур на 8 с, чтобы показать срабатывание
watchdog) и `crashtest-confirm` (вызывает panic, чтобы показать backtrace).
**Обе обязаны быть удалены из любой сборки, способной управлять мотором.**

## 8. Что остаётся небезопасным и должно быть решено до подключения VESC

Честный список того, чего в v0.5 ещё нет:

1. **Supervisor не реализован.** Архитектура (`docs/esp32_architecture.md` §5)
   предполагает независимый слой между `mc_set_*` и CAN, который снимает тягу
   при протухшей телеметрии, NaN, расхождении ERPM и зависании контура. Сейчас
   его роль выполняет само отсутствие передатчика.
2. **Джиттер контура ±0.8 мс не локализован** (см. bring-up §5). До подачи
   тока источник надо найти.
3. **Запись во flash стопорит контур на ~14 мс** (bring-up §9). Нужен запрет
   записи конфигурации во время движения.
4. **`CONFIG_ESP_TASK_WDT_PANIC` выключен.** Для сборки с мотором логика
   обратная: при срыве контура лучше перезагрузиться, чтобы тяга снялась по
   watchdog самого VESC.
5. **Настоящий IMU не подключён**, детекции зависших семплов нет.
6. **Диагностические команды `*-confirm`** должны исчезнуть.
