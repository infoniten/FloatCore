# Изменение конфигурации ESC перед первым подключением мотора

Этап v0.7D.1. Мотор физически отключён, детекция не выполнялась, моторных
команд не передавалось. Записано шесть параметров, каждый — отдельной
операцией с побайтовой проверкой после неё.

---

## 1. Как писалось и почему именно так

**У FloatCore права записи в ESC нет и не появится.** `COMM_SET_MCCONF` и
`COMM_SET_APPCONF` не входят в белый список передачи и не могут быть собраны
(`vesc_protocol_inventory.md` §5.5). Поэтому запись выполнял человек в VESC
Tool по USB, а FloatCore выступал независимым контролёром: читал результат
через CAN и сравнивал с резервной копией.

Разделение получилось полезным само по себе. Записывает один путь, проверяет
другой — ошибка в одном не маскируется тем же самым в другом.

Рассматривался вариант с собственным инструментом записи, который менял бы
один байт в уже прочитанном блоке. Он дал бы побайтовое доказательство по
построению, а не по факту, но потребовал бы завести в репозитории код записи
в ESC. Решение владельца: **не заводить**, писать штатным VESC Tool.

## 2. Резервные копии

Сняты до любой записи, через CAN, обе половины, в двух формах:

Хранятся в репозитории: `build/` в `.gitignore`, а копия, существующая только
на одном ноутбуке, — не копия.

```
backups/vesc/v0.7d1/
  mcconf_id118.bin   484 Б   сигнатура 2efd0142
  appconf_id118.bin  279 Б   сигнатура 7d217eb8
  mcconf_id100.bin   484 Б   сигнатура 2efd0142
  appconf_id100.bin  279 Б   сигнатура 7d217eb8
  fw_id118.bin        32 Б   6.6 / hw 410 / UUID 32002b00…
  fw_id100.bin        32 Б   6.6 / hw 410 / UUID 2f002b00…
  *.json                     те же байты в hex + разобранные поля
```

Инструмент — `tools/vesc_backup.py`, только чтение. Раскладка полей
разбирается **из исходника** `confgenerator.c` той же версии прошивки, а не из
переписанной руками таблицы: переписанная расходится с прошивкой молча.

Копия проверена обратным чтением с диска — совпадает.

**Перекрёстная сверка с USB** выполнена в человекочитаемом виде: экраны VESC
Tool (`App Settings`, `Motor Settings → Voltage / Advanced / FOC`) сверены с
копией, снятой через CAN. Совпали все проверенные поля, включая
`VESC ID`, `Timeout`, `Timeout Brake Current`, `CAN Baud`, `APP to Use`,
отсечки 34.0/31.0 и 41.5/42.0, `Min/Max Input Voltage`, `Max Duty`, а также
`R` и `L`, различающиеся у половин. Два независимых пути чтения дали одно и
то же.

### Процедура отката

1. Снять питание, отключить мотор физически (если он к тому времени
   подключён).
2. VESC Tool по USB, подключиться к половине.
3. `Motor Settings` → загрузить `mcconf_idNNN` из резервной копии → Write.
   `App Settings` → то же с `appconf_idNNN`.
4. Перечитать через CAN и сверить с `.bin` побайтово
   (`tools/vesc_diff.py`).

Файлы `.bin` — это ответы `COMM_GET_*` целиком, включая первый байт с номером
пакета. Для загрузки в VESC Tool потребуется либо снять этот байт, либо
восстанавливать значения по разобранному `.json` вручную. Это неудобство, а
не препятствие: набор изменённых полей мал и перечислен ниже.

## 3. Что записано

| Устройство | Конфиг | Параметр | Было | Стало |
|---|---|---|---|---|
| ESC 118 | mcconf | `si_battery_cells` | 3 | **10** |
| ESC 100 | mcconf | `si_battery_cells` | 3 | **10** |
| ESC 118 | appconf | `timeout_msec` | 1000 | **50** |
| ESC 100 | appconf | `timeout_msec` | 1000 | **50** |
| FloatCore | Refloat cfg | `tiltback_lv` | 3.0 В/яч | **3.6 В/яч** |
| FloatCore | Refloat cfg | `tiltback_hv` | 4.3 В/яч | **4.0 В/яч** |

Не менялись и менять не предлагалось на этом этапе:
`timeout_brake_current` (0.0 — выбег, и это правильно), пределы тока,
`l_in_current_min`, `app_to_use`, `si_wheel_diameter`, `si_gear_ratio`,
параметры мотора, отсечки по напряжению.

## 4. Побайтовые доказательства

Инструмент — `tools/vesc_diff.py`. Сравниваются **сырые байты**, каждое
расхождение сопоставляется с именем поля по сериализатору и делится на три
категории: ожидаемое, runtime-значение, необъяснённое. Последнее означает
остановку.

```
mcconf  id=118   si_battery_cells   смещение 458     03   -> 0a     3 -> 10
mcconf  id=100   si_battery_cells   смещение 458     03   -> 0a     3 -> 10
appconf id=118   timeout_msec       смещения 8,9     03e8 -> 0032   1000 -> 50
appconf id=100   timeout_msec       смещения 8,9     03e8 -> 0032   1000 -> 50
```

Необъяснённых изменений — **ноль** во всех четырёх записях. Ни одна запись не
задела соседнюю половину и ни одна не тронула параметры мотора.

Уточнение к предсказанию: `timeout_msec` занимает смещения 6-9, но старшие
два байта в обоих значениях нулевые, поэтому фактически различаются два, а не
четыре.

### Единственная категория «шума»

`foc_offsets_current[0..2]` и `foc_offsets_voltage[0..2]` — смещения 282-297.
ESC перемеряет их при каждом включении, и между двумя чтениями с перерывом по
питанию они всегда различаются.

Случайный обрыв питания посреди работы дал этому независимое подтверждение:
изменились ровно эти шесть полей и ни одного другого. Классификация,
принятая на v0.7B, оказалась верной.

## 5. Порядок и одна неудача

Записи шли по одной, с проверкой после каждой. Порядок — по половинам
(118 cells → 118 timeout → переключение → 100 cells → 100 timeout) вместо
чередования из ТЗ: то же число записей и та же дисциплина проверки, но вдвое
меньше перетыканий USB.

**Вторая запись с первого раза не прошла.** `timeout_msec` остался 1000:
нажата была кнопка записи конфигурации мотора, а `timeout` живёт в
конфигурации приложения — это разные команды, `COMM_SET_MCCONF` и
`COMM_SET_APPCONF`. Побайтовая проверка поймала это сразу, до следующей
записи. Ровно то, ради чего проверка после каждой записи и требуется.

Отдельная ловушка при работе через CAN forwarding: VESC Tool пишет весь блок
из памяти интерфейса. Если переключиться на удалённую половину и записать, не
прочитав, туда уедет конфигурация локальной — вместе с её параметрами мотора.
Признак, по которому это видно заранее: у половин **разные** измеренные `R` и
`L` (0.3196 Ом / 730 мкГн против 0.3162 Ом / 866 мкГн), и после `Read`
интерфейс обязан показывать значения той половины, в которую собираются
писать.

## 6. Персистентность

Полный цикл питания: лабораторник выключен, USB отключён и от VESC, и от
ESP32, пауза больше десяти секунд, затем включение.

```
ESC 118   si_battery_cells 10   timeout_msec 50   timeout_brake_current 0.0
ESC 100   si_battery_cells 10   timeout_msec 50   timeout_brake_current 0.0
Refloat   tiltback_lv 3.60 В/яч   tiltback_hv 4.00 В/яч
```

Побайтовая сверка с резервной копией после цикла: изменения ровно те же
четыре, необъяснённых нет.

Случившийся ранее полусекундный провал питания за эту проверку **не
засчитан**: к моменту провала запись во flash могла не завершиться, и
подменять полный цикл брounout'ом ТЗ прямо запрещает. Штатная проверка
выполнена отдельно.

Дополнительно конфигурация Refloat пережила перепрошивку ESP32: `idf.py flash`
не стирает NVS, и после неё пороги остались 3.60 / 4.00.

## 7. Сторожевой таймер — конфигурационная проверка

Физически проверить нулевую тягу нельзя: мотор отключён. Проверен контракт.

```
timeout_msec           50 мс на обеих половинах
timeout_brake_current  0.0 (выбег, не торможение)
диагностическая сессия 30 запросов, 30 ответов, 0 таймаутов
шина                   7891 кадр за 77.7 с, ошибок 0, BUS_OFF 0
счётчики ошибок        TX 0, RX 0
```

`COMM_ALIVE` специально не посылался и в белый список не входит: держать чужой
сторожевой таймер живым, не имея права давать команды, значит отключить
защиту ровно тогда, когда она понадобится.

Диагностические запросы семантику таймаута не меняют — `timeout_reset()`
зовут только обработчики `SET_*`, а `GET_*` его не трогают
(`vesc_watchdog_policy.md` §1).

## 8. Какая половина — 118

Установлено **без единой моторной команды**.

`utils_second_motor_id()` возвращает `controller_id + 1` (`util/utils_sys.c:64`).
Наши номера — 118 и 100, и ни один не является соседом другого. Значит это не
две половины одного микроконтроллера через `HW_HAS_DUAL_MOTORS`.

Решающее свидетельство — UUID: `32002b001447333034353333` и
`2f002b001447333034353333` различаются в **первом** байте, тогда как механизм
двух моторов на одном МК прибавляет единицу к **последнему**
(`commands.c:246-248`). Это два разных микроконтроллера, связанных внутренней
шиной CAN.

Из v0.7A и подтверждено снова на v0.7D.1: при подключении USB локальной
половиной отвечает **118** (UUID `32002b00…`, `local` в списке CAN-Devices).

```
ID 118  =  половина с тем USB-разъёмом, которым пользовались всё время
ID 100  =  вторая, доступная через CAN forwarding
```

Остаётся одно: какой из двух фазных разъёмов принадлежит микроконтроллеру
118. Это вопрос разводки платы, и он решается **осмотром** — трассировкой от
разъёма USB к соседним фазным проводам. Моторной команды для этого не нужно.
Пункт остаётся открытым до визуального подтверждения перед v0.8A.

## 9. Что осталось не применённым

| Что | Значение | Когда применять |
|---|---|---|
| `l_current_max` | 25 → **5 А** | непосредственно перед первым прокрутом |
| `l_current_min` | −5 → **−3 А** | тогда же |
| `l_in_current_max` | 15 → **5 А** | тогда же |
| `l_in_current_min` | 0 → **−1 А** | тогда же |

Причина отложить одна: эти пределы относятся к конкретному физическому тесту.
Применять их за дни до него значит оставить машину в конфигурации, которая ни
для чего другого не предназначена, и забыть вернуть обратно.

`l_in_current_min = −1 А` — решение, принятое после разбора в
`motor_parameter_model.md` §9: при нуле раскрученное колесо нечем остановить
электрически. Один ампер в сборку 6 А·ч это C/6, а regen-отсечка 41.5-42.0 В
обрезает его до нуля на полной батарее. Двойная граница.

**Для езды это значение не годится** и будет другим. Политика первого
прокрута и рабочая политика — разные понятия.
