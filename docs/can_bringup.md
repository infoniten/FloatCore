# Пассивный подъём CAN и аудит Dual FSESC (v0.7A)

Этап, на котором впервые доказана физическая связь ESP32 с контроллерами
мотора, и сделано это **полностью пассивно**: ESP32 не отправила в шину ни
одного кадра и отправить не могла.

Параллельно снят read-only аудит живого Dual FSESC по его же протоколу.
Моторы физически отключены на всём протяжении этапа.

---

## 1. Топология USB

Определена заново, а не по старому имени порта: имена устройств на macOS не
стабильны.

| Устройство | Порт | VID / PID | Имя USB | Location |
|---|---|---|---|---|
| ESP32 | `/dev/cu.usbserial-3120` | 0x1A86 / 0x7523 | USB Serial (CH340) | 0x3120000 |
| VESC | `/dev/cu.usbmodem3041` | 0x0483 / 0x5740 | ChibiOS/RT Virtual COM Port, STMicroelectronics, s/n 304 | 0x130000 |

`ChibiOS/RT` — RTOS прошивки VESC, поэтому вторая строка не предположение.

## 2. Аудит VESC: как он снят

Своим клиентом протокола, `tools/vesc_audit.py`, без GUI VESC Tool.

Клиент устроен так, что отправить изменяющую команду им невозможно: список
разрешённых идентификаторов задан белым списком, и `request()` отказывается
кодировать всё, чего в нём нет. `COMM_SET_CURRENT`, `COMM_SET_MCCONF`,
`COMM_LISP_SET_RUNNING` и подобные в него не входят и попасть не могут.

Разбор конфигураций не угадан. Обе сигнатуры сошлись побитово:

| Блоб | Сигнатура с устройства | Источник схемы | Совпадение |
|---|---|---|---|
| mcconf, 483 Б | `0x2EFD0142` | `compat/vesc_protocol/generated/mcconf_schema_6_06.json` | да |
| appconf, 278 Б | `0x7D217EB8` | сгенерирована из `parameters_appconf.xml` VESC Tool 6.06 тем же `tools/gen_mcconf.py` | да |

Сырые ответы сохранены машинно-читаемо: `build/debug/vesc_audit_full.json`
(hex всех payload). Значения enum взяты из самого XML VESC Tool, а не по
памяти.

## 4. Топология CAN

| Параметр | Значение | Откуда |
|---|---|---|
| `controller_id` половины A | **118** | `COMM_GET_VALUES` и байт 4 блоба appconf — два независимых источника |
| `controller_id` половины B | **100** | `COMM_PING_CAN` вернул `[100]` |
| Скорость | **500 кбит/с** | `can_baud_rate = 2`, enum `CAN_BAUD_500K` из XML |
| Режим | **VESC** | `can_mode = 0`, enum `VESC` |
| Статус, группа 1 | **50 Гц**, маска `1` | `can_status_rate_1`, `can_status_msgs_r1` |
| Статус, группа 2 | 5 Гц, маска `0` — ничего не шлётся | `can_status_rate_2`, `can_status_msgs_r2` |

Отсюда предсказание, сделанное **до** включения приёма: на шине обязан быть
периодический трафик около 100 кадров/с — по 50 Гц от каждой половины, только
`CAN_STATUS`.

### Терминация

Первое измерение мультиметром на полностью обесточенной системе, на клеммах
Waveshare:

```
R(CANH, CANL) = 35.3 Ω
```

Стандарт ожидает 60 Ω — по 120 Ω на двух концах линии. На v0.7A это было
объяснено тремя одинаковыми терминаторами по 120 Ω (номинально 40 Ω).
**Эта гипотеза оказалась неверной** и разобрана в разделе 13: реальный
Dual FSESC сам по себе даёт не 60, а около 50–55 Ω, и никакая комбинация из
трёх резисторов по 120 Ω такого не даёт.

**На v0.7A резистор не тронут.** Приём при такой нагрузке оказался
безошибочным (§5), и выпаивать деталь без доказанной необходимости нельзя.

Но безошибочный приём — это работоспособность, а не квалификация, и путать их
нельзя:

```
CAN physical layer сейчас работает:
    500 кбит/с, ~100 кадров/с, ноль ошибок шины, ноль потерь приёма

CAN TERMINATION: PENDING HARDWARE REVIEW   (на момент v0.7A;
                                            закрыт в разделе 13)
```

## 5. Пассивный приём: что увидели

Прогон 89.5 с, от сброса платы, без вмешательства в консоль:

```
кадров            8974 за 89.5 с (100.2/с)
                  стандартных 0, расширенных 8974, RTR 0
DLC               8: все 8974
очередь           в очереди 0, потеряно 0, переполнений 0
ошибки            шины 0, потерь арбитража 0, неудач передачи 0, приёма 0
состояние         RUNNING
```

Идентификаторы:

| CAN ID | Формат | Контроллер | Тип | DLC | Частота | Данные |
|---|---|---|---|---|---|---|
| `0x976` | ext | **118** | `CAN_PACKET_STATUS` (9) | 8 | 50.1/с | все нули |
| `0x964` | ext | **100** | `CAN_PACKET_STATUS` (9) | 8 | 50.1/с | все нули |

Разбор не выведен из вида идентификатора, а сделан по формату из
`bldc/comm/comm_can.c`:

```c
// передача
controller_id | ((uint32_t) CAN_PACKET_... << 8)
// приём
uint8_t id = eid & 0xFF;
CAN_PACKET_ID cmd = eid >> 8;
```

Номера типов — из перечисления `CAN_PACKET_ID` в `bldc/datatypes.h`.
`CAN_PACKET_STATUS = 9`, отсюда `0x976 = (9 << 8) | 118` и
`0x964 = (9 << 8) | 100`.

Нулевые данные согласуются с содержимым `CAN_PACKET_STATUS`: ERPM (4 байта),
ток (2), duty (2). Мотор отключён, всё по нулям.

**Обе половины наблюдаются.** Наблюдаемая частота совпала с предсказанной по
конфигурации до десятых долей. Кадров, не разобранных как VESC, не было.
Команд мотору на шине нет — ни одного типа из списка `SET_*`.

## 6. Почему ESP32 не может ничего передать

Четыре независимых уровня, каждый проверяем:

1. **Профиль сборки.** `FLOATCORE_CAN_PASSIVE` даёт `FC_CAN_RX_AVAILABLE 1`
   при `FC_CAN_TX_AVAILABLE 0`, а их совместное включение запрещено
   `#error` в `fc_build_profile.h`.
2. **Отсутствие API.** Функции передачи не объявлены нигде. Сверх того имена
   отравлены `#pragma GCC poison`, чтобы ошибка была внятной. Негативный тест
   `make can-negative-test` проверяет это тем, что компиляция обязана
   провалиться:
   `error: attempt to use a poisoned identifier`.
3. **Таблица символов.** `twai_transmit` в образе отсутствует — его выбрасывает
   сборщик мусора компоновщика, потому что вызывать его неоткуда. Проверяется
   `tools/esp32_smoke.sh`. Символы `twai_hal_*tx*` остаются: их тянет общий
   обработчик прерывания. Выполниться они не могут — очередь передачи имеет
   нулевую длину, поставить в неё кадр нечем.
4. **Аппаратный режим.** `TWAI_MODE_LISTEN_ONLY` устанавливает `mode_reg.lom`
   контроллера, совместимого с SJA1000: передатчик отключён, ни кадров, ни
   битов подтверждения, ни error frames. Драйвер дополнительно возвращает
   `ESP_ERR_NOT_SUPPORTED` из `twai_transmit()` до обращения к железу
   (`components/driver/twai/twai.c:718-721`).

Режим задан константой в одном месте и защищён `_Static_assert`.
Восстановление шины режим не меняет.

## 7. Влияние на реальное время

Сравнение сделано на одном и том же двоичном файле: приём CAN можно
остановить командой `can-stop`, поэтому разница приписывается именно ему, а не
предполагается.

| | CAN работает | CAN остановлен | v0.6E (CAN в сборке не было) |
|---|---|---|---|
| контур, средний период | 2000.0 мкс | 2006.0 | 2000.0 |
| контур, p99 | 2920 | 2880 | 2640 |
| контур, опозданий | 19.87 % | 19.76 % | 38.96 % |
| контур, пропусков | 1 | 1 | 0 |
| `refloat_thd`, опозданий | 23.91 % | 23.36 % | 50.81 % |
| `refloat_thd`, пропусков | 1 | 1 | 0 |

Разница между «CAN работает» и «CAN остановлен» — доли процента, то есть
**приём CAN на контур не влияет**. Обработки внутри прерывания нет: задача
приёма живёт на ядре housekeeping и разбирает кадры после `twai_receive()`.

Одиночные пропуски дедлайна присутствуют в обоих режимах **одинаково**, то
есть к CAN не относятся. Максимальный период 4342 мкс совпадает по
длительности с одним печатным блоком диагностической консоли на 115200 бод.
Это уже вторая встреча с тем же свойством: на v0.6C по той же причине
стресс-тест I2C пришлось перенести на ядро housekeeping.

Но «не из-за CAN» не означает «неважно». Пропуск дедлайна в контуре
балансировки — это потеря управления, чем бы он ни был вызван, поэтому вопрос
зафиксирован отдельным блокером:

```
DIAGNOSTIC UART CAN BLOCK REALTIME
```

Перед `MOTOR_CAPABLE` блокирующая печать из контекста, способного задержать
контур, должна быть либо запрещена, либо вынесена так, чтобы физически не
могла его задержать. Исправлять это на v0.7A не следует: требуется
архитектурное решение по выводу диагностики, а не точечная правка.

Подгонять критерий «missed = 0» под текущее поведение нельзя.

## 8. Что установлено про приложение на VESC

Четыре независимых признака, все указывают в одну сторону:

| Признак | Значение | Что означает |
|---|---|---|
| `custom_config` в `COMM_FW_VERSION` | 0 на обеих половинах | ни один пакет не зарегистрировал свою конфигурацию |
| `app_to_use` | `UART` (3) на обеих | встроенное балансировочное приложение не выбрано |
| `COMM_LISP_GET_STATS` | нет ответа на обеих | скрипт LispBM не запущен |
| `COMM_GET_QML_UI_APP` | длина 0 | интерфейса пакета нет |

**Refloat на этом VESC не установлен, и никакого другого пакета тоже.**
Предположение, с которого начинался этап, не подтвердилось — и это хорошая
новость: выводить из роли контроллера нечего.

Практическое следствие: сам по себе VESC сейчас не может выдать ток на мотор.
С `app_to_use = UART` он исполняет только то, что ему пришлют по USB, UART или
CAN, и ничего не инициирует.

Половины различаются в 14 параметрах: `foc_motor_r`, `foc_motor_l`,
`foc_motor_ld_lq_diff`, `foc_current_kp/ki`, четыре элемента hall-таблицы и
шесть токовых и потенциальных смещений. Это подпись **раздельно проведённой
FOC-детекции**, а не копии настроек.

### Пересчёт коэффициента контура

`motor_data.c:106`:
`speed_constant = 1 / (1.5 · 0.5 · poles · flux_linkage)`, а коэффициент
Refloat — `kp · TORQUE_CONSTANT_COMPAT · speed_constant` при `kp` = 20 и
`TORQUE_CONSTANT_COMPAT` = 0.6075.

| Источник | poles | flux | `speed_constant` | А на градус | Насыщение по току |
|---|---|---|---|---|---|
| Заглушка FloatCore | 30 | 0.0045 | 9.877 | **120.0** | 0.083° при 10 A |
| VESC, реальная | 14 | 0.1000 | 0.952 | **11.6** | 2.16° при 25 A |

**Аномалия 120 А/градус, обнаруженная на v0.6E, с реальными параметрами
исчезает.** Причина была в заглушке: `flux_linkage` занижен в 22 раза, а число
полюсов завышено вдвое.

Оговорка обязательна и относится к самому статусу этого числа.

`si_motor_poles = 14` — **значение конфигурации, а не измерение**. Моторы
физически отключены весь этап, детекция с ними не проводилась, и подтвердить
число полюсов реального мотор-колеса было нечем. У мотор-колеса их обычно
около 30, и тогда тот же расчёт даёт 5.4 А/градус и насыщение при 4.6°.

Поэтому **11.6 А/градус — текущая оценка по прочитанной конфигурации, а не
физическая константа.** Настоящее значение ляжет между пятью и двенадцатью и
станет известно только после подключения мотора и детекции.

Значения FloatCore на этом этапе **не менялись**: ТЗ v0.7A этого не требует, а
подставлять параметры чужого мотора в свою заглушку без подключённого мотора
означало бы поменять одну недостоверную величину на другую.

## 10. Что понадобится перед этапом с мотором

По состоянию VESC:

1. **Ничего удалять не нужно.** Пакета нет, `app_to_use = UART`. Самый
   безопасный и близкий к штатной архитектуре вариант — оставить как есть:
   VESC остаётся исполнителем, FloatCore будет единственным источником
   балансировочных команд.
2. **Проверить `app_to_use` перед первым подключением мотора.** Если к тому
   времени там окажется `ADC`, `PPM` или балансировочное приложение, VESC
   сможет выдавать ток самостоятельно, и двух контроллеров быть не должно.
   Правильное действие — сменить `app_to_use` на `No App` или `UART`, а не
   удалять что-либо: смена штатна, обратима и не трогает детекцию мотора.
3. **`timeout_msec` = 1000** на обеих половинах. Для балансировочного контура
   это много: при потере связи мотор будет держать последнюю команду секунду.
   Значение придётся пересмотреть вместе с частотой команд.
4. **Детекция мотора** после подключения: `si_motor_poles`, `flux_linkage` и
   пределы тока сейчас не соответствуют реальному мотор-колесу.
5. **`si_battery_cells` = 3** не согласуется с отсечками 34/31 В, выставленными
   под 10S. Расхождение надо устранить до езды.

## 11. Итоговый статус этапа v0.7A

```
PASS:          пассивный подъём CAN и аудит VESC
OPEN BLOCKER:  блокирующий диагностический UART изредка вызывает пропуск
               дедлайна, независимо от CAN
```

Подъём CAN считается успешным: связь доказана, обе половины наблюдаются,
частота совпала с предсказанной по конфигурации, ошибок шины ноль. Вопрос с
консолью остаётся открытым перед сборкой с мотором и не смешивается с CAN.

## 12. Чего этап не сделал

* Квалификация шины I2C по-прежнему **PENDING** — это отдельный открытый
  вопрос, и смешивать его с CAN нельзя. За время этапа накоплено 400 ошибок
  чтения I2C, Supervisor отработал штатно, критерии health не ослаблялись.
* Передача в CAN не реализована и не проверялась — по построению.
* `MOTOR_CAPABLE` не появился.
* Конфигурация VESC не изменена ни в одном параметре, прошивка не обновлялась.

## 13. Терминация: исследование, изменение и повторная квалификация

Этап после v0.7A. Никакого нового кода: прошивка та же, профиль тот же,
изменение только физическое и только на плате Waveshare.

### 13.1. Что на плате Waveshare — по схеме, а не по догадке

Официальная схема платы (`CAN_board.SchDoc`, ревизия 2011-09-05,
[waveshare.com](https://www.waveshare.com/w/upload/c/c5/SN65HVD230-CAN-Board-Schematic.pdf))
содержит **всего четыре компонента**, и нетлист однозначен:

```
U1    SN65HVD230
R1    10 kΩ    вывод 8 (Rs, slope control) → GND
R2    120 Ω    CANH (U1.6) ↔ CANL (U1.7)
can1  Header 2 винтовые клеммы CANH/CANL
P1    Header 4 3V3 / CAN_TX / CAN_RX / GND

CANH: can1.1 — R2.2 — U1.6
CANL: can1.2 — R2.1 — U1.7
```

Терминатор **R2 = 120 Ω подключён постоянно**: ни джампера, ни переключателя,
ни solder bridge на плате нет — резисторов на ней всего два, и второй это R1.

### 13.2. Локализация: измерения по частям

Все измерения на полностью обесточенной системе. Мультиметр недорогой:
**замкнутые щупы показывают 4.8 Ω**, поэтому абсолютные значения имеют
погрешность порядка нескольких ом, и требовать от них сходимости до десятых
долей нельзя.

| Что измерено | ДО | ПОСЛЕ |
|---|---|---|
| Собранная шина (клеммы Waveshare) | **35.3 Ω** | **51.4 Ω** |
| Waveshare отдельно, CAN отсоединён | **115.6 Ω** | **OL** |
| Dual FSESC отдельно | **54.8 Ω** | — |
| Щупы, замкнутые друг на друга | 4.8 Ω | 4.8 Ω |

Проверка модели «две ветви параллельно» на исходных данных:

```
115.6 ∥ 54.8 = 37.2 Ω   предсказано
                35.3 Ω   измерено
                 1.9 Ω   расхождение — меньше погрешности щупов 4.8 Ω
```

Скрытой третьей ветви нет: собранная шина объясняется целиком двумя
известными.

### 13.3. Почему гипотеза «три по 120» была ошибочной

Три параллельных 120 Ω дают ровно 40 Ω, и вывод v0.7A строился на этом. Но
**Dual FSESC изолированно даёт не 60 Ω, а 54.8** — то есть половины уже
терминированы сильнее, чем предполагает стандарт. Никакая комбинация из трёх
одинаковых 120 Ω такого не даёт.

Любопытный контекст: в опорной схеме VESC 4.x
(`vedderb/bldc-hardware`, `design/CAN.sch`) терминатор **не установлен вовсе**:

```
U401  SN65HVD232
R401  NI        <- Not Installed, позиция терминатора между CANH и CANL
R402  10k       <- Rs
C401  2.2u
```

Flipsky — клон, и что-то там впаяно, но **точный внутренний состав терминации
Dual FSESC неизвестен**: 54.8 Ω одинаково хорошо объясняется двумя по 100,
парой 120 ∥ 120 с чем-то ещё около 300, или тремя по 150. Разобрать плату ради
этого не предлагается, и **для принятого решения это знать не требуется**:
достаточно того, что FSESC-сторона измерима как единое целое.

### 13.4. Изменение

```
Waveshare R2 (≈120 Ω): один вывод поднят
Waveshare R1/Rs 10 kΩ: не тронут
```

Выпайки не было — поднят один вывод, поэтому изменение **обратимо одной
пайкой** и не требует нового компонента. Штатного джампера на плате нет, так
что другого способа отключить R2 не существует.

Резистор опознавался не по шелкографии, а прозвонкой: на плате два резистора,
и они различаются на три порядка — искомый показывает ~115 Ω, R1/Rs ~10 kΩ.

### 13.5. Целевое значение

Целиться в ровно 60.0 Ω на этом железе **бессмысленно**: реальный Dual FSESC
сам по себе измеряется около 50–55 Ω, и такой цели физически не существует.
Задача была снять **дополнительную** параллельную нагрузку Waveshare, а не
подогнать сопротивление под теоретическое число.

Убранная ветвь считается прямо из результата:

```
1/35.3 − 1/51.4 = 0.02833 − 0.01946 = 0.00887  →  113 Ω
```

то есть исчезло ровно то, что было снято.

Зачем это вообще понадобилось, если приём и при 35 Ω был безошибочным: по
даташиту TI минимальный дифференциальный выход `V_OD(D) = 1.5 В` **нормирован
при нагрузке R_L = 60 Ω**. При 35 Ω передатчик нагружен почти вдвое сильнее
условий спецификации. В PASSIVE это не проявляется — ESP32 не передаёт, а
драйверы FSESC на коротком проводе справляются. Проявиться может на активном
CAN, когда ESP32 начнёт вести шину и отдавать биты подтверждения.

### 13.6. Повторная пассивная квалификация после изменения

Прошивка не менялась. Окно измерения без единого байта в UART.

```
кадров            9669 за 96.5 с (100.2/с)
                  стандартных 0, расширенных 9669, RTR 0
DLC               8: все 9669
очередь           в очереди 0, потеряно 0, переполнений 0
ошибки            шины 0*, потерь арбитража 0, неудач передачи 0, приёма 0
состояние         RUNNING
идентификаторы    0x964 ext n=4837 50.1/с  VESC id=100 STATUS
                  0x976 ext n=4832 50.1/с  VESC id=118 STATUS
```

Сравнение с baseline v0.7A — совпадение полное:

| | ДО (v0.7A) | ПОСЛЕ |
|---|---|---|
| Кадров / время | 8974 / 89.5 с | 9669 / 96.5 с |
| Частота | 100.2/с | **100.2/с** |
| Идентификаторы | 118 и 100 | 118 и 100 |
| Потери приёма | 0 | 0 |
| Переполнения | 0 | 0 |
| Ошибки шины | 0 | 0* |
| Неожиданные кадры | нет | нет |

\* **Про звёздочку.** Первый прогон после подачи питания показал
`ошибок шины 7`. Счётчик берётся из `twai_get_status_info()` и **накопительный
с момента установки драйвера**, а не с момента `can-reset`, поэтому число
абсолютное. Проверено измерением, а не рассуждением:

* за окно 96.5 с счётчик не изменился — было 7, стало 7, **прирост 0**;
* после `can-stop` / `can-start` (переустановка драйвера на уже активной шине)
  за 61.5 с и 6162 кадра — **ровно 0 ошибок**.

Второе снимает и естественное подозрение, что ошибки возникают при входе на
работающую шину в середине кадра: не возникают. Остаётся подача питания: ESP32
уже слушала, когда поднималось питание FSESC и его трансиверы проходили
неопределённое состояние. Это артефакт последовательности включения, а не
качество шины. Установившийся темп ошибок за 158 с наблюдения и 15 831 кадр —
**ноль**.
